# Operation Contract Corpus (TP-SEAM-CORPUS-001)

Cross-engine contract corpus for the structured editor-operation seam,
created under `plans/PLAN_2026-06-11_operation_seam_unification.md` §3 T1.
Every case file in this directory is executed by **both** operation engines
inside their normal test suites and must produce identical semantic outcomes
and one identical canonical hash of the applied model document:

- **Rust contract reference:** `core/model_operations/operation_applier`
  via `tests/contract_corpus.rs` (runs under plain `cargo test` in that
  crate directory).
- **Browser mirror:** `apps/desktop/src/services/operationService.ts`
  via `apps/desktop/src/services/operationContractCorpus.test.ts` (runs under
  plain `npm test --workspace apps/desktop` from the project root).

The Rust crate is the contract reference: expected outcomes are generated by
running the Rust engine, and the TypeScript engine is held to them.

## Case file format

Each `case_*.json` carries:

| Field | Meaning |
|---|---|
| `case_id` / `description` | Stable id and human description. |
| `mode` | `apply` or `validate_only` — which engine entry point the runners call. |
| `base_model` | Self-contained invented preview-model derivative the case runs against (derived from the existing engine test models). |
| `intent` | The `EditorOperationIntent` record under test (one case intentionally carries an incomplete intent). |
| `claimed_model_hash` | Optional claimed-hash evidence passed to the engine, or `null`. |
| `expected.outcome` | The semantic outcome projection both engines must produce (see comparison rules). |
| `expected.applied_model` | The full applied model document for accepted applies, else `null`. |
| `expected.applied_model_canonical_sha256` | Corpus-harness canonical hash of the applied model, else `null`. |

## Comparison rules (identical in both runners)

1. **Exact equality on semantic fields:** `mode`, identity echo fields
   (`operation_id`, `change_id`, `operation_kind`, `change_kind`,
   `target_object_type`, `target_ref`, `schema_version`, `document_kind`,
   `deliverable_refs`), all six `validation` states, `diff_preview` rows
   (all eight columns), `acceptance`, `audit_boundary`,
   `professional_boundary`, `input_model_unchanged`, the claim-echo subset of
   `model_basis` (`claimed_model_hash`, `claimed_hash_canonicalization`,
   `binding_status`), and the derived `applied` flag.
2. **Diagnostics** are compared **order-insensitively** as semantic records
   `{code, severity, blocking, affected_refs}`, sorted by
   `code + affected_refs + severity` (plain codepoint order) in both
   runners. `blocking` is derived as `severity == "blocking"`.
3. **Applied model documents** are compared **both** ways:
   - parsed-JSON deep equality against `expected.applied_model` (numbers
     compared by value, so `1` and `1.0` literals are equal); and
   - the corpus-harness canonical hash must equal
     `expected.applied_model_canonical_sha256` from **both** engines'
     outputs. This hash parity is the guarantee under test: it catches
     number-serialization or precision drift that deep equality may mask.
4. **Input model immutability** is asserted in both runners (the engines must
   never mutate the input document).

### Corpus-harness canonical hash

`sha256` over a canonical JSON encoding: lexicographically sorted object
keys, arrays in original order, UTF-8, numbers rendered
ECMAScript-`ToString`-compatible (integral doubles render without a trailing
`.0`, i.e. `1` not `1.0`; otherwise shortest round-trip). The TypeScript
runner reuses `canonicalJson` from `apps/desktop/src/services/hashService.ts`
(JSON.stringify number rendering); the Rust runner implements matching
rendering in the test harness.

**Number-range constraint:** corpus numbers must stay finite with
`|v| < 1e15` and (`v == 0` or `|v| >= 1e-6`), and corpus strings stay ASCII,
so ECMAScript and Rust shortest-round-trip renderings agree. The Rust
harness asserts the range and fails loudly on violations.

### Engine-identity exclusion allowlist

These are the **only** fields excluded from cross-engine comparison. Every
exclusion exists because the field intentionally identifies the engine or its
internal canonicalization, not the operation semantics:

| Excluded field | Why excluded |
|---|---|
| `application_route` | Honest engine-route label by design: `tauri_backend_apply` (Rust) vs `browser_fixture_local_apply` (TS). |
| `model_basis.backend_model_hash` | Hash of the input model under each engine's own canonicalization; the canonicalizations differ by design (see next row), so the values differ. Cross-engine hash parity is asserted through the corpus-harness hash instead. |
| `model_basis.backend_canonicalization` | Canonicalization label: `serde_json_sorted_keys_not_rfc8785` (Rust) vs `jcs_like_sorted_object_keys` (TS). |
| `applied_model_backend_hash` | Same engine-canonicalization difference as `backend_model_hash`. The runners assert presence/absence (set for accepted applies, null for blocked) and replace value comparison with the corpus-harness canonical hash, which both engines must reproduce exactly. |
| `diagnostics[].id` | Embeds the engine's internal diagnostic generation counter; not semantic. |
| `diagnostics[].source` | Engine self-identification path (`core/model_operations/operation_applier` vs `apps/desktop/src/services/operationService.ts`). |
| `diagnostics[].message`, `diagnostics[].remediation` | Prose only. The mirrors carry near-identical text but split a few payload-validation branches differently (e.g. the create-node payload checks emit one combined Rust message vs two staged TS messages for the same `OP-CREATE-NODE-PAYLOAD-INVALID` code), so prose is excluded; `code`, `severity`, `blocking`, and `affected_refs` are always compared. |

## Coverage floor (enforced by both runners, not just documented)

- Every operation kind has at least one accepted-apply case: `set_field`,
  `update_load`, `update_support`, `create_node`, `connect_pipe_run`,
  `create_load_case`, `create_primitive_load`, `create_combination`,
  `create_combination_term`, `delete_combination_term`.
- Block classes covered: duplicate id (`OP-TARGET-ALREADY-EXISTS`), missing
  target (`OP-TARGET-NOT-FOUND`), unit mismatch
  (`OP-UNIT-MISMATCH-CONVERSION-UNAVAILABLE`), invalid dimension
  (`OP-UNIT-DIMENSION-UNKNOWN`), stale before-value
  (`OP-STALE-BEFORE-VALUE`), deferred field (`OP-FIELD-EDIT-DEFERRED`),
  unsupported field path (`OP-FIELD-PATH-UNSUPPORTED`), non-finite magnitude
  (`OP-VALUE-NOT-NUMERIC`), empty required text (`OP-VALUE-EMPTY`).
- Dynamic field paths `primitive_loads.N.magnitude.value` and
  `terms.N.factor` each have at least one accepted and one blocked case.
- Deferred fields stay deferred: the corpus encodes blocked-stays-blocked for
  `Component.kind` and whole-record `Combination.terms` editing.

## Expectation generation (bless workflow)

Base models and intents are authored by hand (invented values only).
Expected outcomes are generated from the Rust contract reference:

```sh
cd core/model_operations/operation_applier
CORPUS_BLESS=1 cargo test --test contract_corpus
```

This rewrites the `expected` block of every case file from the Rust engine's
actual outcomes (files are re-serialized with sorted keys). Blessed output is
not self-validating: review the diff before relying on it, and re-run both
suites (`cargo test`, `npm test --workspace apps/desktop`) so the TypeScript
engine is re-verified against the regenerated expectations. Never bless to
make a failing case pass without understanding which engine changed.

## Quarantine convention

If a case exposes an ambiguous divergence (e.g. the Rust reference behavior
itself looks wrong), the case file moves to `_quarantine/` with a `TBD` note
and is excluded from both runners (they only read top-level `case_*.json`
files); the ambiguity is reported for human ruling instead of being silently
reconciled. Quarantined cases as of 2026-06-11: none — the TypeScript engine
reproduced all 44 cases exactly on first execution, with no alignment fixes.
