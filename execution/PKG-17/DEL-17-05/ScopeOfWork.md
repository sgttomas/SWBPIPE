# Scope of Work — DEL-17-05 CAEPIPE external run harness and CSV parser

## Purpose and Objective Traceability

This deliverable is the correlation loop with the external prover. An optional harness hands an MBF that SWBPIPE wrote to the user's own licensed CAEPIPE, collects the results CAEPIPE prints, parses them, binds them back to SWBPIPE's entities and compares them with SWBPIPE's own results; the benchmark set applies that loop across invented model families. The result it contributes is that the owner can see, case by case, where SWBPIPE's mechanics agree with CAEPIPE's and where they do not, each difference screened and classed, without the project bundling the tool, publishing what the tool produced, or reading agreement as professional acceptance.

It serves SOW-030, SOW-046 and SOW-075 under OBJ-007, OBJ-009, OBJ-017 and OBJ-018 (`execution/_Decomposition/SOFTWARE_DECOMP.md`, PKG-17, row DEL-17-05: the harness is optional and user-owned), with `docs/PRD.md` §8.9, §16.2 and §22.5, which makes correlation against an external professional solver the principal validation posture. It owns exit criterion 11 of `docs/RELEASE_TARGET_v1.0.md`: a run is screened against the benchmark method's tolerance profile where the benchmark manifest gives it a SWBPIPE counterpart and its conditions are met; a run without one is named with its reason and not counted; dynamics runs with a counterpart are captured as references and screened when modal and response-spectrum analysis are taken up after v1.0; the findings are triaged, and the owner has reviewed the full record.

- **OUT-001** — The external-run harness and the result parser: the opt-in harness around the user's executable, the run record and run package (`schemas/caepipe_external_run.schema.json`), and the parser of the CSV that CAEPIPE prints.
- **OUT-002** — The correlation and the benchmark set: the public invented cases and benchmark models, the comparison of SWBPIPE's results with CAEPIPE's, the screening against the benchmark method's profile and the triage of findings.

## Deliverable Definition — Ontology

**Terms the product implements.**

- *User-owned executable.* The user's own licensed CAEPIPE, on a machine the user controls. The project holds no copy of it, does not look for it and does not install it.
- *Exchange folder.* A private folder outside every repository, named by the environment variable `SWBPIPE_CAEPIPE_EXCHANGE`. It holds the harness configuration, in which the user names the executable and acknowledges responsibility for the licence and the execution environment, and every file a run produces. Everything CAEPIPE writes, and everything parsed or derived from it, lives here; nothing of it leaves except benchmark agreement the owner publishes under the data boundary policy.
- *Run record.* The account of one external run of one model in one run state: the configuration checked, the state of the executable path, the acknowledgement, the source model and export identifiers, and, where the model declares runs, the run's series, each line of the written MBF the run substitutes or adds, the instruction of a change entered at the program's window with its hash, the operator's (the person or agent operating the program) recorded check or skip and any stated correction, the model saved under the run's name before the analysis, the model batch file the operator exported from that saved model where the run declares an export, or that it was not made, and, for a screened run, the model document SWBPIPE solved, or, for a capture-only run, that no SWBPIPE solve or comparison was made, the MBF's hash and its identity file, the command shape actually used, the working directory and environment, the expected and the observed result file, the exit status, what output was captured, the parser's status and coverage, and the classification of the evidence. A window capture's record (`window_record.json`) is not a run record: it holds the files supplied after the run with their digests, the run line's text and the parse outcome, and is not evidence that a check, entry or save occurred.
- *Target CSV artifact.* The results file CAEPIPE prints for a run. "Expected" and "observed" are states of the same artifact.
- *Bound result.* A result file from a batch run is compared only when its run record binds it to the current MBF: the hash of the MBF on the host and the hash the guest script reported for the MBF it handed the program both equal the current MBF's hash. A print from a window run has no such binding: the window print route compares it only when the MBF stored with it is the writer's file for the run in the current checkout and the instruction stored with it is the run's declared instruction, and each such comparison states what a window capture cannot prove.
- *Capture-only run.* A declared run that has no SWBPIPE counterpart yet: no SWBPIPE state equals it, or the product has no headless entry for its analysis. Its print is collected and kept privately, may be read and parsed, and is compared once a counterpart exists. A hand-entry run's counterpart is SWBPIPE's solve of the model with the entered member; the window print route compares its print, and the run is not counted among the screened runs of exit criterion 11 while it is declared not screened. A dynamics run may declare the SWBPIPE options it would be compared under, but the product has no headless modal and response-spectrum entry yet: its capture is stored, and this route produces no dynamics comparison.
- *Sitting pack.* The committed set of run files at `validation/caepipe_sitting_pack/pack/`, with the Mac-side records each run holds or references (each case's identity sidecar and writer's report; REQ-005, REQ-006) in `validation/caepipe_sitting_pack/records/`. Its index is the run list: it names every file of both folders with its SHA-256 and size, and the SHA-256 of that index, recorded in `validation/caepipe_sitting_pack_identity.txt`, is the pack's identity. Every model file in it is the benchmark generator's output through DEL-17-04's writer, as REQ-005 permits, and has a provenance file beside it stating what is established of that file. Agents run its cases by operating the user's CAEPIPE (owner, 21 November 2026): through the harness where a case prints by batch, otherwise through the program's window by computer use. The prints that come back are read and parsed like any other, and compared where a route exists (Not met, below). The committed bytes do not change: the pack is no longer regenerated, and its builder and inputs have moved on since. The benchmark command does not read the pack: for each run it makes it writes the case's model file afresh from the tracked inputs through DEL-17-04's writer, and its run record binds that file, not the pack's copy.
- *Dry-run sample.* A copy, under its own item id and folder in the sitting pack, of one generator-made dynamics run file of the benchmark set: the run file of the smallest dynamics model in the form that carries both added records, with the SHA-256 the benchmark manifest declares for that run. The pack holds three: one run by the batch command, one opened in the program's window for the dry run's declared checks (i) to (iv), and the sacrificial duplicate the benchmark manifest names for check (v), on which alone the program's export is tried. A dry-run sample is not a benchmark case. Its output is private like every output of the prover, and may be read and parsed there; a public parser fixture of its layout is invented (REQ-009, REQ-013).
- *Parser coverage.* The sections of the printed CSV the parser reads. A section is read only after its column-header and unit rows are verified exactly; a unit is never assumed; values are normalized by the unit catalog's exact definitions; an unknown section is skipped with a diagnostic.
- *Binding.* The attachment of a parsed row to a SWBPIPE entity through the MBF writer's identity file: nodes by the node map, element end forces by the member whose map entry names the same two nodes, supports by node. A row is never bound by its position.
- *Comparison record.* For one quantity of one case: the independent hand-calculation value where one exists, SWBPIPE's value and CAEPIPE's value, in SI base units, with each check and a class for every difference. It identifies the internal model state hash, the exported model hash, the target tool and its version where disclosed, the import and export assumptions, manual changes, the load-case and support mappings, the comparison basis, the tolerance basis and the disposition of each difference (`docs/PRD.md` §22.5). A cause is a labelled hypothesis until evidence supports it.
- *Stated basis.* A named alternative binding or formulation evaluated on SWBPIPE's side for specified quantities and cases. The record preserves the unadjusted comparison, written before any basis is attempted, and shows each alternative beside it with its condition, reason, realization and independent check by closed form or by the product. It distinguishes a documented target convention, cited, from a comparison hypothesis. Each basis ends in a named outcome (applied, not applicable, not representable, refused by the product, or not compared for a run declared not screened) and never costs the plain comparison. Each additional solve has its own folder. The prover's results supply none of the choices, parameters or validation of a basis.
- *Screening profile.* The benchmark method's tolerances in the release target: 1e-4 relative when every input is held exactly; 5e-3 when a named inexact input remains; 2e-2 for nonlinear cases, with support status matching exactly; 5e-3 on modal frequencies with a modal assurance criterion of at least 0.99; plus a printed-resolution floor per result kind. A scalar passes when |S − C| ≤ a + r · max(|S|, |C|), with a the printed-resolution floor of its result kind and r the class tolerance. Values are only tightened.
- *Screening class.* `within_profile`, `finding` (outside the profile), `unmatched` (a value on one side only, a row that binds to nothing, a partial or non-finite sum, a parser error, a value with no established printed resolution other than a printed zero screened zero against zero, a SWBPIPE value in a unit of another dimension than its quantity's, or a value or required support-state match of a member entered at the window whose printed section is not read, with that cause stated) or `status_mismatch` (a case solved on one side and not printed on the other).
- The printed resolution that sets a floor is established per section of the print and printed unit, over the rows the parser kept, by an engineering judgment about one format family: fixed-place printing at the parser's candidate places for that unit, with trailing zeros omitted, uniform within a section. A nonzero token in the section that shows the candidate places establishes that those places occur, and the section's zero, blank and shorter tokens then take that resolution. The witness does not establish that those places are the most the print can show, or that every component of the section is printed alike. If the print is coarser than the judgment assumes, the effect is extra findings to examine; if it is finer, a difference smaller than one printed unit of the candidate places could pass. For each section and printed unit, shorter nonzero tokens without a full-places witness, excess places and exponent form keep their stated unmatched causes. Where the sole cause is that the section shows no nonzero token of the unit, a value whose contributing tokens are all fixed-point zeros, in a unit with candidate places, is screened with one unit at the candidate places as its floor, against a SWBPIPE value in a unit of the quantity's dimension; a blank token is not a printed zero. The record marks these rows and counts their agreements and findings separately, in its summary and in the command's printed counts. With rounding to nearest at a coarser precision, magnitudes below half a coarser unit can print as zero; at exactly half a unit the rounding convention decides. A rejected section or row, or an invalid binding, never supplies a resolution, and no resolution is borrowed across section, case, quantity or unit system. Each comparison record counts, per case, the quantities expected, screened and unmatched, and those unmatched for each cause; a case with no screened quantity says so, and is never read as within the profile.
- Printed resolution is not established for quantities printed in English units, including degrees in an English print, or for radian rotations. Those quantities are unmatched with that cause and are not screened; unit normalization alone does not establish their printed resolution. Screening them requires an established precision basis for each unit/format combination. Admission checks each print's actual unit labels: the SI writer alone establishes neither a print's units nor its angle format. No benchmark print to date carries such quantities; this does not cover the cases of tranches 2 and 3 or the declared runs not yet printed. If a case or declared run that exit criterion 11 requires prints such a quantity, it is unmatched, it is triaged as a finding, and the limitation is then recorded in the release limitations; an unmatched quantity is never counted as agreement, and triage does not make it one. Whether the target program's saved settings can change a print's units is not established, and the harness asserts no unit preference; the protection comes after the print, where the parser reports the print's units and such quantities are unmatched.
- *Inexact input.* A code-dependent input that changes mechanics and cannot be held equal on both sides. It is named on the model and carried by a one-parameter series.
- *Triage.* The examination of a finding in the benchmark method's order (mapping check, closed form, SWBPIPE's own invariants, convention series) ending in one of three classes: SWBPIPE's to fix, a documented convention difference, or unexplained.

**Boundary.** This deliverable owns the harness, the parser, the comparison, the cases and the benchmark models.

- The MBF writer, its identity file, the MBF importer and the authored MBF cases on which the importer is examined are DEL-17-04's. The harness runs the authored cases through the user's CAEPIPE as it runs its own cases, and this deliverable runs the importer's private regression on the MBFs its runs export; the importer's outcomes are DEL-17-04's.
- SWBPIPE's side of every comparison is the product's solve through the headless runner (DEL-10-05). Whether a mechanics capability is correct is a criterion of the deliverable that owns it; a finding classed as SWBPIPE's to fix goes to that deliverable.
- The reference system and the standing mechanics benchmarks are DEL-09-01's. The stress-neutral package is DEL-17-06's. The desktop panel that reviews external-run evidence is DEL-07-12's; it invokes nothing.
- The rule for what public text may say about the prover is DEL-01-02's. Publishing benchmark agreement, and the review of the full record, are the owner's.
- Stresses and code checks are outside every comparison.

**Not decided.**

- Which documented pattern is the first invocation profile, and which print-to-file sections form the parser's coverage (REQ-003, REQ-009; DEL-17-01 `TBD-17-01-004`). The pilot uses one documented pattern and a set of sections as a bounded pilot selection, which governs the pilot only.
- The screening tolerance of the response-spectrum class. It is set before any comparison run, from the class's closed-form references and never from comparison results.
- Which deliverable commits that each published result row names, by its model identifier, the entity it describes (node, element end, support). AC-004 and AC-005 find SWBPIPE's row for a bound member by it; DEL-08-04 commits stable row identifiers and a deterministic order only.
- The pipe shear shape factor and the default gravitational acceleration the prover uses (DEL-17-01 `CQ-17-01-010`). The hand calculations' shear coefficient is an assumption until it is answered by the vendor, or by a private one-parameter series run on the user's CAEPIPE.
- The tolerance within which a hand-calculation or closed-form value counts as agreeing with SWBPIPE's solve. Until it is set, each such difference is recorded and a correlation case's difference is classed (AC-005). Whether SWBPIPE's mechanics are correct remains the owning deliverable's criterion.

## Completion and Reliance Basis — Epistemology

### Requirements

- **REQ-001** — The harness is optional and disabled unless the user supplies a local executable path and accepts responsibility for the licence and the execution environment.
- **REQ-002** — The project does not bundle, download, install or redistribute CAEPIPE or CAEPIPE 3D+, does not wrap it to bypass its licence, and implies no availability of it.
- **REQ-003** — The first executable invocation profile stays undecided until public documentation, a support clarification or the owner's recorded selection of one documented pattern settles it.
- **REQ-004** — The harness records the command shape actually used, the working directory, the input MBF path, the expected and the observed CSV path, the exit status and captured output where available, and diagnostics.
- **REQ-005** — The MBF a run consumes is an output of DEL-17-04's writer, or that output with a declared substitution of whole lines or a declared addition of whole records, neither of which changes a node, element, support or load record. The lines that may be substituted are the data lines under a named options heading from a maintained short list (the pressure options record; the dynamics options record must be added to the list in the same change that first declares a run requiring its substitution). The records that may be added are whole options-level records that the vendor's public import page documents, from a maintained short list (the dynamics options record and the spectrum table); no support or load record is ever added to a written file. A value in an added record whose code or unit that page does not state is declared as such in the run, and the run is used with the operator's recorded check of what the program shows against the stated value, or in a declared form that leaves the record out and has the operator enter it. A file with an addition is not the bound file and is never imported as one. What no documented record carries is entered at the target program's window by the operator, as one named change in the run's declaration: each field with its value, its unit and its sign convention, each cited to the vendor's public page, and a field that page does not state is read from the program's window when the run is made and recorded with the run, never guessed. The operator saves the model under the run's own name before the analysis, and that saved file is held with the print. The run record names the writer's profile and carries each open question that profile carries; for a substituted or added file it also records each original, replacement and added line and the resulting file's hash, and for a change entered by hand the instruction and its hash; results are bound through the writer's identity file.
- **REQ-006** — The run directory holds or references the export manifest, the identity map, the loss report, the MBF input, the CSV output when produced, and the run metadata.
- **REQ-007** — The harness verifies operational facts only: input present, invocation attempted, result file found, parser run, expected sections and counts where confirmed, and diagnostics.
- **REQ-008** — No run or parsed output is classified as professional acceptance, code compliance, formal validation or proof of compatibility. A comparison is validation evidence and is never presented as professional acceptance (`docs/PRD.md` §22.5).
- **REQ-009** — The parser reads only sections confirmed by a public source or by an invented fixture, and reports an unsupported, unrecognized, missing or unmapped section as a diagnostic.
- **REQ-010** — Results are correlated to canonical identifiers through the writer's identity file and manifest; a correlation by row order or name alone is marked weak.
- **REQ-011** — Parsed results are bound to the source model, the export and the run before they are used as evidence.
- **REQ-012** — A check that needs the executable skips, with its reason, when none is configured, and does not fail public CI.
- **REQ-013** — Public parser fixtures are invented or rights-cleared; no CAEPIPE example, private project output or standards-derived data is committed.
- **REQ-014** — User-provided CAEPIPE outputs are private, local and excluded from telemetry by default; a public classification needs documented provenance and redistribution rights.
- **REQ-015** — Diagnostics preserve unit, coordinate, identity-map, loss-report and parser-coverage uncertainty instead of normalizing it away.
- **REQ-016** — External-run evidence binds to a DEL-17-04 MBF export package reference, and an attempted execution blocks unless both the licence and the environment responsibility are acknowledged.
- **REQ-017** — The benchmark compares mechanics only: displacements, rotations, element forces and moments, support loads, frequencies, mode shapes and spectrum responses.
- **REQ-018** — Every benchmark model is invented and comes from a seeded generator that covers model families from straight spans to nonlinear supports, hangers and dynamics; a closed-form member gives an independent third value.
- **REQ-019** — Each code-dependent input that changes mechanics is held equal on both sides or named as an inexact input and carried by a one-parameter series. Comparisons are used to find and fix SWBPIPE's defects; a difference is resolved by finding its cause, and no factor, default or tolerance is set in SWBPIPE only to make a result agree.
- **REQ-020** — Every result is screened with the screening profile. A result outside it, an unmatched row, and a status, refusal or mode-count mismatch are each a finding, and every finding is triaged.

**Not met.**

- AC-002 and VER-002 remain unmet for added-record and hand-entry runs: no code writes a run record for such a run or records the operator's check; its record is its run line and its saved model. The live batch command refuses such a run by name (window_run), since its batch round trip cannot make a window entry or check. The window print route records the files supplied after the run, their digests, the run line and the parse outcome. This evidence does not establish the file the program opened, the entries made, the settings used, or that the analysis was of the saved model; each offline comparison states these limits. Dynamics captures remain references under exit criterion 11 and are compared by no route.
- REQ-019 is not met for cpb-h-01: its named input constant_support_load (the target program computes the support's load itself; SWBPIPE states one) is carried by no one-parameter series. It is compared with that input named, and the difference it carries is attributed to that input until an independently justified one-parameter series supplies the evidence REQ-019 requires. The series's load values are never fitted to the captured result. The vendor's public technical page on the constant support names a route by which this input could be held equal ("To analyze an existing constant support with a known load, input it as a user hanger with a zero spring rate.", https://docs.sstcae.com/tech_manual/constant_support.htm); that route is taken next, with the load field's unit read from the program's window at the run.
- The SWBPIPE side of a comparison is recorded, not verified. Every solve the benchmark command makes, live or offline, is written into a new folder of its own, `swbpipe/<solve id>/`, named by the time, the commit and whether the tree was dirty; it records the SWBPIPE commit, whether its tree was clean, the SHA-256 of the runner binary at the path it executes, the SHA-256 of the request and result it wrote, and the mechanics status and numerical quality the product published for that solve. Its comparison is created beside it under `comparison/<solve id>/`, never replacing an earlier one (an id whose solve or comparison folder exists is never reused), and carries that record and the print it compared with: its path, its route, the SHA-256 of the bytes parsed and the attempt token, or for a print from the window print route its capture id. The comparison's stated bases are created after it, beside it, as `stated_bases.json`, each basis solve in a solve folder of its own. A case is never refused for already holding a request, a result or a case manifest: SWBPIPE's side of a case may be solved again at any revision and compared again with the same print, each comparison naming the revision it solved. A collected and bound CAEPIPE print and its run record are kept unchanged; because the harness's live round trip replaces a case's run record, the command refuses every live attempt on a case whose run record already names a collected print (route print_stored), and that print is compared again offline. A run record that ended in harness_error after a clean batch (start completed, exit status 0, input hash verified, a print route in the guest's report, and the print it named among the attempt's outputs with its digest) still establishes that print: it is refused live as print_stored and bound and compared offline. One that ended in harness_error with outputs collected but whose facts do not establish a clean batch is refused live as print_unestablished, with the facts it lacks, so the folder is kept for examination. A case manifest that is a symbolic link is refused at admission (manifest_link). Nothing checks the stored request and result against their digests later or shows that the runner was built from the recorded commit. The case manifest is the record of the live run: it is written before each attempt's round trip in the state round_trip_started, which shows only that no outcome of that attempt was written, and replaced with the attempt's outcome. A round trip whose start could not be established as not started, completed, or failed and ended leaves the manifest in that state and stops the run, with no settings restore. A round trip whose attempt claimed and ended without its terminal report records the outcome partial (route start_partial), and one whose success report is contradicted by its own nonzero dispatch reply, neither a transport line nor the session-unavailable line, records the outcome partial under route report_reply_contradiction, keeping the report and the reply whole; both are terminal, never retried and never compared. A round trip whose program has run is never retried. Two attempts each established as never started record route not_started. Once the round trip has been called, a failure to write the outcome it led to stops the run, so a due retry or stop is never lost.
- The binding of a print to the model actually run is not met. A print carries no reference to the model it came from. For a batch run through the harness, the run record binds the print to the MBF by the host's SHA-256 of the MBF it staged and the SHA-256 the guest script computed of its copy just before starting the program, which the script compares with the host's, starting nothing when they differ; the print and any model file the program left are read only once the attempt is established as ended and stored in that attempt's own folder. This shows which bytes were handed over and which files came back, not that the print was made from that model. For a window run, made by an agent operating the program's window, nothing hashes the file the program opened or binds the print to it: the model saved under the run's name before the analysis is kept with the print, and nothing yet examines that saved model.
- The window print route stores the regular files supplied for a declared window run under `caepipe_out/window/<first 12 hex of the print's SHA-256>/`, built under a temporary name and renamed into place complete; a stored capture is never written into, and an interrupted store is neither listed nor a bar to a retry. The record identifies the imported MBF, the declared instruction, the saved model and the print by digest, states the checkout it was stored in and whether the writer's file was a commit's, and names the sections the parser did not read. A comparison is made only where the run's declaration lets it be compared, and requires the stored MBF and instruction to match the run now and the print to parse with the current parser; it states the limits of that evidence. A hand-entry comparison carries the run's declared inexact inputs and screening classes, retains each available SWBPIPE reaction and closed form for the entered member, and identifies by name the external value or support state the parser cannot read. A print that fails to parse is retained and its comparison refused. For a batch run through the harness, each print is collected into its own case folder beside its run record.
- The run phase's guest primitives are not established on the deployed guest. That the claim's exclusive create is atomic on the configured work folder's storage, that every process the program starts stays a member of the attempt's named job until it ends, and that the reconciling queries see that job are taken from the platform's documentation and examined here only against a fake guest. A live check of those primitives, and the pinning of the work folder's storage, are not part of this repository. Every guest command the harness builds is at most 850 characters, a margin well inside the lengths established on the route, and one that is longer is refused before it is sent. The launcher query, the job query, the chunk read and the literal value's read-back are short calls of a content-addressed read script that changes nothing; the host's fence and the registry writes made through the registry API are short calls of a content-addressed write script, each operation confined by pattern; and the host accepts a reply from either only when its first line names the digests of that script and of any data file the host installed. The job query reads a job it opens as present, whatever its canary says; it reads one it cannot open as absent only when the open failed with file-not-found and the canary read just before it, in the same frame, shows that failure codes are captured, and as an error otherwise. A test on hosted Windows runners runs the exact read script's job query against jobs the test creates and closes; it shows the script's behaviour there, not the deployed guest's. A REG_BINARY value's data that would bring its write within 50 characters of the limit travels in such a data file; any other command over the limit is refused before it is sent, and a restore that needs one is refused before its first write. The harness is established for an English-language guest only: it reads the messages of the guest's `type` and `reg` commands in their English form, and on a guest in another language they read as unresolved or unknown, so a start whose claim or terminal report is absent stays unresolved and a restore stops at its first write through `reg`, failing closed; its liveness check likewise accepts only the English form of `ver`'s line. Before the first guest step of a live run, and before anything is staged, the command asks that liveness check up to four times, 30 s apart, and reads the guest's own drive letter for the exchange share from `net use` (a line whose remote is exactly `\\Mac\<exchange folder name>`, read only in that command's English form); it uses that drive root for the run in place of the configured guest exchange root, in memory only, and the run record of each live round trip states both. An unreachable guest stops the run, as does a share with no letter, more than one letter, a mapping whose status is neither OK nor blank, a reply that is not a `net use` listing in its English form, or a line that its column layout leaves open. A benchmark run checks its batch argument and its stop files before it asks, and checks the stop files again after each wait for an exclusive job. The harness's export of a stored solve to MBF is held: the guest script refuses it and starts nothing until the export adopts the attempt's claim and job. Until they are checked live, a live run is attended by the agent or person who starts it, one run at a time.

**What agents read and run.** Agents read everything in the private exchange folder (owner, 14 and 21 November 2026; `docs/IP_AND_DATA_BOUNDARY.md` §6.2.1): prints, run records, parsed results, comparisons and differences. They use them to find and fix disagreements. A stored print is compared when its run record binds it to the MBF the writer produces at the current commit, by the host's and the guest's hashes, and names it as a print the round trip collected, or establishes it after a harness error as stated above; where the run record holds a digest for the print, its bytes must match it, and the comparison records the SHA-256 of the bytes it parsed. A print from a window run is compared by the window print route instead, under the conditions of *Bound result* and only where the run's declaration lets it be compared. SWBPIPE's side is solved at a named commit, and each benchmark comparison record states SWBPIPE's numerical standing for that solve (LIM-026). Agents may operate the user's configured CAEPIPE on any invented model, the sitting pack's cases included: through the harness, or through the program's window by computer use where the harness does not reach. Nothing of it is committed or stated in public text (§6.2).

### Acceptance criteria

- **AC-001** — With no exchange folder configured, or with a configuration that lacks the responsibility acknowledgement, every live step skips with a stated reason, public CI passes, and the parser and comparison checks still run. The harness accepts an executable only as the path the user configured; it refuses an exchange folder inside a Git work tree or without an ignore-all rule, and a configured path that is not a plain absolute path, naming the field.
- **AC-002** — The run record of every run, skipped ones included, has each member of a run record as defined above, with a private path redacted where needed. A result file whose run record does not bind it to the current MBF is not compared. The run record names the MBF's profile and carries each open question that profile carries. Where REQ-005 permits a substitution or addition, the record preserves each original, replacement and added line and the resulting MBF's hash. Where it permits entry by hand or requires a window check, the record preserves the instruction and its hash, the operator's recorded check or skip and any stated correction, and identifies the model saved under the run's name before analysis and retained with its print. A declaration or an instruction hash alone is not evidence that a check, entry or save occurred.
- **AC-003** — On the invented print fixture, the parser returns the fixture's authored values, in its output units, for every covered section. A section whose header or unit row differs, or whose unit labels are not of one system, is refused and reported; an unknown section is skipped with a diagnostic; a conflicting duplicate row is reported; and no value is read under an assumed unit.
- **AC-004** — Every compared value is bound through the writer's identity file. A row pair that names no member or several, a second pair for one member, and a member with no pair are each reported as unmatched, and a row pair in another order or position is still bound to its member.
- **AC-005** — For each public correlation case, the comparison record holds the hand-calculation value, SWBPIPE's value and the prover's value for every quantity the case names, with each check and a class for every difference, the difference between the hand calculation and SWBPIPE included; and the case with a deliberately injected input fault is reported as a difference and classed. No difference is left without a class, no cause is recorded as established without its evidence, and every comparison record identifies each item `docs/PRD.md` §22.5 lists.
- **AC-006** — Every model of the benchmark set without declared runs has a benchmark record, and every declared screened run has its own benchmark record, in which every scalar of every mapped case is screened with the profile of its class and carries one screening class. A capture-only run keeps its case's identity. A batch capture-only run is collected, bound and parsed and screens nothing; a window capture-only run is refused by the batch runner as window_run and is run through the program's window. Neither is counted among the screened cases that exit criterion 11 asks for until a counterpart exists. No non-finite value and no partial sum is `within_profile`. Every finding has a triage class reached in the method's order, every comparison record identifies each item `docs/PRD.md` §22.5 lists, and the owner has reviewed the full record.
- **AC-007** — The benchmark generator gives the same bytes for the same seed, and the tracked models equal a fresh generation. Every model is invented, names per case, and per run where it declares runs, the inputs not held exactly, and belongs to a family. Every run a model declares names its series and the MBF the target program runs, with that file's hash, and, for a screened run, the model document SWBPIPE solves. The set holds straight spans, nonlinear supports, hangers and dynamic models (REQ-018); and each closed-form value a model carries is recorded, in each screened run state where it holds, beside SWBPIPE's solve of that state with their difference.
- **AC-008** — No tracked file is an output of the prover, a value parsed or derived from one, or a comparison or run record of a real run, apart from benchmark agreement the owner has published under the data boundary policy, and none sits under an exchange-style path; a file of such a kind is tracked only with a sidecar declaring it invented. A run package that embeds a private, protected or commercial payload blocks, and a package's privacy defaults are private, local-only and telemetry off under any partial override.
- **AC-009** — A run package validates against its schema, names the DEL-17-04 MBF export package it rests on, and blocks an attempted execution that lacks either acknowledgement. A skipped package records the configuration checked, why the path was absent or invalid, the skip reason and that parser-only checks ran. No package field, record or output classifies a run or parsed output as professional acceptance, code compliance, formal validation or proof of compatibility, or presents a comparison as professional acceptance.
- **AC-010** — Where an exchange folder is configured, the private regression check re-parses each stored result file, solves the case again, repeats the comparison and fails when any quantity's outcome, cause or evidence status leaves its recorded classification. It skips with its reason when no folder is configured.

## Production and Verification Method — Praxeology

**Method choices that define the product.**

- The harness runs one case at a time, in the user's environment, and stops no process it did not start.
- A batch result is bound by hash to the MBF that produced it before any value is compared; a window print is bound only by the digests of the files stored with it, and its comparison states that limit.
- The comparison works in SI base units, and the printed resolution of the prover's output sets the floor of every tolerance. A printed zero is screened only under the full conditions of the printed-resolution passage: a fixed-point zero whose sole no-witness cause is that its section shows no nonzero token of its unit, in a unit with candidate places, against a SWBPIPE value in a unit of the quantity's dimension. It is screened with one unit at the candidate places as its floor, marked and counted apart. A token with excess places or in exponent form keeps its row unmatched, even where the section shows no nonzero token.
- A difference is carried by a named hypothesis and a one-parameter series, never absorbed by a wider tolerance.
- The cases, models, settings, comparison rule and code are public; runs, results, comparisons and classifications are private, except benchmark agreement that the owner publishes under the data boundary policy.

**How each criterion is examined.**

- **VER-001** — Executable check (observes the harness with no configuration, with an unacknowledged configuration, with an exchange folder inside a work tree and with an invalid path): each skips or refuses with its stated reason, and no process is started.
- **VER-002** — Executable check (observes the run record written with a substituted runner for unchanged, substituted, added-record and hand-entry runs, including skips, and the comparison's refusal of an unbound result file). The check examines the lines and resulting MBF hash, the instruction and its hash, the recorded window checks or skips and corrections, the saved-model and print identities required by AC-002, and, where the run declares an export, the exported model batch file or the record that it was not made, with its association with that run's saved model and instruction; absent human observations remain absent rather than being manufactured by a test. The generator checks separately establish only the declarations and bytes it can produce.
- **VER-003** — Comparison with a named reference (the invented print fixture, whose values were authored by hand) and executable check (observes the parser on altered headers, mixed unit systems, unknown sections and duplicate rows).
- **VER-004** — Executable check (observes binding on invented tables with reordered, missing, duplicated and unbindable rows).
- **VER-005** — Comparison with a named reference (closed-form hand calculations that import no product code) and executable check (observes the comparison record of each public case on invented prover values, the fault-injected case included).
- **VER-006** — Comparison with a named reference (CAEPIPE's printed results for each benchmark model, produced by the user's own installation) screened by the release target's profile, and judgment by the owner: reviews the full record of screening and triage.
- **VER-007** — Executable check (observes the generator's output for a fixed seed against the tracked models, each model's declarations and family, and each closed-form value against SWBPIPE's solve).
- **VER-008** — Executable check (observes tracked files for prover output, exchange-style paths and undeclared derived records; and run packages with seeded private payloads and partial privacy overrides) and judgment by a reviewer who did not write the text: examines public text added in this deliverable for content that evaluates the prover.
- **VER-009** — Executable check (observes run packages against the schema, with and without each acknowledgement, and the skipped package's fields) and judgment by a reviewer who did not write them: examines records and outputs for the classifications REQ-008 excludes.
- **VER-010** — Executable check (observes the private regression check on an invented exchange folder and with none configured); the check itself runs where a real exchange folder is configured.

## Governing Values and Decisions — Axiology

- **AX-001** — *Breadth of comparison.* Better is more benchmark families, cases and result kinds screened, and fewer unmatched rows. Breadth is never bought by loosening a tolerance, by a factor set only to make a result agree, or by binding a row by its position.
- **AX-002** — *Explained differences.* Better is a larger share of findings triaged to a cause that a closed form or a series supports. A cause is never recorded without that evidence; the finding stays unexplained.
- **AX-003** — *The user's tool.* No convenience justifies finding, bundling or installing the executable, or running it without the user's configuration and acknowledgement.
- **AX-004** — *Evaluate privately.* Nothing that evaluates the prover leaves the exchange folder except what the data boundary policy lets the owner publish, and narrow confirmed parser coverage is preferred to a guess at an unconfirmed section.
