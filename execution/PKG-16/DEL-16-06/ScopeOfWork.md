# Scope of Work — DEL-16-06 Controlled model operation application

## Purpose and Objective Traceability

There is one way a model changes. An accepted, valid, previewed batch of structured operations is applied whole, by one engine, to the model state it was written for; anything else leaves the model exactly as it was and says so. This deliverable is that mutation seam, and it is also the embedded agent that works through it: an assistant in the desktop's conversation panel that reads the model, proposes changes, solves and reports through SWBPIPE's own capability catalog, and whose changes wait for the person. The result it contributes is that every edit, by a person or an agent, arrives at the model by the same checked route, and that a person can ask the agent to build and solve a system without giving up the decision on any change.

It serves SOW-069 and SOW-070 under OBJ-015 (`execution/_Decomposition/SOFTWARE_DECOMP.md`, PKG-16, row DEL-16-06), with `docs/PRD.md` §5.3, §10.3 and FR-AGENT-001 to FR-AGENT-003. `docs/RELEASE_TARGET_v1.0.md` exit criterion 17 names this deliverable: from a person's request in the conversation panel, the embedded agent builds the reference system, solves it and reports its key results through SWBPIPE's capability catalog; every change goes through the one operation route and is applied on the person's acceptance or within autonomy the person granted; and the agent records no acceptance, approval or reliance.

- **OUT-001** — Application of accepted operations to the current model.
- **OUT-002** — Refusal without change: every rejected, invalid, blocked or stale request leaves the model as it was.
- **OUT-003** — The one operation engine, in its native build and its web build.
- **OUT-004** — The application outcome, handed to the operation history and to persistence.
- **OUT-005** — The embedded agent host and SWBPIPE's capability catalog.

## Deliverable Definition — Ontology

**Terms of application.**

- *Operation engine.* The single implementation the product uses to validate and apply operations. It is built natively for the desktop and as WebAssembly for the browser build. No other code applies an operation.
- *Apply.* A function of a model document, a batch and the model hash the batch claims. It returns a new model document with an outcome, or no document. It never alters the document it was given.
- *Whole or nothing.* Each operation of a batch applies to the document the previous one left. If any is refused, no document is returned.
- *Basis.* The model hash a batch was written and accepted against. Application requires it to be the hash of the document being changed.
- *Outcome.* What an application returns: the batch, each operation with its author, the diagnostics, the hash applied to, the resulting hash, the record of the person's acceptance of the change, and whether the result has been saved.
- *Publication.* The workspace session taking an applied document as its current model. It is the only way an edit of the current model's content reaches the session; opening, creating or replacing a project, and undo and redo of a checkpoint, are DEL-07-11's and DEL-02-05's session acts.
- *Person-entered value.* The bend flexibility factor k, the SIFs, the other component modifiers (stiffness scaling and stiffness) and their source. Users enter their own k and SIF.

**Terms of the embedded agent.**

- *Embedded agent.* An agent runtime the desktop starts on the person's explicit action and talks to over a private pipe. It reaches a model provider only through the host.
- *Host.* The desktop's native side of the agent: it starts and contains the runtime, validates every tool call, binds it to the session, and returns results.
- *Capability catalog.* SWBPIPE's list of the tools the agent has, the operations it may propose, the jobs it may start and the acts it may request. It is the agent's whole reach into the product. Every tool has exactly one of four effects: it reads, proposes, computes or requests. For each tool the catalog states three things separately: its effect; its policy class, which says whose act the effect waits for; and where the tool is exposed. In this release the policy class of every propose and request tool is that the person's own act is required. The class is stated apart from the effect so that a later decision on autonomy changes a class and no effect. The admitted operations are a closed list of operation kind, object type, change kind and field path; the kinds and object types are drawn from DEL-16-01's taxonomy. The jobs and the requestable acts are closed lists too.
- *Read.* A bounded return of what the product already holds: the model and its records, findings, results and the tables the desktop derives from them, saved states and recorded runs, the outcome of a job, and the standing of a proposal or a request. A read changes nothing in the model, the project store or any file. It may move what the desktop shows to the thing read, the selected entity or the located result; that is view state, which nothing stores, and it never changes what a pending proposal or request is about. While the person's attention is held (while a control's form or dialog is open, while the person is reviewing a proposal, or while the person is at a control a request took them to), nothing the agent controls moves or replaces what is displayed. A read that only returns what it read is not refused. What is refused is the change itself, at the moment it would reach the view: the navigation a read asked for, and the replacement of displayed content by a job's result. That holds also for a read or a job that began before the person's attention was held and completes during it. The refusal says what was not moved or replaced and why, and the agent may ask again later.
- *Compute.* Starting a job the product runs on the current model or on retained results, and waiting for its actual outcome: a solve, a rule check, a comparison, a hanger sizing. A job changes no model and writes nothing a person keeps: no stored state, run record, project or file.
- *Request.* An act the agent asks the person to perform: saving a model state, recording a run, saving the project, exporting a table, saving or printing a report, and the user release of a report. A request is never the act, and it runs nothing. Registering one makes its capture. The host registers the capture in the conversation panel's request list, unchangeable, stamped as requested and agent-authored with the conversation, turn and call it came from. Registering performs nothing and moves nothing the person is looking at. When the person chooses a request in the list, the desktop takes them to its own control for that act with the view set to the settings the capture names; that is view state, and it happens only on the person's choice. Choosing changes no source content, and a request that is no longer pending cannot be chosen. The person then performs the act through that control exactly as they would unasked: one explicit act where the control is one act, the control's own form or system dialog where it has one, and nothing added in front of either. Declining is the person's other choice. The act is the person's own, by the desktop's own route, and so passes every check and control its owning deliverable puts on it, the export and privacy controls of DEL-12-02 among them; no route takes a value from a request. A completed act is attributed to a request only on a receipt (below) of the invocation the person made from that request, whose content equals the request's capture. Equal content shows that what was asked for has been done; it does not show that the request caused it, and no record says that it did. An act the person makes without choosing the request, or on other content, is the person's own and settles no request. A request for a user release takes the person to the report's own release control (DEL-08-01 REQ-019): pressing that control is the person's selection, and the request carries no selection, no statement and no user-release standing; its record says only that the agent asked.
- *Capture.* What a request fixes when it is registered, stated for each requestable act in the catalog as a closed list of members of two kinds, with the rule by which each is judged equal. *Source content* is what the output would be made from, by its hash: the model document, the retained result of the run, the two sides of a comparison. A run is named by the hash of its retained result and its model, not by an identifier alone. *Settings* are what shapes the output, by value: a report's composition, a table's case, filter and units. The capture itself never changes. Source content is watched: when the live content a capture names changes or becomes unavailable, the request is stale. Settings are not watched: they are what the view is set to when the person chooses the request, a person or a read may move them freely before and after, and they are judged only on the receipt. Text the agent suggests for a stored record, such as a state's name, is registered and shown with the request; it fills no field, and it is no part of what is compared. What the person enters in the control (a state's name and notes, a release's selection and statement) is the person's: it is recorded with the act, and it is no part of the capture.
- *Commitment.* The point at which the person's act in the desktop's control can no longer be withdrawn by them: the one act of a one-act control, or the last choice of a control with a form or a system dialog (the dialog's own Save). A route that returns having performed nothing because the person cancelled within it has not been committed, whenever in the route its dialog opened, and the person may use the control again as often as they like. A request dispatches nothing, so nothing of a request is ever repeated: the person's committed act takes effect once, by the route's own rules, and a request is settled at most once.
- *Invocation.* One use of a desktop control for an act, from the moment the person starts it. The host gives each invocation its identity, natively, at that moment: before the route prepares anything and before any dialog opens. It records then the workspace, the session and the request the invocation is associated with, if any. An invocation's content is fixed when it starts. For a route whose native work precedes its last dialog, as a report save's does, the invocation started when the person started the control, not when they answered the dialog.
- *Association.* The link between a pending request and the invocation the person makes from it. It is made when the person chooses the request in the list and replaced when they choose another. An association from which no invocation has started ends when the person leaves the control it took them to and when the request leaves pending. An invocation that starts while an association is live is associated with that request and with no other, and that is fixed from its start whatever the person does next, navigating away included; the association is then spent, so that no second invocation starts from it. An invocation that starts with none live is associated with no request.
- *Receipt.* The owning route's own report to the host of one completed invocation, made natively and never by the webview's account. It carries the invocation's identity as the host made it; the kind of act; the workspace and the session; the export context it ran under (DEL-12-02), or that none applies where the act is not an export; and the content, by the members and rules of the capture for that act, as what the route actually took in and what it produced, never as a claim echoed back at completion. The host takes a receipt once. A receipt already taken, a receipt of an invocation that started before the request was registered, a receipt of an invocation the host did not itself identify, and a receipt from another workspace, another session or an earlier run of the application settle nothing.
- *Request standing.* Pending: registered and not settled. Pending does not mean that nothing happened, and it does not mean that the act may safely be asked for again. A cancelled or failed attempt leaves the request pending. What the host sees happen to a request (the person chose it, an attempt was cancelled, an attempt failed and the kind of failure the route reported, an attempt was started and no completion has been reported) is given to the agent's session as an observation of that request: the agent's observation of the request returns it, and the host reports a failed attempt, and an attempt with no reported completion, to the session with the request it concerns, so that the agent does not ask again without knowing. Whether to repeat an act whose outcome is uncertain is the person's to judge, and the observation says so. Declined: the person declined it. Refused: the host refused it and names why: at registration, or because the route reported that nothing needed writing (a state already stored is refused with that state's handle). Stale: source content the capture names changed, or became unavailable, while the request was pending. Withdrawn: the turn was interrupted or the session ended while it was pending. Declined, refused, stale and withdrawn are final: no later act or receipt settles such a request or returns it to pending. An invocation that had started before its request became stale or withdrawn still takes effect or not by the route's own rules; its real outcome, an uncertain one included, is reported to the agent's session as an observation on that request, and changes no standing. Performed: the host took a receipt, while the request was pending, of the invocation associated with it, which is the one the person made from this request after choosing it, and the receipt's content equals the capture. The standing points to the record of the act, which names the person as its actor and the host as its recorder, and means nothing beyond that act. Opening a control, building a release record, a cancelled save or a completed act on other content is not completion. Unknown: the route reported, for an invocation the host identified, that an act on equal content was committed and gave no evidence of its outcome, as after an error that may have followed a write. A completion the host cannot tie to an invocation it identified is rejected and changes nothing. One receipt settles at most one request, and settles it only when its invocation is associated with that request and its content equals that request's capture. An invocation associated with no request settles no request, whatever its content. Where its content equals the capture of a pending request, the host reports to the agent's session, as an observation on that request, that the person made a matching act, and nothing more: the request stays pending, and nothing says the person confirmed, answered or accepted it. An act whose route gives no receipt can be requested, and the person can perform it, but its request reaches only pending, declined, refused, stale or withdrawn, and a use case that requires the agent to observe that act's completion is unfinished for the agent however the act went (DEL-07-06 REQ-016). The catalog lists, for each requestable act, the standings its request can reach; an act is listed as one whose request can be settled only where its owning route gives a receipt, and a change to the list is a change to the catalog. Printing has a standing of its own in place of performed: *sent to the print dialog*. It is reached only on the route's receipt of the hand-over of the captured report to the system's print dialog, never on the press of the Print control, and it says in those words that nothing is known of what followed. What the person does in the system's dialog is not observed, so the rule that a cancelled control leaves its request pending does not apply after hand-over. Until the print route gives that receipt, a print request reaches only pending, declined, refused, stale or withdrawn.
- *Session.* The agent's conversation with one workspace: the model that was open when the person started the agent. Creating, opening or replacing a project, recovering an autosave and restarting the application end the session. None of them is an act the agent can request. Ending a session withdraws its pending requests and its pending proposals, and a later session does not inherit an earlier session's handles.
- *Proposal.* A batch the agent submits with its declared assumptions. The host registers it in the review queue, unchangeable, stamped as proposed and agent-authored with the conversation, turn and call it came from. Registering applies nothing.
- *Proposal standing.* Pending review, rejected, withdrawn, applied or unknown.
- *Live basis and retained basis.* A read of the model, a new proposal, a new request and a job are bound to the current model. Observing a proposal or a request and reading a run's results or a job's outcome are bound to the model state the proposal, the request, the run or the job was made on, and stay so when the model moves on. A request is bound to its capture: a receipt settles it only while it is pending, and equality is judged on the content the receipt carries, not on what the view shows.
- *Handle.* An opaque reference the host issues for a workspace, a proposal, a request, a run, a job's outcome or a page of results. It is valid for one running application, one workspace and one session, is not a path and proves no identity.
- *Provider.* The model service the person configures: endpoint, model identifier, context window and whether a key is needed. The key is held in the operating system's keychain.
- *Relay.* The host's loopback service through which the agent runtime reaches the provider. The runtime holds a per-start token for the relay and never the provider's key.
- *Supplier.* The stock agent runtime binary, pinned by version and by size and hash for each supported architecture.

**Boundary.**

- The record and the taxonomy are DEL-16-01's. Validation and the preview are DEL-16-02's: they are the validate-only mode of this engine. The person's decision, the author stamp and the operation history are DEL-16-03's. What an agent's rationale must carry and what no agent surface may state are DEL-16-04's.
- The rules of a change kind belong to the deliverable that owns the records it changes, which also owns that kind's module in the engine: the model-data records, settings, condition sets and the document validator (DEL-02-01), project units (DEL-02-02), the document version check (DEL-02-05), library application (DEL-03-01), model checks (DEL-04-06) and pressure and bend authoring (DEL-04-07). This deliverable owns the engine that runs them and the operations no other deliverable owns.
- The workspace session, with its live model, revision, review queue and undo and redo, is DEL-07-11's. The review surface with its preview and Apply is DEL-07-08's. Saving is DEL-02-05's. Taking the person to a desktop control with the view set to a request's capture, and attributing a route's receipt to a request, are this deliverable's; the routes, their receipts and what they write stay with their owners.
- The reference system, its key results and its independent references are DEL-09-01's. Building the supplier into the application and signing it are DEL-10-04's.
- What may be sent to a provider is set by `docs/IP_AND_DATA_BOUNDARY.md` §6.1. This deliverable adds no destination beyond the provider the person configured.

The embedded agent host is activated: it is part of the product, not held behind a gate awaiting a decision. It is to work on machines other than the one it was built on, which REQ-011 and AC-009 require and the activation does not establish.

**No autonomy in this release.** Exit criterion 17 allows a change applied within autonomy the person granted. None is built for v1.0. That is a choice the SWBPIPE Agent 0 made for this release, not an omission and not a standing prohibition: what this release offers is the person's own act on every change the agent proposes and on every act it requests, and a grant of autonomy has no design and no evidence behind it yet. So no tool applies, accepts or grants, as before; no tool performs a requested act or makes a release; and no setting lets a proposal or a request take effect without the person's act on it. Four things stay the person's: Apply on a proposal; every person-entered value; the act a request asks for, start to finish; and the selection and statement of a user release. What the product does without anyone's act, autosave among it (DEL-02-05), is unchanged.

**Rule packs in this release.** The person supplies a rule pack. The agent selects one from the local store by handle, evaluates it against a run and reads its outcomes; it writes no part of a pack. Help with drafting a pack is deferred for this release. That is a choice of scope the SWBPIPE Agent 0 made, not a professional prohibition: arranging criteria, mappings and expressions the user supplies into an attributed proposal for the user's review is drafting, not the adoption of a design basis (PRD §5.3 to §5.5). A later drafting capability would need governed storage, provenance, privacy and review of what is drafted, not merely another tool. The restrictions on person-entered values are separate and stand.

**Not decided.** Whether a later version lets the agent act within autonomy the person granted (DEL-16-03). Whether a later version helps draft a rule pack. Whether an agent may propose person-entered values (k, the SIFs, the other component modifiers and their source, and bend realization) is undecided. Release limitation LIM-001 (`docs/RELEASE_LIMITATIONS_v1.0.md`), which refuses them and leaves the person to enter them during the journey of exit criterion 17, awaits the SWBPIPE Agent 0's declaration under exit criterion 3, and is shown to the owner with the request for the verdict.

## Completion and Reliance Basis — Epistemology

### Requirements

- **CLM-001** — Only an explicitly accepted, valid, previewed batch of structured operations is applied, and only to the model whose hash is the batch's basis (SOW-069; PRD §5.3).
- **CLM-002** — A rejected, invalid, blocked or stale request changes nothing, and its outcome never looks like a success (SOW-069; decomposition PKG-16, which allows no hidden model mutation).
- **CLM-003** — One engine applies operations, with the same behaviour in its native and its web build, and with the meaning DEL-16-01's taxonomy gives each kind.
- **CLM-004** — An applied batch returns a deterministic outcome that says what changed, on which state and into which state. The outcome goes to DEL-16-03's history and DEL-02-05's persistence, and neither becomes another way to change a model (SOW-070).
- **CLM-005** — The desktop embeds an agent that operates SWBPIPE through the capability catalog (`docs/RELEASE_TARGET_v1.0.md` exit criterion 17). The host validates every call against the catalog and binds it to the live session. Every agent change enters the review queue as a proposal and is applied only by the person's act, through this engine. Every act the agent asks for is registered as a request and is performed only by the person, through the desktop's own control for that act. The agent's attribution, the model basis of every call, the bounds on what it reads and the true standing of every proposal are preserved. The agent runtime has no shell, file, patch or web capability, and that is established by observing it, not by configuring it.
- **REQ-006** — A batch is applied whole or not at all (decomposition AB-00-03).
- **REQ-007** — An operation whose author is not a person cannot write a person-entered value, by any route: a field edit, a component created with modifiers, a bend realization or insertion, or a library record that copies modifier members (`docs/RELEASE_TARGET_v1.0.md`, Pressure effects: users enter their own k and SIF).
- **REQ-008** — Reconnecting a pipe end refuses a pipe that a component names (a bend span, a tee leg, a rigid component, an expansion joint or a connector span), a pipe with a component other than a terminal marker at its fixed end or at the node it leaves or joins, a pipe that is a member of a pressure region, and a move onto a pressure region's internal node. Each refusal names what blocks it. Reconnecting inside a pressure region while keeping membership is not provided. Deleting a pipe is refused while any record names it and never removes other records.
- **REQ-009** — An agent route that consumes solve or preview results tells native execution from fixture fallback. If the native call fails, the route fails; fixture output is never reported as the result of a run.
- **REQ-010** — From a person's request in the conversation panel, the agent builds the reference system from a blank model, solves it and reports its key results, through the catalog (exit criterion 17).
- **REQ-012** — *Requests.* An act that writes to the project store, to a file or to a printer, or that makes a user release, reaches the agent only as a request, and no read or job performs one. A request names one act from the catalog's closed list and the things in the workspace it concerns, by handle. It names no file path, file name, destination or printer, and for a user release no selection or statement. A request runs nothing and supplies no value to any route: text the agent suggests for a stored record is shown with the request and fills no field, and it is never an output name, a path, a destination, the wording of a control or a statement of consent. Registering a request moves nothing the person is looking at; the view moves to a request's capture only when the person chooses that request. The person's act is their own, by the desktop's own control and route, with every check that route applies. A request is settled only on a receipt: the owning route's own native report of one invocation that the host itself identified when the person started it, naming the kind of act, the workspace, the session, the export context where the act is an export, and the content the route took in and produced, when that content equals the capture. A receipt is taken once and settles at most one request. A receipt of an invocation that started before the request was registered settles nothing, and neither does the agent's account, the webview's account or a record that existed before. A receipt settles a request only when its invocation is associated with that request, which is the invocation the person made from a request they chose, and its content equals that request's capture. An invocation the person made with no request chosen settles no request; where its content equals a pending request's capture, the agent's session is told that a matching act of the person was made, and the request stays pending. No record reads as the person's answer to a request. Equal content shows fulfilment, not cause. A change to the source content a capture names makes its request stale; a declined, refused, stale or withdrawn request is never settled or revived; and an invocation that had already started is reported to the agent's session with its real outcome. While the person's attention is held by a control's form or dialog, by the review of a proposal, or by a control a request took them to, nothing the agent controls moves or replaces what is displayed, whenever the read or job that would do so began. A pending request is never reported to the agent as nothing having happened: an attempt the host observed without a completion is reported to the agent's session as that, and repeating an act whose outcome is uncertain is the person's to judge. An act whose route gives no receipt leaves unfinished any use case that requires the agent to observe its completion. A state save or a run recording is requestable only while the project is stored on the revision the session holds, and a project save only as a save in place; otherwise the request is refused and says why. The catalog bounds how many requests may be pending and how many a turn may register, and the host refuses the excess before registering. Nothing the agent sends after registration changes a request, and a request is settled at most once. No record made by a request states acceptance, approval or reliance, and none reads as an act the person did not perform (F-PIP-3).
- **REQ-011** — The agent works on machines other than the one it was built on: the person configures the provider, the key is kept in the keychain, the supplier is bundled for the supported Mac architectures, and where isolation is not qualified the agent is unavailable and says why.

### Acceptance criteria

- **AC-001** — By each product route (a single edit, a batch in review, an agent proposal, an imported proposal), a batch is applied only when it passed validation, its preview was generated, the person accepted it and its basis is the current model's hash. The applied document passes the document validator, differs from the input by exactly the previewed rows with every member the batch does not name unchanged bit for bit, and has the hash the outcome reports.
- **AC-002** — For each of a contract-invalid record, a blocking validation finding, a missing acceptance, a stale basis, a stale before value and a refusal part-way through a batch: no document is returned, the input document is byte for byte the same with the same hash, the outcome says not applied and carries the named diagnostic, and it carries no acceptance record.
- **AC-003** — Every case of a shared set of operations gives the same outcome (validation states, preview rows, diagnostic codes with severity and affected references, boundary records) and the same canonical hash of the applied document in the native build and in the web build. No product route reaches a module outside the engine that applies or validates an operation.
- **AC-004** — For an applied batch the outcome names the batch, each operation with its author, the hash applied to and the resulting hash, and is the same for the same inputs. It says the result is in the session only until it is saved. After save and reopen the stored model's hash is the outcome's resulting hash. No edit of the model's content reaches the session except through an application.
- **AC-005** — With the pinned supplier and a model served on the person's own machine, in the native application, six things are observed. (a) Round trip: the model makes a tool call, the host validates it in full against the catalog whatever the provider did, answers with a value the model could not have known, and the model's reply is grounded in that value. (b) Containment: attempts by the runtime to run a shell command, read or write a file outside its private directory, patch a file, fetch from the web, reach any address but the relay, or start another process each fail, and built-in tool activity by the runtime ends the session. (c) Review: a proposal is registered in batch review with its operations, assumptions and attribution and is applied only by the person's Apply there, and a rejected proposal is observed as rejected. (d) Binding: a call on a stale basis is refused by name; a completion that is unknown, repeated, from another session or from an earlier run of the application is refused and nothing is dispatched again; a turn interrupted while a proposal is pending withdraws that proposal, one interrupted after application began reports the actual result, and an outcome without evidence is reported as unknown, never as success or rejection. (e) Reads: a read is bounded at the catalog's limits before it is collected, keeps the document's stored units, and returns a withheld value as withheld with no substitute number. (f) Custody: the provider key is absent from the runtime's environment, arguments and files, from the webview and from every log.
- **AC-006** — On every route, an operation whose author is not a person and that writes k, another component modifier or the modifier source, realizes or inserts a bend, creates a component with modifiers or applies a library record copying modifier members is refused by `OP-BEND-FLEXIBILITY-USER-ENTRY-REQUIRED` or `OP-COMPONENT-MODIFIER-USER-ENTRY-REQUIRED`. The catalog admits none of these. The agent's model summary lists the components that await the person's modifiers, and a solve report names every bend that is not realized, so no result is reported as if it were.
- **AC-007** — Each refusal of REQ-008 occurs, names the blocking component, region or record, and leaves the model unchanged; a reconnect none of them covers is applied; and deleting a pipe that a record names is refused with a list of the records.
- **AC-008** — In the packaged desktop, from requests typed in the conversation panel, the agent builds DEL-09-01's reference system from a blank model through proposals that a person applies, solves it on the exact pressure route and reports the named key results. The model built has every entity of the reference system's specification and no other; each reported value equals the value the results view shows for the same run; nothing was applied except by the person's Apply; and afterwards no record of acceptance, approval or reliance by the agent exists.
- **AC-009** — On a Mac of each supported architecture that holds no developer configuration, the person enters a provider in the panel, the key goes only to the keychain, the agent starts only when the person starts it, and a tool round trip completes. The supplier that runs is the bundled binary whose size and hash equal the pin for that architecture; no other binary is searched for. A locked keychain or a missing key gives an explicit unavailable state and no file is used in its place. On Windows and Linux the panel says isolation is not qualified and no supplier process starts.
- **AC-011** — For each requestable act, ten things are observed. (a) Registration: the request list shows the act, what it concerns, the agent's attribution and any text the agent suggested, equal to the capture as registered; nothing has been written, exported, printed or released; and what the person is looking at has not moved. (b) The person's act: choosing the request takes the person to the desktop's own control with the view set to the capture's settings, runs nothing and fills no field, which is observed in the control's fields immediately after the choice and before the person types; the person then performs the act by that control with nothing added in front of it, and what is written, exported or printed is what the same control produces when the person uses it unasked on the same content, as the deliverable that owns the act defines it, having passed the same checks and privacy controls. (c) Binding: a request is settled only on a receipt of an invocation the host identified natively when the person started the control, before any preparation or dialog; the receipt names the act's kind, the workspace, the session, the export context where the act is an export, and the content the route took in and produced; its content equals the capture; and it is taken once and settles at most one request. A receipt of an invocation that started before the request was registered settles nothing, whether the invocation completed before registration, was in flight at it, or had only its last dialog still to answer. An invocation the person made from a request they chose settles that request when its content equals that request's capture, and otherwise settles no request, a different request with an equal capture included. An invocation made with no request chosen settles no request: where its content equals a pending request's capture, the agent's session is given an observation on that request that the person made a matching act, the request stays pending, and nothing says the person confirmed, answered or accepted it. The association with a chosen request is replaced by a later choice; before any invocation starts from it, it ends when the person leaves the control or the request leaves pending; once an invocation starts from it, that invocation's association is fixed, navigating away included, and no second invocation starts from it. A change to the source content a capture names (the model, the run's retained result, either side of a comparison), whether made by the person or by an applied proposal, makes the request stale for good; a change of settings (a report's composition, a table's case, filter or units), by the person or by a read, makes nothing stale, and an invocation is judged on the settings its receipt carries. An act on other content, in another workspace or session, or under another export context settles no request, and no request is retargeted. (d) Refusals: a request that names a file path, file name, destination or printer, a release selection or statement, or an act outside the closed list is refused before registration; so is a request beyond the catalog's pending or per-turn bound, a state save or run recording while the project is not stored on the session's revision, and a project save that would not be a save in place; a state already stored is refused with its handle; and an attempt to change a registered request changes nothing. (e) Once: a person who opens a control from a request and cancels within it, at its form or at its system dialog, has performed nothing, the request is pending and the control can be used again, except that what the person does in the system's print dialog after hand-over is not observed; a request is settled at most once; a receipt presented a second time settles nothing; and a completion that is unknown to the host, repeated, forged, from another session or from an earlier run of the application settles nothing, performs nothing and changes no standing. (f) Interruption and end: a turn interrupted, or a session ended, while a request is pending withdraws it, and withdraws a pending proposal in the same way; declined, refused, stale and withdrawn are final; an invocation the person had already started takes effect or not by the route's own rules, settles nothing, and where the session still exists its real outcome is reported to it as an observation on that request. (g) Outcomes: each standing the catalog lists for an act is observed for that act as what it is, and no act is asked to show a standing the catalog does not list for it. Performed is reported only on a receipt, of the invocation associated with the request, whose content equals the capture, with the record of the act; a committed act on equal content, by an invocation the host identified, with no evidence of its outcome is unknown; a failed attempt leaves the request pending. A failed attempt, and an attempt the host observed with no completion reported, are each reported to the agent's session with the request they concern, and the agent's observation of the request returns them; the report of an attempt without a completion says the outcome is not known and that repeating the act is the person's to judge, and nothing given to the agent about a pending request reads as nothing having happened. A record that existed before the request, a matching model or run alone, the webview's account alone, and a completed act for other content are none of them evidence. The catalog's list of the standings each act's request can reach is checked against the routes: for each act listed as one whose request can be settled, the owning route's receipt reaches the host by a path the webview cannot write; an act whose route gives no receipt is not so listed, its request reaches only pending, declined, refused, stale or withdrawn, listing it otherwise fails the check, and a use case that requires the agent to observe its completion is reported unfinished. A print request reaches sent to the print dialog only on the route's receipt of the hand-over of the captured report, never on the press of the control, and never reaches performed. (h) User release: choosing the request takes the person to the report's own release control and opens nothing; the release flow opens only when the person presses that control, making their selection for that report, and the statement checkbox starts unticked; the request is performed only when the person completed the release there and the released package was published, never because the flow opened, the statement was ticked or a save was started and cancelled; completion is read from the save route's receipt for that invocation together with the published package, whose record binds every member of the report by content, so that a release of another composition of the same run is not taken for this one; and the release record contains the person's own selection and statement with the bindings and time DEL-08-01 REQ-019 requires, and names the agent nowhere. (i) Returns: no request, and no outcome or observation of a request, returned to the agent contains a file path, a file name or a readback of what was written, exported, printed or released. What the agent may read of the model, the results and the tables themselves is governed by Read and is not narrowed by this clause. (j) Attention: while a control's form or dialog is open, while the person is reviewing a proposal, or while the person is at a control a request took them to, no read moves the view and no job's result replaces what is displayed, including a read or a job that began before and completes then; the read still returns what it read; the refusal of the change says what was not moved or replaced and why; and the same read or job when none of these holds changes the view as before.
- **AC-010** — With the native solve made to fail, the agent's solve and result tools report the failure, and no fixture value appears in a result or in the agent's report.

## Production and Verification Method — Praxeology

**Method choices that define the product.**

- The engine is the Rust operation applier, compiled natively and to WebAssembly. TypeScript holds the user interface, the builders of operations and a thin routing adapter, and no validation or application logic (`docs/architecture/adr/ADR-0001_operation_seam_engine_unification.md`).
- Apply is pure: it returns a new document and writes nothing. Publishing to the session and saving are separate acts.
- The agent runtime is a stock Codex app-server, release 0.160.0 of `openai/codex`, run as a child process over private standard input and output. The catalog is offered to it as dynamic tools. The runtime is used as published and is not reimplemented.
- `apps/desktop/src-tauri/resources/agent-capability-catalog.json` is the one catalog; there is no second copy to edit.
- The host, not the agent, stamps status, author, attribution, the validation states and the boundary records; arguments that supply them are refused. Numbers the agent writes are kept as the text it wrote.
- The runtime reaches local and hosted providers alike through the host's loopback relay. A provider that is not on the loopback address is reached over HTTPS only.
- The runtime is contained by the operating system: a private home and working directory, one loopback port, and no start of another process. It inherits no developer configuration, instructions or credentials.
- The supplier is bundled per architecture and verified against its pinned size and hash before it runs. The pin manifest also names the supplier's licence and notice files.

**How each criterion is examined.**

- **VER-001** — AC-001, executable check: observes the returned document and outcome on each product route for an accepted current batch, a contract-invalid record, a blocking finding, an absent acceptance and a stale hash, and compares the applied document with the previewed rows using a differ that imports no engine code.
- **VER-002** — AC-002, executable check: observes the input document's bytes and hash before and after each refused path, and the outcome each returns.
- **VER-003** — AC-003, comparison between the native and the web build of the engine: the same operation corpus is run through both and their contract-visible outcomes and canonical hashes are compared; with an executable check that no product route reaches a module outside the engine that applies or validates.
- **VER-004** — AC-004, executable check: observes batch, basis and result identity from the application's outcome through publication, save and reopen in the native application, and that each edit of the session's model follows an application.
- **VER-005** — AC-005, executable check with judgment by a named role (a reviewer who did not write the host): runs the pinned supplier and a locally served model in the native application through the round trip, the denied-operation probes, the review of a proposal, and controlled protocol cases for each binding and interruption outcome; the reviewer examines the native commands and permissions the host adds.
- **VER-006** — AC-006, executable check: observes the engine's answer to each write path of a person-entered value under each author type, the catalog's admission of the same paths, and the summary and solve report on a model with unrealized bends.
- **VER-007** — AC-007, executable check: observes each reconnect refusal and its named blocker, an admitted reconnect, and the deletion of a pipe that records name.
- **VER-008** — AC-008, judgment by a named role (the owner, or a person the owner names, applying each proposal in the packaged application), with an executable check that judges the model tree, the results view and the agent's report against DEL-09-01's specification and key-result names. A scripted provider and a stand-in for the person examine the route only and do not settle this criterion.
- **VER-009** — AC-009, executable check: on a clean account of each supported architecture, observes provider entry, the keychain, the binary that runs and a round trip; then a locked keychain and a missing key; and on Windows and Linux the panel and the process list.
- **VER-010** — AC-010, executable check: forces the native solve to fail and observes the agent's tool results and report.
- **VER-011** — AC-011, executable check with judgment by a named role (a reviewer who did not write the host): for each requestable act, reads the project store, the export folder, the print hand-over and the release record directly, before the request, after registration, after the person chooses the request and after each standing the catalog lists for the act; reads the control's fields immediately after the person chooses a request and before any input; declines a request; makes each change of source content and each change of settings of (c), before an invocation, during one and after its commitment; performs the act on other content, in another session and under another export context; completes an act begun before registration, one in flight at registration, and one with only its last dialog unanswered at registration; with one request pending and with two of equal captures, performs the matching act with none chosen and reads the observation the agent's session is given and that nothing is settled; performs it after choosing each, and after choosing a request whose capture the act does not match; chooses one request and then another, and chooses one and leaves its control, before acting; starts an invocation from a chosen request and navigates away before it completes; presents a receipt twice; starts an attempt that reports no completion and reads what the agent's session is given; makes each refused request of (d); attempts each act through every read and compute tool and through a request alone, with no act by the person; cancels at each control's form and at its system dialog and uses the control again; interrupts and ends the session before the person starts the control, after they start it and after their commitment, and reads the standing and the late observation each leaves; for an act whose route gives no receipt, observes that the person's completed act leaves the request short of settled and that a use case needing its completion is reported unfinished; for a user release, observes separately the request chosen and nothing pressed, the flow opened and left, the statement ticked and the save cancelled at the file dialog, a published package, a publication whose outcome is uncertain, and a completed release of another composition of the same run; for printing, observes that the press of the control settles nothing and that only the route's receipt of the hand-over gives sent to the print dialog; for a route other than the release, an invocation whose outcome is uncertain; runs controlled protocol cases for each forged and repeated completion, for a completion reported by the webview with no receipt from the route, for a receipt naming another workspace, session, act or export context, for a receipt carrying an invocation identity, a start or an association the host did not make, for a receipt from an earlier run of the application, and for saturation of each bound; makes each read and starts each job of (j) with a form open, a dialog open, a proposal under review and a request's control open, starts each before the person opens one of these and lets it complete after, and makes each again with none; and compares the capture shown with the capture registered, and what the person's act produced with what the same control produces unasked on the same content. The expected result of each act is the one its owning deliverable's scope states. For each act the catalog lists as one whose request can be settled, the reviewer traces the owning route's receipt from the route to the host and confirms that it carries each member a receipt must, that the host made the invocation's identity before the route prepared anything, and that nothing in it passes through the webview's account; an act so listed without that receipt fails. The reviewer also examines what each request, observation and result returns to the agent.

## Governing Values and Decisions — Axiology

- **AX-001** — *One route.* Better is fewer code paths that can produce a changed model; the target is one. No caller, whether an agent, an import or a bulk edit, gets a shorter path that skips validation, the preview or the person's decision.
- **AX-002** — *Truthful outcomes.* Better is a smaller share of outcomes that end as unknown, reached by keeping the evidence of what happened. It is never reached by guessing: an uncertain result stays unknown, and nothing that might apply twice is retried.
- **AX-003** — *An agent that gets the work done.* Better is fewer turns, fewer refused proposals and a smaller prompt for the agent to build and solve the reference system. The weight is on the agent operating the application effectively, ahead of workflow machinery around it. Effectiveness never costs the person's Apply or a person-entered value.
- **AX-004** — *A contained agent.* Better is a smaller set of files, addresses and secrets the agent runtime can reach. The set is never widened to make a provider, a model or a platform work; where containment is not established the agent is unavailable.
