# Incremental project-setup after a scope change

Owner-authorized Root tranche `ROOT-PROJECT-SETUP-INCREMENTAL-20260926` adds an incremental setup mode to the bundled `project-setup` workflow, a bounded `REVISE` mode to `scope-of-work`, and a rule for reopening an `ISSUED` deliverable (D-GOV-50, `docs/SPEC.md` §3.3). Before this tranche, `project-setup` treated Functions 1 and 2 as one-time and deferred an active SCA to `scope-change`, while `scope-change` handed `ADD` back "through WORKING_ITEMS with project-setup", so setup of amended scope had no defined method. On 2026-09-26 the owner decided the tranche's open questions: "A, B, C and E all as recommended".

- `project-setup` now has two setup modes, inferred from workspace state: `INITIAL` (Functions 1–2, unchanged) and `INCREMENTAL` (new Function 5). An amendment still in progress is finished through `scope-change` first. `INCREMENTAL` runs after checkpoint group 3 acceptance against the accepted snapshot (`_ScopeChange/_LATEST.md`), its accepted action register (`Amendment_Actions.csv` or the register its group-2 manifest names), `Propagation_Plan.md` and `Handoff_State.md`. It reuses the recorded coordination representation and tracking mode.
- `ADD`: scaffolding happens after acceptance, not in the candidate. Incremental setup scaffolds only the new entities with the source-qualified `preparation` skill, then initializes production (`SOW_V1` through `scope-of-work` `MODE=INIT`; DOMAIN through `domain-documents` in its `SCA_DRIVEN` mode as the amendment's hand-off) and their dependency and status records. Existing folders, IDs, content and lifecycle state are preserved. `audit-scope-closure` is the post-acceptance closure check that the additions were scaffolded.
- `REMOVE` and retired `MERGE`/`SPLIT` sources: nothing is deleted. It confirms the `scope-change` retirement rule (the `[RETIRED — {AMENDMENT_ID}]` annotation and one `_STATUS.md` history line, lifecycle state unchanged). It appends the history line only where the accepted poststate lacks it.
- `MODIFY`/`RECLASSIFY`: no re-scaffolding. A `SOW_V1` deliverable at `INITIALIZED`, `SEMANTIC_READY` or `IN_PROGRESS` goes to `scope-of-work` `MODE=VERIFY` after a boundary-named edit, otherwise to the new `MODE=REVISE`. `REVISE` changes only the parts the amendment names, keeps IDs and unaffected content, records the amendment reference, ends with `MODE=VERIFY`, and never changes lifecycle state. `CHECKING` and `ISSUED` deliverables are held for the human.
- Reopening an `ISSUED` deliverable (D-GOV-50): `ISSUED → IN_PROGRESS` is authorized only by an accepted amendment (checkpoint group 3 accepted) whose accepted action register names the deliverable with `MODIFY`, or `RECLASSIFY` that changes its scope. The human records the transition in `_STATUS.md`, citing the accepted amendment snapshot, at the incremental setup's `MODIFY` routing. Tools do not enforce this yet: `tools/scaffolding/write_status.sh` and the App's lifecycle `transition.ts` still refuse `ISSUED → IN_PROGRESS` until they implement a check of the amendment record, so the human records it directly for now.
- Dependency stages rerun only for the affected deliverables and their neighbours, following the recorded `docs/SPEC.md` §5.3 mode. Under `FULL_GRAPH` the closure audit covers the accepted inventory, and an accepted project DAG that predates the amendment is reported stale.
- Setup evidence goes to a run record under `_Coordination/AgentRuns/<RunID>/` and a line in a new agent-owned, append-only `_Coordination/SETUP_LOG.md`. `_COORDINATION.md` stays human-owned and gains no setup-log section.
- Adoption baseline: when a loop adopts the incremental mode, its first run (Phase 5.0) writes one `BASELINE` line in `SETUP_LOG.md`, confirmed by the human, stating that amendments accepted up to that date are already set up. Those older amendments are never reprocessed.
- Human checkpoints: confirm the baseline once, confirm each incremental plan, then a report.
- `scope-change` records the hand-back to `project-setup` `INCREMENTAL` mode in `Handoff_State.md`, and a missing folder for an accepted addition is an `EXPECTED_CONSEQUENCE`. A production-contract update is handed back unless the accepted write boundary names `ScopeOfWork.md`. Its handoff also lists `ISSUED` deliverables the amendment authorizes the human to reopen.

Accepted SCA snapshots, existing `_COORDINATION.md` files, `_STATUS.md` records and historical run records are not rewritten. `docs/SPEC.md` changed in §3.3 and §3.4, so a loop that pins SPEC will see drift.

This loop holds accepted `SCA-*` amendments and uses `project-setup` and `scope-change` for its workspace. This loop decides its own adoption; this source tranche grants no release.
