## Recommendation and authority

**PROPOSAL:** Let a human complete a small, explicit engineering edit where it is made: enter coordinates or a property, see its draft effect and validation, then press Add/Apply (or an equally explicit commit gesture). Validate automatically, commit through the existing operation engine, update selection, invalidate stale results and offer one Undo. Let an agent prepare a coherent batch against a named model revision, explain the engineering intent and unresolved inputs, and present a readable grouped diff for the user's explicit application. Both paths must use identical typed operations and semantic checks. Their presentation and authorization evidence differ because authoring a command and reviewing an agent proposal are different acts.

The current interaction is already less restrictive than the parent's exploratory path suggests. `OperationApplyPanel.tsx:95–113` enables Apply independently of Validate and labels Apply “Validate and apply to the session model.” `BatchReviewPanel.tsx:43–44` likewise does not require a previous Validate click. The observed Queue → Pending → Validate → Apply sequence was a chosen route, not a compulsory four-stage approval procedure. A simplification estimate must therefore compare the actual shortest current path; no click-count or productivity improvement has been measured here.

The exact governing requirements support an inline human workflow:

- `docs/PRD.md:139–143` (§5.3): GUI and agent changes are structured, validated, shown to the user, and applied through the model engine; agent output cannot accept itself.
- `docs/_Registers/ScopeLedger.csv:70–71`: SOW-069 requires schema validation, constraint validation, diff preview and controlled application; SOW-070 requires history, rationale, assumptions, affected entities and audit metadata.
- PKG-00 DEL-00-05 `ArchitectureBasis.md`, REQ-05-02/03: application-service mutation and reversible edit undo/redo preserving solve-readiness diagnostics. DEL-00-03 REQ-03-01..04: commands/queries/jobs, transaction boundaries, result envelopes, and background-job cancellation/progress.
- `docs/CONTRACT.md`, OPS-K-AGENT-4 governs agent proposals, OPS-K-AUTH-1 prevents professional-reliance claims, and AUTH-2 binds any human acceptance record to reviewed hashes. Neither assigns a fixed number of buttons to a human edit.

**INFERENCE:** A draft preview shown inline before an explicit human commit, with automatic validation and a generated diff before publication, can satisfy these rules without changing authority. Do not interpret “direct manipulation” as writing the domain model directly. Pointer motion remains draft state; a deliberate completion action requests an engine transaction. Unexpected cascades or unresolved assumptions should open a review surface rather than silently enlarge that command. Successful basic edits need a concise result, not a repeated professional-boundary checklist.

## Implemented seam and its limits

**CODE:** `services/operationService.ts:57–84` routes native calls through Tauri and browser calls through WASM from the same Rust applier. `services/operationBatchService.ts:60–116` does the equivalent for batches. `src-tauri/src/lib.rs:1853–1886` exposes validate/apply single and batch commands. These are application seams, not a documented, authorized public agent transport.

`core/model_operations/operation_applier/src/atomic_batch.rs:34–198` checks submitted shape and original model hash, replays each member on a private evolving clone through the single-operation engine, and returns a model only if every step succeeds. A late failure publishes no partial model or acceptance. Validate discards temporary state and returns no applied model. Members can depend on earlier members. The outcome preserves ordered per-step diagnostics/diffs, input/batch/output hashes, and submitted intents explicitly marked untrusted. Author `agent` requires source metadata and rationale (`:303–320`); the test `author_metadata_is_preserved_and_user_agent_have_same_semantics` (`:660`) compares resulting user/agent model payloads. This establishes an inspected parity test design, not universal runtime parity.

`App.tsx:870–960` binds queued batches to a cloned basis, revision and hash; it checks revision and request generation around asynchronous work, rechecks the current hash, verifies returned basis/batch identity, and publishes one checkpoint on complete success. Single application has corresponding request/revision/hash checks (`:988–1075`). Queue clearing invalidates requests synchronously (`:853–868`). Undo/redo restore session checkpoints, capped at 25, clear computed outputs, and require later save (`:1087–1138`). These are useful single-session protections.

Two limits matter for a future command service. First, Tauri receives the whole model and claimed hash from its caller. Agreement proves consistency with that supplied model, not that it is the latest authoritative persisted project across writers. A public writer needs service-owned current revision and compare-and-swap publication; it cannot rely solely on an agent-supplied model/hash pair. Second, clearing a queue suppresses late publication; it does not demonstrate interruption of synchronous Rust replay. Expose the difference between withdrawal of intent and stopping computation. Existing solve cancellation has a separate generation/token flow (`App.tsx:574–699`), not a generic cancellation guarantee for all commands.

**CODE:** `AgentProposalPanel.tsx:136–145` is a deterministic review-only sample with Accept disabled. The newer toolkit `review.agent` routes to offline batch intake (`capabilityCatalog.ts`), with the live provider hold visible. These are distinct features; the disabled sample is not proof that offline agent-authored batches cannot apply.

The current catalog points to UI focus targets and supports discoverability; it is not yet a semantic command registry. Generate GUI affordances and future machine discovery from the same entries, retaining the accepted NORMATIVE-NOW/ROADMAP distinction.

The minimum contract families are read snapshot/search/inspect/references; prepare and validate batch; explicit commit/withdraw; history/undo/redo; save/open; and solve start/status/cancel/read results. Prepare returns base revision/hash, canonical operations, deterministic diff and structured findings. Commit consumes the exact prepared operation hash plus base revision and authorization evidence, revalidates, atomically publishes or rejects, and returns a receipt with new revision/hash and invalidations. Add idempotency keys before retries become externally possible. Unknown IDs, unavailable capabilities, stale bases and unsupported topology return typed errors; no private SQL or alternate model writer is exposed.
