## What is reusable, and what it actually means

**Authored model and scene.** The product document holds stable node, pipe, material, section, support, component and case IDs; pipes refer to endpoint nodes. It mixes authored physical intent and solver-oriented details such as `y_reference` and component consumption modes. It is a graph already, but component records primarily attach to a node plus kind-specific span references; there is no demonstrated general port/tangent/connection system. The viewport projects this document into tagged meshes. `pipeMesh` uses fixed display radii, not pipe OD, and components are symbols. Picking preserves entity identity. A pipe-like image therefore proves neither physical dimensions nor analytical idealization. [S05,S08]

**Topology/editing.** Existing operations create nodes and explicit straight runs, components, support/load records and shared sections. Atomic batches replay the same operation engine on private intermediate documents and publish one final model only if every step succeeds. Hash and before-state checks protect stale proposals; the UI provides one undo checkpoint per applied batch. General scene selection is one `EntityRef`, while GeometryTools has its own multiple-pipe checkboxes: useful local multi-selection, not a shared model-wide selection set. [S09,S10]

Splitting preserves the original pipe ID on the first half and creates explicit new node/pipe IDs. Endpoint nodal loads/supports can remain, but attached component or pipe-load/wind references block the geometry-only edit. Translate/rotate/mirror support copy or in-place modes; copies require explicit identity maps, rotations/mirrors transform orientation, and attached engineering data or unselected incident pipes block in-place edits. These guards are valuable: they are not a complete topology-aware transform. Route gestures and bend creation do not establish automatic tangent trimming, port mating, attachment redistribution, or an engineering routing constraint solver. [S09,S10]

**Engineering properties.** Shared section assignment/update/detach and cache checks exist. Their supported binding is pipe OD/wall; local mass inputs remain per span. Rust derives section properties and mass from explicit wall/tolerance/material/contents/insulation quantities. Self-weight generation produces source-hash-bound load-operation drafts with explicit gravity; it is not evidence of a persistent dependency that automatically regenerates accepted gravity loads after a density/section edit. Temperature-point material selection/interpolation and explicit load-case modulus bases exist. A catalog should provide reviewed data references, not hidden values. [S11,S12]

**Mechanics.** Reusable crates include six-DOF Euler–Bernoulli frame/straight-pipe elements, sparse interactive and dense scrutiny paths, linear restraints/springs, nonlinear support active sets, load application, case algebra and mechanics stress recovery. Product code includes thermal and pressure effects, explicit equivalent-static wind/seismic generation, component modifiers, expansion-joint user stiffness and curved-bend macro-elements. It supports more than a straight-only toy. However, branch/rigid/component review metadata and selected consumption modes must not be generalized to complete fitting mechanics. [S07,S13]

The curved-bend route replaces a mapped straight chord's stiffness, validates radius/chord/angle/orientation consistency, and has arc-specific recovery. Its numerical arc representation does not mean the authoring environment can automatically turn a routed corner into correctly trimmed tangent legs and a fitting. Global mechanics remains a centerline/frame idealization; no inspected requirement establishes need for a full solid CAD kernel. [S07,S13]

**Constraints.** The Python constraint engine checks supplied records, references, units, provenance and reported conflict states. For example it preserves a supplied `validation_status=conflict_detected` as a diagnostic. This is not evidence that it computes swept-volume clearance, slope feasibility or obstacle avoidance from the current 3D model. Those geometric evaluators are new work, preferably over simple centerline/swept envelopes initially. [S14]

## Recommended technical spine

**PROPOSAL:** introduce a small typed engineering-document service behind the existing structured operation boundary. Retain IDs and provide explicit migrations; do not turn Three.js meshes into truth or create a second GUI-only model editor. Start with nodes/junctions, straight and circular-arc centerline segments, component ports and connectivity, section/material references, support/load attachments, and engineering intent/assumptions. Add stable stations or attachment coordinates along spans so splitting and remeshing do not depend on array position. Keep fabrication-grade surfaces and general boolean solids outside the first scope.

Authoring must accept incomplete designs. Distinguish malformed edits (invalid identity, impossible numeric geometry, broken mandatory reference) from incomplete engineering assignments (unknown material, missing support/load, unresolved component idealization). Preserve unresolved intent and visible blockers while permitting save, further routing and review. Solve readiness is a separate query over a selected scenario. Current blank-model and missing-input diagnostics are useful foundations; avoid requiring all solve inputs just to lay out a route. [S06,S09]

Use deterministic projection services: (1) engineering graph to scene, with true OD/insulation envelopes where known and explicit symbols where unknown; (2) graph plus analysis choices to an immutable analytical snapshot; (3) analytical snapshot to existing numerical crates. The derivation manifest should bind source revision/hash, transformation version/settings, coordinate basis/conversions, library versions/hashes, scenario, warnings and exclusions, and one-to-many source-to-analytical mappings with station ranges and local frames. Numerical mesh refinement must never churn authored engineering identities.

The initial analytical adapter should expose the existing linear mechanics slice, not require complete support, bend and local-FEA coverage first. It can normalize one declared coordinate basis, derive sections, resolve explicit material values, compile straight elements and selected linear support/load families, and return existing result envelopes with a new source-map sidecar. Unsupported families remain editable but block this solve profile unless an explicit accepted idealization permits them. Validate equivalence against existing product/numerical fixtures before switching a caller.

Retain whole-model invalidation initially: it is conservative and straightforward. Add dependency-aware regeneration only when its read-set contract is reliable. Generated self-weight is a good first case: density/OD/wall/insulation changes must mark its load derivation stale and show a regeneratable diff, rather than silently leaving old weights or replacing user-entered loads. Store result records against immutable input snapshots; keep the old result available as historical after edits, never as current.

A general CAD kernel becomes justified only by concrete later needs—exact imported B-rep editing, boolean solid construction, fabrication detailing or robust surface interrogation. Clearance for initial piping routes can begin with explicit cylinders/arcs and equipment envelopes. This is an architectural proposal grounded in current centerline scope, not an externally benchmarked technology selection.
