## 1. A large canvas element is not necessarily a usable visible canvas

`App.tsx:1711–1725` places Toolkit immediately before PipeViewport inside one viewport column. `ToolkitPalette.tsx:55–114` inserts the complete searchable catalogue in normal document flow. `styles.css:3201–3209` permits it to grow to `min(60vh,36rem)`, with groups containing a button and explanatory paragraph for every command. At 768px frame height, 60vh is approximately 461px before considering surrounding chrome. The parent report is therefore consistent with the source layout: expanding discovery consumes the vertical region used to see and manipulate the model.

This is not simply the original short-canvas CSS returning. Current `styles.css:1268–1278` gives the viewport a 520px minimum, while its containing pane scrolls independently (`598–616`). A 520px off-screen or clipped element does not satisfy the product intent of a visible modeling surface. The model core also shares vertical space with a bottom dock (`App.tsx:1771–1784`); at widths below 1320px, the core minimum becomes 230px and dock minimum 280px (`styles.css:2939–2959`). Fixed-width tree/agent/inspector allocations compound the budget: expanded columns are 250/280–320/340px at that breakpoint, while viewport minimum is 400px. The source deliberately hides the agent when both tree and inspector are expanded (`524–532`), demonstrating that this is already a constrained state-dependent layout.

**Proposal, DEL-07-01/02/06 with DEL-07-09 contract ownership:** reserve visible canvas geometry across actual workflow states, not merely minimum element height. Put tool discovery in a bounded overlay/popover or a substitutable side panel. Keep a short, context-relevant toolbar accessible without reopening a catalogue. Use explicit pane resizing/collapse rules that preserve the selection and pending edit. Validate desktop sizes including the inherited 1203×768 and the old 1280×800 acceptance size; do not assume a large workstation monitor.

## 2. Capabilities exist, but authoring is organized around operation plumbing

Toolkit is a genuine executable index: search covers labels/groups/descriptions, commands explain unavailable selections, Escape restores toggle focus, and selection closes the catalogue (`ToolkitPalette.tsx:21–39,69–111`). App routing opens the relevant inspector/tree/dock and focuses a target (`App.tsx:1439–1456`). These are useful foundations, not an absence of tools.

Current viewport code supports orbit/pan/zoom, raycast picking, node coordinate capture, pipe endpoint selection, and component-node selection (`PipeViewport.tsx:286–308,588–619`). Node/pipe/component forms still render beneath the canvas and command bar (`811–817` onward). Support and load commands route elsewhere. Generic 15px icons are present beside Node, Pipe, Support, Component, and Load (`733–789`), so “no icons” would be incorrect. The catalogue itself is text-led; its source renders no per-command icon (`ToolkitPalette.tsx:79–100`). Distinct symbolic interaction can improve recognition without manufacturing engineering dimensions.

The inspector presents property readouts, a display card, provenance, flags, unit catalogue, a single-field review-intent builder, previews, queue, then multiple specialized creation forms (`PropertyInspector.tsx:281–406` onward). That structure exposes the operation mechanism more prominently than the selected object's editing task.

**Proposal, DEL-07-01/02/09:** organize entry around Select, Route pipe, Insert component, Restrain, Assign properties, and Loads; retain searchable access to the full accepted vocabulary. An active tool should show a concise next action, preview geometry, required fields, and commit/cancel affordance beside the model. A pending-changes count should open review directly. Preserve structured validation, hash binding, and undo; changing presentation need not bypass PKG-16. Repeated human creation and an agent batch can share transaction semantics while using different capture interfaces. Any automatic-apply policy change requires its own decision; it is not implied here.

## 3. Text is entering a quantity-specific presentation path

The normal node property list already keeps Label as text (`modelView.ts:69–75`). The separate inspector context card is the likely relevant path: `PropertyInspector.tsx:295–300` renders DualUnitValue unconditionally from the selected editable field. Its helper attempts numeric conversion but retains nonnumeric strings, then always passes the value to QuantityReadout (`1146–1154`). `display-units/index.tsx:81–94` emits “quantity is not a finite numeric value” for an invalid numeric source when a target exists. Thus a text label can acquire irrelevant unit/conversion messaging even when the property list is correctly typed. This is a source-supported mechanism consistent with the inherited symptom, not a native repro.

**Proposal, DEL-07-02:** distinguish text/reference/enum/quantity editors explicitly. Render quantity conversion and entered-unit context only for dimensioned numeric fields; preserve useful missing-value notices on actual quantities. Test labels, IDs, references, empty numeric fields, unsupported dimensions, and finite numbers under entered/SI/US display modes. Keep storage unchanged, per OPS-K-UNIT-1 and OPS-K-DATA-2.

## 4. June 18 recurrence is evidence of an acceptance gap, not a proven cause

The June 18 plan records the human complaint verbatim and specifies a canvas-first frame, one navigation spine, demoted telemetry, and creation forms outside the canvas (`PLAN_2026-06-18_workspace_redesign_c5_7.md:30–49,88–106`). It required a fresh packaged 13-step human pass at 1280×800 plus a larger size (`242–250`). Its own June 19 corrective note says an audit found B/C/D unmet after the initial increments, then records repairs while retaining the packaged human gate (`264–266`). Current source has real orbit controls, symbols, unit displays, collapse rails, and a menu/dock shell. The evidence therefore does not support “the redesign was never implemented,” nor does the historical plan establish today's current shell authority. Later decisions and exact binary provenance need separate reconstruction before attributing regression to a particular tranche.

Inspected tests provide meaningful functional evidence but a narrower acceptance bar. `ToolkitPalette.test.tsx` checks all 24 vocabulary rows, gating, search, Escape, and dispatch. `e2e/toolkit-batch-dist.spec.ts:5–55` exercises real Wasm, queue/apply, batch preview, and undo. `DisplayIntegration.test.tsx:12–43` checks actual quantity conversion and unchanged model/hash/drafts, but does not test a selected text field's context card. Older smoke checks include geometry and canvas screenshots: `r2-smoke.spec.ts:75–110` asserts usable pane dimensions greater than 64px and no status overlap; `497–502` checks color count and visible triad/cube/command bar. These are not equivalent to proving sustained canvas usefulness with Toolkit open or measuring a complete uncoached authoring journey. No blanket claim that the repository has no visual or geometry tests is justified.

**Proposal, DEL-07-06:** freeze a small set of representative interaction states and task walkthroughs before implementation. Measure visible, unobscured canvas bounds; inspect toolkit-open, form-open, pending-review, inspector-open, solve, and results states. Agree target sizes, readable controls, allowable scrolling, and task success with the human owner. Require build/version-bound packaged evidence and an independent usability session as separate deliverables from unit tests. Current `_STATUS.md:7–8` explicitly retains independent-usability and measurable readability/contrast holds as VERIFIED_NOT_VALIDATED; functional pass counts cannot close them.
