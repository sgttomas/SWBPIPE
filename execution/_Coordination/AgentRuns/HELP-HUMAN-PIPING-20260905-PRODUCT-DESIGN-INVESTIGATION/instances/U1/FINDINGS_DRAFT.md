## Recommendation and evidence calibration

The immediate design deliverable should be a tested interactive prototype of that work, including its incomplete and failed states. A larger command catalogue or visual restyling alone will not resolve the demonstrated workflow problem.

## Five core workflows

1. **Start and establish context.** New/Open leads directly to a model, coordinate triad, units, and useful empty-state action: “Start a pipe run.” Show the project name and save state. Ask for project units and explicitly selected material/section sources as needed; do not prefill engineering properties with plausible numbers. Permit intentionally incomplete geometry while labeling missing solve inputs.
2. **Route and refine.** Choose Route pipe, pick an existing endpoint or an explicit new start, and sketch successive orthogonal or freely directed segments with dimensional input. Show a ghost route, segment length, elevation, and candidate snap before committing. Select a segment to change length, insert an explicitly supported bend/component, or move an endpoint. An elbow choice must display the actual geometry and treatment available; an unsupported insertion must not masquerade as a successful symbol placement.
3. **Assign engineering meaning.** Select runs or segments, assign a named material/section source, add supports/restraints, connect equipment/nozzles, then define load cases and combinations. Make axes and degrees of freedom visible when entering restraint behavior. Show shared-reference impact before changing a section used by several pipes. Bulk editing complements geometric manipulation and preserves per-row units and provenance.
4. **Prepare and analyze.** “Check model” opens a focused list of affected objects and remedies. Separate geometry/connectivity issues, missing mechanics inputs, missing user-rule inputs, and provenance warnings. Where the derivation bridge exists, a read-only analytical view exposes element/node mapping and simplifications. Run an identified analysis state; show actual service progress and cancellation outcome. A non-converged or failed job remains a failed job, not an empty results screen.
5. **Review and iterate.** Choose run, load case, quantity, and display units; link the table and viewport. Inspect displacement, forces/reactions, stresses, and supplied rule ratios with their own availability states. Change a support or route, preview its affected objects, commit an operation, and compare explicitly named states/runs. Old results can remain inspectable only as results for their old model; do not show them as current.

These are proposed product journeys. Route gestures, insert-in-run semantics, attached-object transforms, derivation, and durable comparisons need separate capability/owner confirmation before being offered as implemented.

## Surface organization

Keep the existing workflow spine recognizable during prototype testing: Model, Loads, Analyze, Results, Rules, Report. Avoid adding a second mode rail. The canvas persists beneath contextual changes where useful. The exact labels/order can be tested, but should not be replaced by the internal command taxonomy.

| Surface | Proposed role and behavior |
|---|---|
| Top toolbar | Frequent verbs with recognizable icons and short labels: Select, Route pipe, Component, Support, Move, Measure; Undo/Redo and view controls. Context/selection determines availability. Less frequent commands live in searchable menus. |
| Left browser | Model hierarchy and search, entity-type filters, visibility/isolation, and selection. Grouping by system/run is a proposal requiring model support; use actual entities until available. Display units and IDs in details, not every tree label. |
| Center canvas | Primary work area; triad/view controls, ghost geometry, snap indicators, selected-object outline, direct handles, optional dimensions and engineering glyph layers. Toolbar opening must not consume its vertical space. |
| Right inspector | Selection-specific typed fields, compact required-data summary, and collapsible geometry, engineering, references, and provenance groups. During creation, this becomes the current tool options panel with a clear Finish/Cancel action. |
| Bottom table/drawer | Optional resizable model grid, issues, or result table. One active drawer; synchronized selection and scrolling. The viewport remains visible during row edits. |
| Status area | Active tool hint, coordinate/units context, save state, run status, issue count. Evidence, hashes, solver versions, and diagnostic codes remain reachable through Details. |

Choose one home for each field and action. Do not repeat the same selected properties in a readout, a quantity context card, an editor intent card, and a unit catalogue. A “More details” disclosure can preserve provenance, conversion support, and exact operation evidence without teaching internal schema vocabulary during routine work. Actionable warnings must remain visible, with affected object and repair action; hiding all warnings as telemetry would violate the intended safety behavior.

## Interaction and visual contract

**Selection:** click selects; modifier-click adds/removes; marquee selection uses an explicit documented containment/crossing convention; Escape backs out of the active action before clearing selection. Hover feedback differs from selected state. Overlapping geometry offers a pick list. Hidden objects do not unexpectedly participate. Tree, grid, inspector, and canvas share stable IDs and multi-selection; mixed values are explicitly “Mixed.” Preserve selection and camera during property edits where the operation permits.

**Manipulation:** separate orbit/pan/zoom from object editing, with visible active-tool state and keyboard alternatives. A move handle previews connected geometry and affected supports/components; if a supported operation cannot carry those attachments, explain the restriction before drag completion. Show numeric distance/elevation with units adjacent to the preview. Finish creates one reviewable operation or coherent transaction through the existing service path; Cancel leaves the model unchanged. An ergonomic Finish/Add action may orchestrate validation and commit without exposing an extra navigation round trip, subject to the owning operation contract and authorization semantics.

**Snapping:** start with endpoints, a visible world/reference grid, and axis constraints; surface the active snap type and target. A temporary override and typed coordinate entry must be available. Screen proximity is a candidate, not permission to silently merge topology. Distinguish “align with” from “connect to”; show connection outcome before commit. Adopt numeric tolerances only under explicit design/engine authority, never from visual intuition.

**Icons:** define one domain taxonomy across toolbar, tree, viewport legend, and inspector. Geometry: node, pipe, bend, tee, reducer. Boundary conditions: anchor, directional restraint, spring/hanger, equipment/nozzle. Loads/results: force arrow, moment arc, pressure, temperature, displacement. Application actions: select, move, rotate, duplicate, undo, search. Use consistent silhouettes, stroke weights, optical sizing, and state overlays. Generic platform symbols fit general actions; piping objects need domain-specific glyphs. Pair unfamiliar glyphs with labels/tooltips, accessible names, and shortcuts. Use color plus shape/text for selection, warnings, and result legends; never let a green symbol alone imply engineering approval.

**Typed microcopy:** “Name” accepts text and has no unit conversion. “X position” shows value plus unit. “Material missing — choose a material before analysis” names the action. “Cannot move this selection: connected support S-12 is outside the supported operation” names the restriction. “Results belong to Model 12; current model is 13” names staleness. “Rule checks unavailable — allowable stress not supplied” distinguishes rule readiness. Internal strings such as `conversion_performed`, unit-catalog routes, and DEC references belong in technical details. Preserve machine codes in copyable details for diagnosis.

**Failure and accessibility:** inline field errors preserve draft entries and focus the first failing field; cross-object failures link to the object. Distinguish empty, loading, unavailable, blocked, stale, failed, and cancelled. Keyboard users need complete tree/grid/inspector routes for modeled operations, visible focus, Escape behavior, and announcements of selection, validation, and job state. Check high contrast, color-vision differences, text enlargement, reduced motion, and trackpad/mouse operation. The adopted conformance/readability target remains a human decision under DEL-07-06; this packet proposes validation tasks, not a certification claim.

## Preventing another redesign recurrence

The June18 plan §1 records the same wall-of-strings and postage-stamp complaint. Its §8 already required a dominant viewport, no raw machine strings on default surfaces, and a packaged human journey. Section9 records a June19 corrective tranche because earlier increments failed criteria B/C/D. Some redesign components did land; recurrence does not prove that the entire prior redesign was ignored. The narrower evidenced concern is that later feature assembly can violate product outcomes while individual components and operation coverage still pass. Historical causation, ownership decisions, and the exact binary regression are not established here.

Proposed sequence, before implementation authorization:

1. **Freeze scenario and vocabulary evidence.** Map the five journeys to current operation capability, residuals, and landing owner. Confirm the geometry/analysis representation distinction with A2 and commit semantics with H3. Identify unavailable functions explicitly.
2. **Prototype the actual interactions.** Produce connected wireframes and an interactive prototype for route creation, support editing, bulk assignment, missing-data repair, and results iteration. Include small-window, expanded-tool, long-list, error, and mixed-selection states. Freeze the chosen design with rationale after review.
3. **Validate tasks with users.** Have the owner and independent representative users perform these tasks without coaching. Record completion, navigation detours, wrong-object edits, recovery, and comprehension of analysis state. Set performance/usability targets with the owner before judging success; favorable internal impressions are insufficient.
4. **Implement vertical journeys.** Keep one integration owner for the shell and icon/property system. Each slice includes geometry, inspector, validation, operation routing, and error/recovery behavior. A new capability must fit the approved frame and use existing field/icon patterns. Cross-package capabilities go to their owners; DEL-07-09 supplies organization/coverage, not editor implementation.
5. **Gate on outcomes in the packaged app.** Bind screenshots/video, checks, usability results, and limitations to the actual binary commit/build. Repeat a compact critical-journey set whenever a toolbar, drawer, inspector, or global navigation changes.

Candidate outcome checks: at 1200×768 and 1440×900, opening every tool leaves the route and active edit target visible and interactive; no clipping or horizontal page overflow occurs. A proposed initial compact-window budget is at least 600×420 clear canvas pixels during ordinary single-object authoring, to be tested and adjusted by the owner. This is a proposed product metric, not existing authority. A text label never produces a quantity diagnostic; unsupported conversions preserve entered values. Route, selection, bulk editing, cancel, and undo are demonstrated end to end. Required engineering values remain visibly missing. A failed derivation or stale result cannot read as ready/current. No raw policy/debug strings appear on default task surfaces. Keyboard task completion and warning/result comprehension are demonstrated separately from DOM-test success.

Closure here is an accepted investigation packet only. Authoritative product acceptance, engineering validation, derivative regeneration, implementation scope, and lifecycle status remain with their owners.
