## Rules implemented

### N-2: numbers (Python; Rust unchanged)

- **Numbers.** `_is_number` is now any `int` or `float`, with `bool` excluded. This matches `Value::Number` in Rust.
- **Conversion.** A new `_as_f64` mirrors `Value::as_f64`:
  - a `float` is returned as it is;
  - an `int` is converted with `float(value)`;
  - an `int` whose conversion overflows gives `None`.
- **Where the conversion applies.** `_number`, `_num_eq` (and so `_same`), the fit binding and the stored-primitive factor all use `_as_f64`. Every later equality therefore compares the binary64 values Rust compares. For example, `exact_point` requires `selection == point temperature`, and `100000000000000000001` equals `1e+20` in both languages.
- **Why the values agree.**
  - serde_json 1.0.151 is built with `float_roundtrip`. It holds an integer literal outside i64/u64 as the correctly rounded binary64.
  - It converts i64/u64 integers with `as f64`, which rounds to nearest with ties to even.
  - CPython's `float(int)` gives the same value in both cases.
- **Indices.** The `U64_MAX` bound is kept only in `_index`, giving `INTEGER_INVALID` as before.
- **Overflow.** An integer that overflows binary64 is refused in Python as `SOURCE_LOAD_REFERENCE_NUMBER_INVALID`, in the finite-tree step S2.
  - **Rust** refuses the same literal at the JSON text boundary. serde_json returns `ErrorCode::NumberOutOfRange` when the correctly rounded value is infinite (`f64_long_from_parts`), so no `Value` exists.
  - This is recorded as language-specific, the same way as the `NONFINITE-*` cases. The harness asserts that Rust fails to parse the text.
  - The boundary is the same in both languages. `2^1024 − 2^970 − 1` rounds to the largest finite binary64 and is admitted. `2^1024 − 2^970` is the tie, rounds to even (2^1024) and is refused.
- **Rust code.** Unchanged for N-2: `number` already used `as_f64`. The shared cases now pin that behaviour (mutant RS-N2-PIN).

## Questions and carry-forward

1. **Design question: readers admit, carriers refuse.**
   - **What happens.** Every accepted N-2 document is admitted by both readers at dispatch, in the validator and in transport. `numerical_use_standing` is `numerically_eligible` in both languages. But the canonical carrier build refuses it in both languages:
     - Rust `derivative::derive_document` gives `UNSAFE_JSON_NUMBER` (`guard_json`);
     - Python `build_analysis_run` gives `CHECKED-JSON-UNSAFE-INTEGER`, or `CHECKED-JSON-NUMBER-OUTSIDE-PROFILE` for the float forms, from `core/serialization/canonical_json/adapter.py`.
   - **Why.** The `openpipestress_jcs_ijson_v1` profile refuses any integral number with magnitude above 2^53 − 1, whether written as an integer or as `1e+20`. Every integer outside u64 is above that limit, so the N-2 exposure can never reach a carrier in either language.
   - **This predates this TASK.** The `1e+20` form was already reader-accepted and carrier-refused before it.
   - **How it is pinned.** I pinned the behaviour as it is: the new optional `carrier_rust` and `carrier_python` keys, with a note, record the exact refusal. The harness asserts it together with `numerically_eligible`, instead of building a record.
   - **Decision needed.** Should reader admission be aligned with the carrier number profile, for example by refusing integral magnitudes above 2^53 − 1 in both readers? That would be a further tightening, so I did not make it without your approval. The canonical-JSON layers are outside my boundary.
2. **New error code.** `SOURCE_LOAD_REFERENCE_LAW_SEGMENT_DUPLICATE` is new and identical in both languages. The adjacency and strict-interval rules reuse the existing `SOURCE_LOAD_REFERENCE_LAW_SEGMENT`.
3. **The `json_text` op in Rust.** The Rust harness requires every `json_text` literal to be refused at the text boundary. It exists only for literals that a serde_json `Value` cannot hold. Any other literal can be expressed as an ordinary `set`, because serde_json parses the case file exactly as it would parse a raw document.
4. **Not done.** I ran no broader suites beyond the brief's targeted checks (for example physics-1 consumers, stress-neutral and headless). The only reader change outside N-3 is Python's number admission, which affects only inputs that were refused before.
