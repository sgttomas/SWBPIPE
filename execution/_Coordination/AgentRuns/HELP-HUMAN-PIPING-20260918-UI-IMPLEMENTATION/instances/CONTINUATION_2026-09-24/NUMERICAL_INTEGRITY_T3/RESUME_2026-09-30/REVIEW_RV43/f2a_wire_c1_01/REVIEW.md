## RV43-F1 — Establish upstream no-wrap provenance before claiming exact charges

**Blocking; P1 for contract reliance. Location:** WIRE_CONTRACT.md:64–66 (also SOURCE_COMBINATIONS.md:107 and :126).

The projector is said to prove exactness for nonsaturated, internally consistent counters and checked sums. That condition is insufficient for this source: unchecked additions occur in the underlying SumWork components, not only in StageWork presentation counters. `wide_sum.rs:291,294,323,367,443,467,511,542` uses ordinary `+=` to accumulate term/shift/net/round work. `clear` retains those counters (:188–195). The saturating SumWork LME total and merge (:92–103) happen after these updates and cannot detect a component that already wrapped. `adaptive.rs:1296–1409,1428,1724–1730,1877,2288` and `verify.rs:522,743–747,1216` also form some totals using ordinary addition; StageWork::add at adaptive.rs:1186–1205 is another ordinary-add layer. In an overflow-checking build some such failures panic; in a build permitting unsigned wrap, a previously overflowing counter can be small again. MAX rejection covers saturation/equality ambiguity, not that history.

**Trigger and impact:** if any admitted source/count/unguarded-work segment reaches one of those unchecked overflows, post hoc safe-integer checks, checked W+K reconstruction, stage sums and meter deltas are not a proof of exact historical LME. Some checks may catch a particular inconsistency; all can derive from the same already-reduced counts, especially shared work exposed only as totals. The 20B/60B stop thresholds alone do not prove otherwise because checks are intermittent; for example condition_observed has no StageGuard parameter (`factor.rs:695ff`) and build_shared checks after it (`adaptive.rs:1366–1389`). A finite 128-limb accumulator bounds the cost of an individual operation, not cumulative operation count before the next check. The proposal's named `saturation_not_excluded` path does not expressly cover unchecked-wrap provenance.

This is **not** a demonstrated overflow on any present admitted workload, a claim that an accepted numerical result is wrong, or a request for a new solver experiment. It is a missing sufficient precondition in the future exact-receipt contract. Both replayed records are small and pass all arithmetic checks.

**Required correction:** replace the sufficiency claim with a requirement for independently checked upstream no-wrap evidence. Bind it to the actual admitted source/count/build profile and maximum work between guards, covering cumulative SumWork components, aggregate totals, stage additions and stopped/error paths. Make that obligation explicit in the P1–P5/admission dependency and W09 control inventory; inability to establish it must decline W1 before relying on an exact receipt, preserving the ordinary transaction. Alternatively, a separately authorized checked/sticky-overflow counter seam can deliver explicit overflow state without changing prices or numerical policy. Do not solve it by clipping totals, relabelling a wrapped counter as an exact charge, or assuming the provisional byte target enforces the bound. Any actual maintained counter change needs its own frozen write-set and review coverage.
