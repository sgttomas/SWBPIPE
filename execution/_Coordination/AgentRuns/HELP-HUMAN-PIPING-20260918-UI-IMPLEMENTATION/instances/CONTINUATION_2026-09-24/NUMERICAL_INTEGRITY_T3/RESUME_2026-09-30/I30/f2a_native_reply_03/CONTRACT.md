## 1. One transport outcome, not a backend state

Only a poll of an existing **completed W1 job** whose large-reply slot is temporarily
unavailable produces the proposed closed `W1ReplyBusy` control frame. It carries the
requested job identity and exact code `SOLVE_NATIVE_W1_REPLY_ADMISSION_UNAVAILABLE`.
Its exact proposed fields are `{reply_kind:"w1_reply_busy", job_id, code}`; no
caller-supplied retryable flag controls the retry. W1ReplyError uses the same three
fields with reply_kind="w1_reply_error" and a finite closed error-code set.
It has no `state`, result, error_message-as-backend-failure or terminal claim. The
stored backend record remains completed, with its real Value and resident lease.
Do not fabricate queued/running, turn the record failed, drop its result, start a
new solve or replay a completed request. Native direct solve is not retried by this
mechanism; its single response is covered by its own upfront completion reservation.

Implement the frame through the **existing poll command and service**, not a new
IPC endpoint/framework. Successful ordinary/exact statuses retain their existing
wire shape and error behavior. Proposed native return is a private non-Serialize
IpcResponse wrapper around either the normal status or a W1 transport control.
The service recognizes a control only after checking its closed shape, exact code
and matching requested job id. It turns Busy into a private branded transient
outcome/error; arbitrary error text, unknown codes or wrong-job frames never retry.

`pollPreviewMechanicsJob` currently awaits IPC before touching `jobInvocations`
(previewService.ts:209–230). Busy returns through the transient branch **before**
the terminal-state branch: no `terminalClaimed=true`, invalidation, map deletion,
registration or diagnostic mutation. Capture remains the original object created
for the actual dispatch, with its mode/fingerprints and cancellation state.

## 2. First-party state transition in the existing wait loop

Extend `awaitBackendSolveJob` (solveJobAudit.ts:150–157), not a general retry service.
Its narrow optional retrieval guard observes the originating run generation and
model revision; it does not mint capture. workspaceSession supplies this guard
from its existing `solveRunGate` and `modelRevision` at :823. The service retains
an identity reference to the original job capture solely for safe cleanup; it is
not a second capture or a new registration. Cleanup checks object identity before
removing a map entry, so a later registration reusing an id is never removed.

| Observed event | Exact next action |

| Current generation, normal queued/running status | Existing behavior: await the current 50-ms polling delay, then poll the same job. No new timing policy. |
| Current generation, valid W1 Busy | Retain job/capture/active generation; drop the received small frame; await that same existing delay; poll the same job again. Do not pass the transient outcome to workspaceSession's failure catch. |
| Repeated Busy | Repeat one-at-a-time. Keep one pending poll OR one timer, one last transient flag if needed, and the original capture reference. No growing error/event list, recursive retry promises, new job, or extra capture per iteration. |
| Slot becomes available; real completed status/result arrives | Existing identity checks and successor validation run; the real terminal response consumes terminalClaimed once, registers the actual source if valid, and removes the same capture entry. Return that real status to normal workspace completion. |
| Cancellation requested during Busy | Existing handleCancelRun/dispatchActiveSolveCancellation remains active; cancellation does not invalidate the run-generation token. Continue retrieval until a real terminal response. No additional cancellation request is generated by retry itself. |
| Backend accepts cancellation | Preserve service:233–251: invalidate/remove the original capture on the **actual accepted receipt**. Continue status polling; the real cancelled/failed status requires no result registration. Do not pretend a Busy reply accepted cancellation. |
| Cancellation is refused because backend is already completed | Keep capture and retrieve the completed response on a later poll. Preserve the existing receipt text/accepted=false behavior; do not fabricate cancelled state. |

| Wrong job, malformed control, unknown code, genuine IPC or validation error | Existing nonretryable/error behavior, with the selected specific custody/registration refusal where applicable. No broad catch-and-retry of errors and no solver rerun. |

Only actual terminal response processing or the existing accepted cancellation may
retire capture for those reasons. Busy alone does neither. The optional stale guard
must not conflate `isCancellationRequested` with stale: SolveRunGenerationGate keeps
the generation current during cancellation (solveGates.ts:22–33).

Retry has no attempt-count/time exhaustion that silently converts temporary reply
contention into a terminal solve failure. It stops deterministically on a real
terminal, actual nonretryable error or originating-generation detachment. If slots
never release, retrieval remains pending with constant retained state and working
cancellation/staleness handling; no time-to-result guarantee is claimed. The slot
release/wake behavior must be tested, not inferred from this statement.

For a real W1 terminal result, use one capture-local `validationPending` flag:
set it only after current/job/capture checks and before async successor validation;
clear it in finally. Recheck generation, original capture identity and invalidation
after validation, then commit terminalClaimed and registration only for that still-
current actual response. A second first-party validation of that capture waits by
the same sequential retrieval discipline (a local validation-pending outcome,
never a substituted backend state); it must not claim or delete it. The
official loop has one outstanding poll, so this is a fixed exclusion flag, not a
queue. Cancellation invalidation wins. Keep ordinary/exact terminal processing
unchanged; the W1 completion branch must not reorder their established error path.
The stale predicate is checked **inside validateCapturedSource immediately before
nativeSourceInvocations.set**, after its async reader/hash work; an outer check
after an already committed WeakMap registration is insufficient.

## 3. Owned replies, including denied and error paths

The selected metric is **application-owned Rust allocation through owned JSON-body
transfer**, not Tauri post-transfer queues, WebView/TS heaps or whole-process RSS.
Prior I30 and RV41 source-pin the Tauri IpcResponse::body seam; command return is too
early. Tauri's ordinary Err conversion builds InvokeError Value via serde_json
(ipc/mod.rs:240–251), so a guard dropped before that conversion does not cover it.

Clone drops after serialization; slot releases at transfer or actual error/abandoned-wrapper Drop, never command return. |

Wrapper retains that small owner through the same body transfer/drop. K large slots do not fund it. |

Bound its code/message/identity fields; do not format/copy the full result or arbitrary Debug tree into it. It is a real error, not Busy or a fake failed backend state; record stays unchanged. Service uses the existing specific-error path, not automatic retry. |
| Serializer/proof failure while building a W1 body | Drop any large partial buffer/clone at its actual last use, retaining the small error allowance, then produce the bounded reply-local error control. Its emergency small-buffer construction must be proved/available under P4. If it cannot be guaranteed, this caller profile is unqualified; do not claim an uncovered ordinary Tauri Err path meets the selected bound. | Ordinary/exact polling or errors, unknown-job/argument errors before a W1 scope exists | Preserve current wire/behavior. Their existing request/InvokeError costs are outside the W1 per-job success envelope; name them separately in the per-request/caller census. Do not silently throttle them or call their memory zero. |
| Abandonment/cancellation | Resident Value and reply copies have distinct owners. A UI cancellation or abandoned generation does not release a Rust reply still serializing. Only actual Rust Drop/transfer does. Current terminal records persist until actual record/table teardown. |

The explicit transport controls are a proposed realization of ROOT's transient
reply direction. They avoid dropping a W1 guard before Tauri's ordinary Err-to-Value
conversion. They do not change mechanics receipt/result semantics, ordinary error
channels, or introduce raw inspection/Current/export entitlement. Native tests must

## 4. P4 count contract — per-request is not an aggregate promise

Let R be resident job/lease/shared-container ownership, L the large reply bound,
D the denied/error request bound and S any simultaneously live shared reply state.
A per-job expression `R + K*L` covers only admitted large replies. With d live
control/error requests its aggregate is at least `R + K*L + d*D + S`; input parsing,
old/new buffer overlap and other named resident terms also enter their actual phase.
Never set d=0 or d≤K merely because denial is “small.” No numeric K,D or allowance
is selected here.

The first-party loop **enforces one pending poll or timer per active retrieval**;
it does not enforce a server-wide/per-job cap against arbitrary concurrent callers.
Each denied/error request has a finite local bound and owns its small permit through
transfer, but current native source supplies no aggregate cap on their simultaneous
population. An all-replies-per-job aggregate claim therefore still needs an explicit
admitted-request overlap bound and an enforcement/profile proof from P4. Without
that, report only the separate per-request bound and K-admitted-reply bound; do not
claim the complete native allowance has been proved. No queue/registry framework
or ordinary-request throttling is authorized by this packet.

P4's finite inputs: actual request/id byte lengths, bounded control code/message
lengths, UTF-8/JSON escaping and float formatting maxima, Value/String capacities
and moves, simultaneous partial/full/error buffers, large/control wrapper headers,
resident lease/ref counts, actual registry backing treatment, serializer/build pins,
and live denied/error request count or its enforced premise. Framework queues after
the declared transfer, unrelated requests/jobs and TS heaps are explicit exclusions,
not bounds. TS waiting keeps one timer/promise/capture and no per-Busy history; that
functional fact is separate from Rust byte qualification.
