## 1. Exactness is history, not a final numeric predicate

A sufficient checked-work design needs values accompanied by sticky loss/inconsistency state, or fail-stop operations whose failure custody is equally complete. Distinguish clean exact MAX, overflow, subtraction underflow/inconsistent provenance, and unavailable evidence. Once any operand is inexact, subtraction or multiplication by zero must not make the ownership history exact again. MAX−MAX is not a zero proof. ## 2. A sufficient pre-mutation carry invariant

The two 128-limb magnitudes use 8,128 payload bits plus 64 headroom bits. add_raw checks the span between the lowest term bit and largest raw-term leading bit; it does not count terms. It mutates anchor/magnitudes before the final `term_limbs += limbs+1`; carry increments also occur after writes. Thus “detect work overflow eventually” alone does not prove a safe prior magnitude.

One sufficient local invariant is: while a sum remains usable, every successful nonzero raw insertion contributes at least one (in fact limbs+1>=2) unit to an exact monotone lifetime term-work counter. Before any shift, anchor change or raw write, establish room for the incoming raw term's minimum charge, without yet overcharging the eventual operation. If previous successful raw count n satisfies n<=T and exact checked room proves T+1<=u64::MAX, then incoming n+1<2^64. Each raw term is <2^span times the anchor unit, span<=8128, so each positive or negative magnitude is strictly <2^(8128+64)=2^8192. Reanchoring preserves the inequality using the new common minimum and largest-term high. Actual charges must still be checked at every update, and a failed reservation/update must stop or poison the value before any future arithmetic can consume it.

This does not require copying donor's historic raw term count into the receiver: add_scaled first forms each full donor sign magnitude times u64 factor, and add_raw derives high from that full scaled integer. Donor carry bits therefore become part of the incoming term span. add_product_of nets b, uses each nonzero net limb as a scale for a's two magnitudes; every resulting add_raw needs the same invariant. Donor/value validity and loss state must be checked even before zero-factor/empty shortcuts if the receipt claims the complete dependency history. Clones inherit the current magnitudes, cumulative work and poison, so the above bound remains conservative; clear/reset retain lifetime work/loss.

Partial writes are the critical exception: failure in add_raw can precede `used` update. Such a sum is unusable. reset clears both full arrays but must retain the loss evidence; ordinary clear only clears the used prefix. Either poison denies all reuse/observation until a full reset, or every such exit must reset fully before any value reuse. A future invariant must explicitly include that interrupted insertion, not simply count successful final charges. New clean objects do not erase a containing attempt's prior loss.
