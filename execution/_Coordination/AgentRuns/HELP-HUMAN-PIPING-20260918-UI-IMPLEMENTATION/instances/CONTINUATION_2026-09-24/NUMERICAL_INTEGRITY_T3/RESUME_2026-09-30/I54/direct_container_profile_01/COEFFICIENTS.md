Let `s(T)=size_of::<T>()`, `a(T)=align_of::<T>()`, `up(x,a)` be checked alignment rounding, `c` observed capacity, `l` observed length, and `h` a source-proved *high-water population*, not necessarily the returned length. Every addition/multiplication/rounding must be checked and every requested `Layout` valid; a failed calculation denies the proposed admission. The heap header for a Vec/String/map/Arc handle already lives in its containing allocation's stride or in stack storage; do not add it as a second heap allocation. Nested child backings are separate. Primitive strides here are u8/bool=1, u16=2, u32=4, u64/f64/usize/thin pointer=8, `[f64;3]`=24. Composite Rust layouts remain actual build facts.

For s>0 define:

```
m(s) = 8 if s == 1 else (4 if s <= 1024 else 1)
r = checked_add(l, additional)
Grow(s,c,l,additional) = c                      if r <= c
                       max(2*c, r, m(s))        otherwise
Exact(c,l,additional) = max(c, r)
PushCap(s,0) = 0
PushCap(s,h) = m(s) * 2^ceil(log2(max(1,h/m(s))))  # integer ceiling; h>0
AppendUpper(s,c0,h) = max(c0,m(s),2*h)             # h>0; see conditions
```

Use an integer doubling loop for PushCap; the displayed real-log notation is explanatory. AppendUpper applies to ordinary append/reserve-for-the-actual-appended-count, with no unrelated oversized reserve, no fabricated iterator hint, and h covering every reached prefix. For h=0 preserve c0, including deliberately reserved storage. Deletions/clear/dedup do not make a prior high-water allocation smaller. ZST Vec capacity can be usize::MAX but requested backing is zero; do not multiply before checking s=0.

Every selected cached .17.1 source equals its cached archive member, with SHA-256 recorded. This is a concrete source-correspondence inference, stronger than version-name matching. The checksum-kind field in embedded LLVM bitcode was not decoded: no new decoder/compiler/install was introduced, and this packet does not silently promote adjacent MD5 strings into a signed build attestation. Independent review must decide reliance on this correspondence. The formulas themselves follow the identified .17.1 source exactly.

`HB` means that checked cached .17.1 source. For HashMap<K,V> the stored element is T=(K,V); HashSet<K> uses T=(K,()). Use the **tuple's** size/alignment, including any padding. Standard RandomState has no per-entry allocation; custom hashers/allocators are outside this binding. The installed NEON Group holds uint8x8_t, so G=8 (HB/control/group/neon.rs:14–21). HB alloc.rs's std/nightly path calls Global.allocate; STD/alloc/alloc.rs:205–213 returns the requested slice length exactly, so HB/raw.rs:1577–1599's optional utilization of an oversized allocator slice does not enlarge buckets for this Global binding. Physical malloc usable size is not that slice length.

```
Buckets(s,0) = 0                         # heap-empty singleton
Buckets(s,k), 0<k<15:
    t = max(k, 7 if s<=1 else 3)         # Group width 8
    result = 4 if t<4 else (8 if t<8 else 16)
Buckets(s,k), k>=15 = next_power_of_two(floor(8*k/7))
Full(b) = 0 if b==0 else (b-1 if b<=8 else 7*b/8)
HashReq(s,a,0) = 0
HashReq(s,a,b) = up(s*b,max(a,8)) + b + 8  # no final pad_to_align here
```

The last `b+8` is the actual control allocation, including the duplicated group; it is not allocator overhead. Reject overflow and the source's `size <= isize::MAX-(alignment-1)` violation. Sources: HB/raw.rs:104–162,182–235,1619–1641. The request need not be a multiple of its alignment. Conditional examples at slot `(s,a)=(24,8)`: b=4/8/16 request **108/208/408 bytes**, respectively, before String child backing. Treat these as evaluated formulas for that layout, not a new observation of arbitrary Rust tuple size.

The direct numeric-parser bound follows these concrete source steps; it does not rely on an observed fixture or on a presumed fast parser path:

1. `Number` has only finite f64/i64/u64 alternatives under the verified feature set. ZMIJ's spelling uses ≤24 bytes total and ≤3 exponent digits; using ±999 is deliberately looser than binary64's actual scientific range. For the truncated parser branch, `scientific_exponent` shifts by at most24 integer/leading-fraction digits, then bhcomp subtracts a count≤24. For the concise branch, parse_decimal has already adjusted by ≤24 fraction digits and bhcomp receives ≤20 itoa digits. Both are covered by scaled decimal exponent **[-1047,1023]** (SJ lexical/exponent.rs:24–49; parse.rs:12–39,49–82; bhcomp.rs:193–221). The number lexer scratch reconstructs the mantissa prefix only (de.rs:677–710,742–755,816–831); the synthetic leading zeroes in parse_decimal_overflow replace already consumed fractional zeroes. Its high-water length therefore stays≤24 for this source-generated text.
2. Bigint::default reserves20 limbs (lexical/bignum.rs:9–20). The target build.rs chooses `fast_arithmetic="64"`, so each limb is8 bytes. A ≤24-digit mantissa needs≤80 bits, at most2 limbs. The second Bigint in small_atof is the exact halfway comparator: mantissa<2^54, binary exponent in **[-1075,970]**, directly from f64 masks/bias/denormal exponent and bh_extended (num.rs:270–285,370–379; bhcomp.rs:78–94,135–179).
3. The largest pow5 exponent is1047. At entry to small::imul_pow5 the operand has at most2 limbs. The largest indexed cached power is `POW5_11` with38 limbs, so `2+38<2*KARATSUBA_CUTOFF=64`. Thus **only scalar in-place pow5 multiplication is reached** for this generated family (math.rs:390–432; large_powers64.rs:53; cutoff math.rs:663). No long_mul/karatsuba temporary Vec family is charged here. Arbitrary original numeric text is a different parser profile, not an extra prerequisite smuggled into this direct route.
4. Using 5^n<2^(3n), the theoretical comparator has ≤3195 bits after pow5, at most50 limbs. Starting at capacity20, scalar push growth reaches at most80. Its subsequent positive binary shift is at most970+1047=2017 bits: at most5212 bits total, **82 limbs**, causing at most one reserve from80 to160. The real mantissa's possible opposite shift is≤1074, so ≤1154 bits or19 limbs, which fits its original20 capacity. The positive-decimal branch has≤80+4*1023=4172 bits,66 limbs, and fits capacity80 after its scalar growth. These are conservative independent bounds; no favorable exponent correlation is assumed.
5. `ishl_bits` can push one carry, then `ishl_limbs` reserves the required limb prefix and splices `repeat(0).take(n)` (math.rs:460–525). Its size_hint is exact; STD/alloc/vec/splice.rs:55–94,123–134 confirms that the pre-reserved shift makes no extra heap buffer: the leftover collect is empty. At the worst negative branch, real capacity20 survives while theory old80 and new160 coexist: **8*(20+80+160)=2080 bytes**. After growth, requested resident Bigint backing≤8*(20+160)=1440. Positive-branch growth is smaller. Return/move does not clone either Bigint; both drop before the next JSON number. `DIRECT_PARSE_NUMERIC_CHECKS.json` independently checks these integer bounds.
