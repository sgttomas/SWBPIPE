## Concrete input counterexample and justified finite parameters

For either route, a call to the existing poll command can supply a valid existing `jobId` and an extra payload member `unused` containing an arbitrarily long string. Tauri first deserializes the complete JSON Value (`ipc/protocol.rs:291` or `:521–528`); argument lookup selects only `jobId` (`ipc/command.rs:84–103`). No closed-payload or length check removes the extra member before its allocation. Thus a bound based only on the generated ID does not bound this accepted request's Q, even with one callback. This is a source-derived counterexample to that proposed bound, not an executed test or a claim all such inputs are supported by I30.

The actual first-party service is narrower: `previewService.ts:209–212` submits only `{jobId}`. Generated IDs are `backend-solve-job-` plus a u64 decimal (`lib.rs:1646–1655`): **at most 38 ASCII bytes**, hence the canonical compact JSON payload is at most **50 bytes**. This bounds logical payload length only, not String/Value capacities, transport headers, parser scratch or error strings. The wait loop has one outstanding poll per retrieval (`solveJobAudit.ts:150–156`); it proves neither a finite number of retrievals nor a full native-lifetime count after response transfer. Cancellation and detachment must remain distinct.

## Exact missing term and smallest prospective decision

Write I38's equation unchanged, partitioning allocations once:

`E_native(k,t) = R(k,t) + S(k,t) + Q(k,t) + sum_i L_i(k,t) + sum_j D_j(k,t)`.

R retains completed job Value/lease and applicable registry backing. S includes the attributable shared backing/metadata baseline, including custom-task-map capacity where in scope. Q includes raw/parsed inputs, arguments, command/URL/header copies and resolver/transport contexts through actual Drop, including prefix and post-body tails. L/D retain the I30 wrapper ownership cuts. The exact missing census is the supremum of simultaneously retained included native contexts and reply owners across both routes, plus their complete input-dependent capacities. K only bounds admitted large owners. Neither `sum D_j ≤ K*D` nor `Q ≤ H_body*Q_one` follows.

**The smallest no-wire-change next decision is an explicit P4–P5 supported caller profile, not a global IPC redesign.** ROOT must choose whether the qualified claim covers canonical first-party retrievals only or also arbitrary accepted raw poll payloads. The former can use the 38/50-byte logical input derivation; the latter needs a separate complete input allowance and cannot inherit those numbers. Ordinary/raw calls may retain their current behavior outside the claim; rejecting or truncating them is a different availability/contract decision.

That profile must also state a concrete lifetime census basis: for a *closed finite qualification episode*, let A be its exhaustively accounted native callback admissions from both routes (including applicable fallback, preflight and abandoned attempts), with exact input shapes and initial shared capacities. Then `N=|A|` gives `H ≤ N`; retained contexts are bounded by the sum of all admitted contexts' per-phase capacities, and custom task-map population by its initial population plus custom admissions. This derivation is independent of nesting and early cleanup, and selects no arbitrary numeric ceiling. **A JS-call count is not A; current source supplies no such exhaustive episode/profile enforcement or native-admission mapping.** A paper manifest alone is not a public continuous-use guarantee. Converting this into a supported finite-episode restriction or excluding otherwise expected continuous/overlapping usage requires the owning availability decision. I53 selects neither.

For continuous first-party operation, the still-required product/profile correction is a proved lifetime boundary for old contexts before their census slot is reused, covering callback prefixes, both outbound native callouts and abandoned generations. A guard acquired inside the poll command is too late to cover earlier Tauri/Wry copies. No local result-wrapper edit alone discharges this term. The concrete dependency cleanup defect, *if its early-exit paths are in the selected profile*, is Wry's missing identity-checked task-key cleanup when its responder is dropped or its response fails; any prospective correction must preserve UUID identity, stop semantics and backing-capacity accounting. Such cleanup addresses that retained-entry path only, not the nesting/input proof. No patch, semaphore, queue, new endpoint or admission policy is selected here.
