## Why the reference-profile claim is coherent

ReferenceKernelProfile, ReferenceHProfile and ReferenceVRProfile would contain
fixed reviewed premises, private fields and named basis constructors. Returning
a proof_basis identifies those premises. It cannot establish that current
machine code uses their layouts, allocation sites or library implementation.

The current evidence combines separately scoped witnesses, including debug,
feature-enabled release and different diagnostic artifacts. The proposal says
so explicitly rather than inventing one previously qualified production build.
Conditional source arithmetic over that fact set is meaningful without claiming
the conjunction has been transferred to a particular executable.

W1SizeFacts::of_this_build and VR Sizes::of_this_build evaluate only their
listed public size_of expressions (H counts.rs:369 onward; VR scale.rs:231
onward). They do not inspect private node requests, compiler/link provenance,
allocation paths, library source, or source/profile compatibility.
Therefore the proposal correctly prevents silently mixing current public sizes
with historical private facts under the unchanged historical identity.

Implementation must keep the named reference fact bundle coherent, including
compatibility of the kernel profile and the H/VR composition using it. If
multiple basis IDs are exposed, a mismatched combination must be rejected or
explicitly represented as a separately justified basis. This follows from the
proposal's immutable named-premise contract; it is not a new current-build
verification mechanism. Current public-type checks remain separate.

Missing descriptors/proof cells must remain explicit errors. A reference
profile is not a license to supply zero, a caller-chosen overhead, or a
partial admission subtotal. Renaming Verified to Reference does not by itself
repair an incomplete envelope; all previously required mathematical/source
components and corrections still apply.

## Qualification and metadata are correctly separated

The proposed external record links the reference IDs to exact source/archive,
locks, build command/compiler/std/target/features/profile, allocator/request-site
correspondence, binary hash and actual launch/input/count identities.
These are the previously required artifact-specific reliance facts.

The inspected H runner metadata function (:800–826) accepts source IDs from
its caller, labels build_profile='release', queries a toolchain and hashes the
provided binary. Those operations do **not** prove that the queried compiler,
reported source or release setting built that binary. VR's runner (:269–277)
reuses that metadata. The proposal identifies this gap and does not rename
the existing function an attestation.

Unknown/mismatched artifacts can therefore calculate conditional reference
numbers and retain ordinary CLI behavior, while receiving no external
qualified-bound/reliance or measured-run authorization. The qualified use still
requires exact build/input/launch review before relying on admission values.
This is procedural qualification on the accepted workflow, not a claim of
automatic in-process enforcement.

Documentation at the estimator and entry adapters must retain that meaning.
A profile ID is not evidence, and fields named estimate_max or legacy admission
estimates do not become proven bounds for an arbitrary executable just because
a reference constructor returned numbers. No current artifact is qualified by
this design.

## Ordinary CLI, CI and protected checks

Actual sources support the proposal's preservation requirement:

- H Cargo.toml sets test=false for k6_observe. k6b_bin.rs launches the ordinary
  debug subprocess via CARGO_BIN_EXE, requires successful numerical W1/parity/
  prefix/row behavior, numeric estimates, and the named half-cap refusal.
  Its opening scope explicitly asserts no time or memory bound. A library
  cfg(test) carve-out would not qualify that independently built subprocess.
- H counts/main retain ordinary counts-file/computed paths and the half-cap
  predicate. VR keeps counts-only and the ordinary half-cap branch. A new
  blanket unknown-build error would change those protected behaviors.
- H k6b_w1.rs checks hand arithmetic and all33 committed count identities.
  VR tests/scale.rs checks storage counts for193 factored CI cases and estimate
  ordering. These are real assertions to preserve, not tests to skip because
  a host lacks final production qualification.
- VR feature_guard.rs enforces no enabled mutation feature in product manifests,
  no-feature CI commands, and no execution-tree paths in VR Rust sources.
  The Ubuntu numerical workflow uses Rust1.97.1 and excludes execution data;
  numerical_ci retains locked fetch followed by actual offline cargo tests.

Embedding only the small maintained reference facts and non-path basis IDs
avoids an execution-tree dependency. External qualification may reference
governed evidence, but source/tests must not load that evidence tree or add
feature/bypass tokens to make CI pass. Even provenance comments/strings in
guarded Rust files must respect the existing no-execution-path check.

Reference-arithmetic tests on Linux prove those equations under the stated
premises; they do not prove Linux private requests equal M5 witness requests.
This is an accurate claim boundary, not a permitted reduction of testing.
Implementation review must preserve all33/193 identities and the existing
semantic/allocator/current-public-type/overflow/missing-proof/mutant coverage,
including the ordinary debug subprocesses. Do not reduce193 cases to the24
numeric caller-table roster or replace an actual executable-bound assertion
with a weaker reference-only assertion.

The proposal commits to these constraints; this source-only review does not
prove future implementation can satisfy every assertion. If corrected
integration reveals a conflict with a protected criterion, return that actual
conflict for its owning disposition. No exception, ignored test, platform skip,
changed tolerance or invented bound is pre-authorized here.

## Remaining implementation and reliance limits

Before reliance, the concrete adapters and documentation must make reference
basis selection, coherent composition, missing-proof behavior and external
qualification unmistakable. An error name such as BuildBasisMismatch must

arithmetic, immutable ID-to-fact mapping, final ordinary-production correspondence,
sidecar identity binding, exact counts/launch mapping, prior envelope

described as enforcing one.
