## Why a new record version is simpler here

The current `schemas/analysis_run.schema.json` calls itself an exact-version dispatcher and routes 0.2.0 solely to `analysis_run.v0.2.schema.json`. That strict schema's `SemanticContract` definition fixes ID `openpipestress_result_semantics_v0_2` and SHA-256 `4d6886d19e304db897e5e9f8f0054cbee91ba7795868f9698e2bbe070bde94da`; both per-row interpretation and run reproducibility use that definition. Python `core/analysis_runs/compatibility.py` and desktop `services/analysisRunCompatibility.ts` likewise fix the old map, builder name, provenance and `strict_analysis_run_v0_2` record-contract identity. Therefore 0.2 is presently a shape **and a pinned interpretation contract**, not a documented generic container for arbitrary semantic tables.

The proposed precision schema preserves the structural shape but replaces those semantic constants. Its `oneOf` dispatch can be made mathematically disjoint and does preserve the old schema file. That is not inherently ambiguous or dishonest if every reader implements the new discriminator. It is nevertheless a prospective expansion of what outer 0.2 means: an old exact-0.2 reader rejects the new object, while version-only checksum readers currently accept hashes without establishing semantics. Each later `/reactions-1`, `/pressure-1` or `/stress-1` would invite another schema suffix or further branches. A normal analysis 0.3 successor makes the changed interpretation explicit at the existing family boundary and keeps the historical 0.2 contract intact.

Do not infer that every referenced semantic-map update forever needs another analysis minor version. Define **new** analysis 0.3 deliberately as a carrier with a typed, exact registered semantic ID/hash contract: syntax/shape version and interpretation identity have distinct jobs. The active implementation recognizes only the exact precision-1 mapping initially; future reserved semantic IDs are unsupported until their mappings and whole consumer path are qualified. One 0.3 schema plus a shared exact semantic registry is preferable to a separate `analysis_run.v0.3.<semantic>.schema.json` for every method. If JSON Schema enumerates active pairs, keep its active pair set generated/bound to the same registry; runtime checking is still required for source/row/case/hash correspondence. No unconstrained string or `oneOf` branch means an unknown interpretation is supported.

D67's explicit 0.2 adoption applied to its own immutable analysis/stress-neutral record families. It did not promote model documents, raw mechanics or operations, and it preserved old family meanings. The proposed 0.3 successors follow that distinction; they do not retrospectively rewrite D67, rehash legacy records, or require the model version to match the result version.

## Stress-neutral decision

The current stress-neutral 0.2 schema pins profile `ops.stress_neutral.v2` / version 0.2.0. More decisively, `core/handoff/stress_neutral/package_v0_2.py` fixes `SEMANTIC_CONTRACT_REF` to `fixtures/results/semantic_contract_v0_2.json`, stamps that reference into export and unit-disclosure basis, and requires it in the validator. Its physical dimension/witness rules are therefore more than a generic unchanged CSV carrier. Using that builder for precision-1 and merely retaining an old reference would falsely identify the interpretation basis. Broadening the old validator would change the historical profile contract even if unchanged numeric cells still round-trip.

Select `stress_neutral_export.v0.3.schema.json`, profile `ops.stress_neutral.v3` / version 0.3.0, and a version-qualified builder/validator. Reuse unchanged CSV columns, checksum algorithms and member projections where they remain correct; a version increment is not a reason to redesign them. Bind the exact new semantic ID/hash plus the corresponding analysis 0.3 record and raw/derivative source identity. Preserve received row values, units, source annotations and original-versus-received checksum distinctions. New source producer/quality/formulation information must remain recoverable through the hash-bound source/analysis linkage, and any displayed/exported assessment must explicitly reference that evidence. If it is not embedded, disclose that the external source is required to verify qualification; unit-preservation witnesses alone never establish numerical eligibility.

Historical exports must remain byte-stable/verifiable through the historical functions. The new current exporter cannot relabel raw precision rows with the old semantic table simply because their current kinds happen to overlap. Conversely, an explicit historical re-export is not a new solver run and must not invent precision/integrity evidence.

## Reader, builder and qualification separation

1. **Historical reader:** select the original analysis/export outer version, validate its exact historical schema and semantic basis, then verify original record/member/row checksums using the original projection/canonicalization. Preserve raw source bytes and missing metadata. Report `match`, `mismatch`, `unverifiable` and `unsupported interpretation` distinctly. A matching checksum proves the identity of received bytes; it does not authenticate the claimed solver, recover missing precision or make Current.
2. **Current builder:** validate the new raw tuple and mandatory producer/quality/formulation fields before dispatch; build analysis 0.3 only from that admitted source. Preserve an actual blocked or `not_assessed` source without promoting its quality. No catch-and-fallback to `build_analysis_run_v0_2`, no caller switch that manufactures missing new headers, and no source-version-only test that mistakes old synthetic raw 0.2 for the new producer.
3. **Compatibility construction:** retain historical fixture reproduction and explicit historical record revisions as historical operations, with original source meaning and fresh record identity only where appropriate. Do not delete old fixtures or silently change their raw version to 0.1 to make current tests pass. Keep their original expected bytes and test their original builder contract in a clearly historical test. If the legacy builder remains publicly callable, it must be a named historical adapter, excluded from the Current composition path and unable to take a new qualified source back through old semantics.
4. **New analysis validator:** require agreement among run-level semantic ID/hash, every row interpretation ID/hash/signature, supplied source producer semantic ID, registry mapping, source row identity/hash, manifest/source model and producer/build bindings. Check actual source equality/row accounting, not merely same run ID. A forged precision header plus recomputed checksum is still unauthenticated without the existing origin/build evidence.
5. **Standing:** freshness against model/input hashes, source authenticity, supported interpretation, mechanics status, numerical eligibility and physical formulation scope remain distinct. Old records may be authentic and input-matching but need recompute. New records may be authentic and schema-valid yet `not_assessed`, `unresolved`, failed or physically unsupported. None qualifies as integrity-checked Current merely through outer 0.3.

The existing `verify_analysis_run_record` computes a record projection/hash and currently does not validate semantic ID/hash or raw producer. Keep that verification meaning truthful. Add/version an interpretation/schema validation stage; do not rename a checksum match as whole-contract verification. A generic safe shared projection helper may be reused when its exact version-qualified payload exclusions are unchanged, but a historical verifier must not silently switch to a new normalization.
