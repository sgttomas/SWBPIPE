## The task in one paragraph

Gap G-31; design system §6.6: "Selection is a halo: a 2 px `canvas.selection` outline around the element's silhouette and its glyphs, drawn against the ground, with the node label plate taking a `canvas.selection` edge. Hover is a thinner 1 px `canvas.hover` halo. … Multiple selection halos every selected element." §6.7: halos draw over colour unchanged. Today a selected element is **recoloured**: `applyInstancedSelection` in `viewportResource.ts` overwrites its instance colour with the selected colour (and non-instanced objects get their material colour set), which destroys the element's own colour. You replace that recolour with a halo outside the silhouette, and add the hover halo. This is a **named semantic change**.

## What to build

1. **Selection halo.** 2 CSS px (so `2 × pixel ratio` device px) in `canvas.selection`, exact token value (unlit, not tone-mapped, sRGB as `Color.setHex` gives), **outside** the silhouette of every selected element of every kind the product draws (pipes in both geometry modes, the four placeholder kinds, nodes, supports; load arrows if they are selectable today: check). The element keeps its own colour and its edge line: remove the recolour (`applyInstancedSelection`'s selected branch, and the non-instanced material recolour), keeping base-colour repaint intact. Multiple selection halos every selected element. A hidden element has no halo. Theme change repaints the halo in place (nothing created or disposed, one invalidation). The halo is display-only: **no halo object may become a pick input**, and picking stays analytic over the typed model index (assert it in a test: no new object is registered with the picking primitives; picking tests byte-identical and green).
2. **Hover halo.** 1 CSS px in `canvas.hover` on the hovered element; **a selected element shows no hover halo** (P1 §4.4). Hover state stays where it is (`hoveredEntityKey`); pass it to the resource by a new setter beside `setSelectionPresentation`. Hover must not cause a React re-render storm or a layer rebuild: one small update and one invalidation per change of hovered element, nothing when the hovered element is unchanged.
3. **The working form changes no renderer construction.** Options you must weigh, build one of as the working form, and cost the others:
   - **(a) depth-tested shell**: the element's geometry drawn again, expanded 2 px in screen space, behind the element. Cheapest; hidden wherever nearer geometry covers it. In the centreline mode node spheres (radius 0.095) swallow pipes (radius 0.052, median length 0.1 in the fixtures), so a pipe's halo would mostly be hidden from the user.
   - **(b) drawn over nearer geometry, masked by depth**, no stencil: last in the frame, a mask pass draws the haloed elements with colour writes off and depth written at the near plane (`depthTest` off), then the expanded shell draws with depth test on at a depth just behind the mask, so it shows everywhere except inside the element's own outline. It spoils depth only in pixels drawn after everything else (check what draws later: the first profile's cue is `depthTest: false`; the gizmo is a separate scissored render: verify whether it clears depth). The manager's lean, for you to verify or overturn with reasons.
   - **(c) the same with a stencil buffer** (`new THREE.WebGLRenderer({ antialias: true, stencil: true })`): the owner has now allowed a renderer-construction change if the picking tests are unchanged and D-72's limits hold, and ROOT decides it on this slice's numbers. **Build (c) only as a patch file** `{LANE}/probes/C2/stencil_candidate.patch` (made with `git diff`, read-only) **and a build copy outside the repository**, then restore the tree to the working form; nothing of (c) is in the tree you return. Say plainly which of (b) and (c) you judge right and why (memory, draw count, fragility, what each does to MSAA edges, what a later slice such as C3's dimming would meet).
   - How the shell is expanded is yours: screen-space extrusion along a projected direction, in one draw, is preferred over multi-offset redraws, because the form must hold with 10,000 selected. For a prism, extruding rim vertices along the projected radial direction (and end vertices along the axis) avoids the cracks a hard-edged normal extrusion leaves; spheres and the torus extrude along their normals; boxes and cones need a rule of their own. Haloed instances should be drawn from dedicated halo meshes that share the base geometries and carry only the selected instances' matrices (capacity grown geometrically, never per frame), so an unselected scene pays nothing. Every halo object enters the ownership ledger and is disposed with its layer or resource; if a layer is rebuilt the halo follows (`replaceLayer`). State the ledger counts exactly.
