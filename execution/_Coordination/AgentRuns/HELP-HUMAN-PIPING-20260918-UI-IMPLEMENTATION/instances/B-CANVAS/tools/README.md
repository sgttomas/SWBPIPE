# `orbit_probe.mjs`: the B-CANVAS lane's guidance probe for per-frame cost

Written by T1-ORBIT-PROBE and finished by T1-ORBIT-PROBE-2 (TASK, Type 2; both Claude Fable 5.1) for the canvas lane manager B-CANVAS, 2026-09-19. Path placeholders are those of the sealed briefs in `../briefs/`: `{WORKING_ROOT}` is `projects/chirality-piping`, `{DESKTOP}` is `{WORKING_ROOT}/apps/desktop`, `{RUN}` is the run folder two levels above this lane, `{LANE}` is `{RUN}/instances/B-CANVAS`.

**What this is.** A plain Node ES module, no new dependency, that measures what a frame costs while the model is orbited with real pointer input, so that the lane can see whether a slice that adds work per frame (an edge line, a hover halo, a label budget) is worth keeping. **It guides the lane and decides nothing about D-72.** The qualification runs are ROOT's, by a separate runner and a separate instrument (`{DESKTOP}/e2e/ui-foundation/**`). This tool imports nothing from that instrument and carries none of its tolerances, limits or oracles; the two thresholds it reports fractions against (16.7 ms and 33.3 ms) are reporting bins, not a verdict. It reads the instrument's two fixture files as data. It never builds and it changes no product file. Its evidence on this host is under `{LANE}/probes/T1/` with a `SUMMARY.md`.

## Interface

```
node orbit_probe.mjs run --dist <dir> --pipes <1000|10000> --mode <schematic|actual-od>
     --labels <on|off> --theme <light|dark> --dpr <1|2> --window <WxH> --pacing <vsync|uncapped>
     --variants "<name>[@<distDir>]=<query>;<name>[@<distDir>]=<query>" --pairs <n>
     [--warmup-ms 2000] [--measure-ms 10000] [--port 5185] --out <file.json>
node orbit_probe.mjs resources --dist <dir> --pipes <1000|10000> [--query <query>] [--dpr 2]
     [--window <WxH>] [--port 5185] --out <file.json>
node orbit_probe.mjs summarize <file.json> [<file.json> ...]
node orbit_probe.mjs self-test --dist <dir> [--port 5185]
```

- **Every browser and every server on this host goes through the run's lock script:** `sh {RUN}/tools/with_e2e_lock.sh node {LANE}/tools/orbit_probe.mjs ...`, one series per hold. Port 5185 by default; the tool refuses 5174, 5175, 5176, 5177, 5183, 5184 and 5186, which belong to other configurations on this host.
- `--dist` names a **built** `dist` directory (it must hold `index.html`). The tool serves it itself from a small static server on 127.0.0.1 (correct content types including `application/wasm`, single-page fallback for extension-less paths, `Cache-Control: no-store`), so the measured build can be a copy kept outside `{DESKTOP}/dist` and a later build cannot disturb a run.
- A **variant** is a name and a URL query string appended to the page's address; the query may be empty. The tool knows nothing about what a query means; the product under test reads it. `--variants "off=;band=canvasProbe=edge-band" --pairs 3` runs off, band, off, band, off, band. Every run is a fresh browser and a fresh page.
- **A variant may name its own build** (addition of 2026-09-19): `<name>@<distDir>=<query>`. Then `--dist` is needed only by variants that name none. Each run is served by a server rooted at that run's build alone, so no run can be served another variant's files; the output records each variant's build identity, and `summarize` prints each identity once and says whether the variants share it. A variant with no build, or a directory without `index.html`, is refused before any browser starts. A directory path containing `=` or `;` is not supported.
- `--pacing uncapped` launches the browser with `--disable-frame-rate-limit --disable-gpu-vsync`, so that the frame interval reflects what a frame costs rather than the display's period. The output says whether that took effect (see below).
- Browser: `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` when set and present, otherwise Playwright's `channel: "chrome"`, otherwise the bundled Chromium; always headless. The browser's version string and the WebGL renderer string are recorded; no executable path is.

## Output files

One pretty-printed JSON file per series, `tool: "b-canvas-orbit-probe"`, `formatVersion: 1`. It holds the full argument list with every path reduced to a placeholder (`{WORKING_ROOT}/...`, `{REPO_ROOT}/...`, `{OUTSIDE_REPOSITORY}/<basename>`, `{DIST}`), the **build identity** of every variant (SHA-256 of `dist/index.html`, and the names and sizes of the files under `dist/assets`), the fixture's identity (file, SHA-256, project id, counts), host identity (platform, CPU model and count, Node and Playwright versions; never a path), the host's load averages before and after every run, and per run everything listed under "What it measures". The only per-frame list kept is the list of intervals over 33.3 ms (capped at 1,500). Every string written is passed through a scrubber that replaces the working root, the repository root, the home and temporary directories and anything that still begins like a home, temporary or system-private directory of a Unix or Windows host; the self-test checks that no machine path survives.

## How a run works

1. **Open the fixture by the product's own load path.** The product opens its start-up model by importing one module (`invented_preview_model-*.js`, or the JSON it falls back to). The tool intercepts exactly that one request and answers it with a module whose default export is the fixture (`{DESKTOP}/e2e/ui-foundation/fixtures/ui-foundation-<pipes>.model.json`, read as data). Every other request is served from the build unchanged. The page is then "model ready" when the diagnostics surface reports the fixture's project id with assignment status `committed` and at least one main-render submission. This is the same route the instrument uses; the tool copies nothing from it.
2. **Set the state through the product's own controls:** the "Appearance theme" select; the `viewport-geometry-schematic` / `viewport-geometry-actual-od` buttons (waited on until the diagnostics report the mode, and for actual OD an available OD generation); the `toggle-viewport-labels` button by its `aria-pressed`; then `viewport-view-isometric` and `viewport-fit-model`.
3. **Wait until settled** (definition below), then **find a press point**. With labels on the product gives the hovered entity a label and the label takes the pointer, so a press at a fixed point after a hover may never start the orbit. The tool tries candidate points outside in (eight points on each of five rectangles inset from the canvas edge, then the centre), keeping only those from which the orbit path stays inside the page, rests the pointer on the candidate, waits until settled again, and takes the first point that `document.elementFromPoint` still resolves to the canvas itself.
4. **Install the frame recorder** in the page by an expression (not an init script, so the page carries nothing of the tool until this point): one function rescheduled with `requestAnimationFrame` every frame, writing each timestamp into a preallocated `Float64Array` of 400,000 entries; a frame allocates nothing. The tool's own Node process collects its garbage just before the orbit, so that the parsed fixture cannot cause a pause in mid-orbit. After 700 ms of idle recording it reads the diagnostics once ("before orbit").
5. **Orbit with real pointer input:** mouse down at the press point, then `mouse.move` every 4 ms on a timer in the tool's process, never awaited one by one (a slow frame cannot slow the pointer). The position is a function of elapsed time alone: a figure of eight, x = 0.28 × canvas width × sin(2πt / 5 s), y = 0.12 × canvas height × sin(2πt / 2.5 s), offsets from the press point, so every variant sweeps the same angles. This runs for the warm-up window, then the measurement window, then a 150 ms tail; the send-gap histogram is recorded. At the start and the end of the measurement window `Performance.getMetrics` is sampled over the DevTools protocol.
6. **Collect**, in the page: interval statistics over the measurement window only, the diagnostics at the end of the window; then mouse up, wait until settled again, and read the diagnostics once more ("after orbit"). The browser is closed and the server is closed before the next run.

## What it measures

1. **Frame intervals** between `requestAnimationFrame` timestamps taken in the page: count, mean, p50, p95, p99 and maximum (nearest-rank percentiles), the fractions over 16.7 ms and over 33.3 ms, the offsets and lengths of every interval over 33.3 ms, and under `vsync` the fraction of missed refreshes (an interval over 1.5 times the idle page's period). Timestamps come in steps of 0.1 ms, so under display pacing "over 16.7 ms" is mostly rounding of 16.67; read the mean, the p95 and the missed-refresh fraction together.
2. **Main-thread cost** from `Performance.getMetrics` deltas between the two samples: task, script, layout and style durations over the window, in total and per frame (frames by the mean interval), busy fraction, layout and style-recalculation counts, JS heap before and after.
3. **Product diagnostics** from `globalThis.__openPipeStressUiDiagnosticsV1.readCurrent()` (type in `{DESKTOP}/src/features/workspace/uiDiagnostics.ts`), read before the orbit, at the end of the window and after the orbit: renderer information (draw calls, triangles, lines, points, geometries, textures), the ownership ledger's `live`, `created` and `disposed` with its generation, the canvas's CSS size, drawing-buffer size and pixel ratio, the geometry mode and OD status, the label state and rendered count, the model's project id, generation and identity hash, and the camera and submission sequences. The run also records whether the orbit moved the camera and left the model generation and geometry unchanged.
4. **Console**: counts and the first twenty texts of console errors, warnings and page errors.
5. **Pacing**: before the product opens, a blank page of the same browser presents a moving square every frame for 400 ms and the interval p50 is recorded. Under the display's pacing that p50 is the refresh period; with the limit off it is far below it. `uncappedTookEffect` is true when it is under 4 ms. An idle product page cannot show this, because with nothing to present it is paced either way.

## Settling

"Settled", as the tool means it before and after an orbit, is read from the product's diagnostics surface and the DevTools Performance domain, polled every 100 ms: for 500 ms on end the product reports no pending animation frame of its own (`ownedPendingRafCount` = 0), its main-render submission sequence and camera sequence do not move, and the main thread's task time is under 20 % of wall time. The `resources` subcommand uses a second, stricter observation that needs no product change: page-side wrappers installed before any product script (`requestAnimationFrame` / `cancelAnimationFrame`, and the WebGL draw and clear calls) count pending callbacks, fired frames and draws over a one-second window, beside the product's own pending-frame count and submission sequence. It reports "settled" only when no frame is pending, none was requested or fired, and nothing was drawn or cleared. The same observation is repeated as a control while a real-pointer orbit is under way and must then report "not settled"; the evidence shows it does.

## `resources`

With nothing timed: open the fixture, light, schematic, labels on, Isometric, Fit; record the ledger and renderer information; then theme light → dark → light twice, geometry schematic → actual OD → schematic twice, labels toggled and restored twice, grid toggled and restored twice, recording after every step; report whether `live` is identical before and after and whether `created − disposed = live` at every step and whether each round trip returns to identical `live`; then the settle check 1.5 s after the last input, and the orbit control.

## `summarize`

Prints markdown: a Series table (arguments, canvas size, pacing calibration, whether uncapped took effect, build identity, browser, WebGL renderer), a Builds table with one row per variant and a sentence per series saying whether the variants share a build identity and a query (an A/A series), a Variants table (runs, p50 and p95 of the per-run p95 values, per-run p50, mean interval, fractions over each bin, main-thread ms per frame, draw calls, triangles, mean load, console errors), a Paired-differences table (each later variant minus the first, pair by pair, median and range, and as a share of the reference), and a Resources table. Medians and ranges; never a verdict.

## `self-test`

Checks the percentile, interval, path-scrubbing, variant-parsing and summary arithmetic on fixed arrays, checks that a variant without a build and a build directory without `index.html` are refused before any browser starts, then runs one 2.5 s series on the 1,000-pipe fixture with two copies of the given build under two names (each served from its own copy), validates the shape of the output (including that the orbit moved the camera and that no machine path is in the text) and the summary's rows. Exit 0 on pass.

## What it does not measure, and what to keep in mind

- **GPU cost under the main-thread limit.** On this host the orbit is main-thread-limited: at 10,000 pipes uncapped the main thread is busy for most of the wall time and the interval did not change with device pixel ratio 1 or 2, with a larger window, or with a GPU synchronisation call every frame (a trial observation, 1.95 to 2.01 ms in six cases). GPU work that stays under that limit is invisible to the tool. A slice whose cost is mostly on the GPU can read as free here and still cost on a slower GPU or a larger canvas.
- **Headless, on a shared host.** A headless browser has no compositor bound to a real display; `vsync` pacing is Chromium's own 60 Hz ticking. Load averages are recorded beside every run because other lanes and children share this machine; only browser and timed work is behind the lock.
- **Not the redesigned Model view.** Today's layout at 1440 × 900 gives a canvas of 794 × 560 CSS px (444,640 px²). The redesigned Model view will have a 1000 × 828 canvas (828,000 px²), which is not on this branch. `--window 1646x1168` gives a canvas of exactly 1000 × 828 CSS px in today's layout and is the lane's **conservative stand-in** for that area; it is clearly not the redesigned layout, and any control moved by a later shell slice changes it (re-measure it when the shell changes; the value here was measured at the lane head this README was written for).
- **Noise floor.** The A/A series under `{LANE}/probes/T1/` are the tool's noise floor on this host: with one build under two names, a paired difference within the ranges shown there is noise. See `SUMMARY.md` for the numbers per measure. A difference between two real variants that is smaller than that floor is not detected by three pairs; a larger one may be, and repeating the series says whether it holds.
- **The pointer is driven from the tool's own process.** When the host holds that process back, fewer moves reach the page and the page does less work per frame. Every run records `pointer.sendGapsOver8Ms` and a send-gap histogram; a run whose count is far above its siblings' (34 against 0 to 5 in one evidence run) should be read with suspicion. The tool records this and does not flag it.
- **Timestamps come in 0.1 ms steps**, so under display pacing p50 and p95 sit at 16.7 or 16.8 ms and "over 16.7 ms" is rounding; the missed-refresh fraction and the mean carry the information there.
- **Nothing about acceptance.** It does not run the instrument, does not read its oracles and does not compare against D-72's limits. It carries no usability, performance or conformance claim.
- **Nothing was needed from the product that it lacks.** The controls, test ids and the diagnostics surface named above were enough.
