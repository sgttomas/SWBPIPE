## Finding 1 — SQLite copy order and stale-sidecar resume in the store carry-forward

- **Severity:** minor. **Actionable before merge:** yes (a few lines; cheaper to fix now than after the path ships).
- **Location:** `{REPO_ROOT}/projects/chirality-piping/apps/desktop/src-tauri/src/lib.rs`, lines 592–618 (`carry_forward_legacy_project_store`), specifically the loop at 604–611 and the main-file copy at 613.
- **What is wrong.** Two related things.
  1. *Order.* The `-wal`/`-shm` sidecars are read at lines 604–611 and the main database only at 613. For a file-level hot copy of a WAL database the safe read order is main file first, then WAL: a WAL is replayed over whatever main file it is paired with, so pairing an **older** WAL with a **newer** main file writes stale page images over newer pages. The reverse pairing (newer WAL, older main) is what WAL recovery is designed for. The store is in WAL mode unconditionally — `apply_store_migrations` executes `PRAGMA journal_mode = WAL` (`lib.rs:843`) — and the legacy bundle can be running while the renamed one starts, so the legacy store can be checkpointed between line 611 and line 613.
  2. *Resume.* The guard `source.is_file() && !destination.exists()` at line 607 means that if a previous attempt died after the sidecars landed and before the rename at 618 (the failure path at 622–628 only runs for a returned `Err`, not for a killed process), the **next** run keeps the stale sidecars and copies a **fresh** main file. That is exactly case (1) with an arbitrarily long gap, and it is the "a WAL copied without its main file" case the brief names. The resulting store is then never re-copied, because `legacy_project_store_source` returns `None` once a main file exists (line 581).
- **Evidence.** `lib.rs:604–618`; `lib.rs:843` (`journal_mode = WAL`); `lib.rs:581` (one-shot guard). The doc comment at 593–595 claims only main-file atomicity, which is true, so the comment is not dishonest — but the ordering it describes as a safety property is the unsafe one for a concurrently-written source. The five tests at `lib.rs:4356–4437` cover new-present / new-absent / both-absent / sidecars-copied / self-sibling. None covers a resumed attempt or a source mutated between the sidecar copy and the main copy, so the tests do not cover what is at risk here.
- **Smallest correction.** Move `fs::copy(&legacy_store, &partial)` (line 613) above the sidecar loop, and in the loop replace `!destination.exists()` with an unconditional copy (a sidecar at the new location with no main store is never user data; the failure path already cleans up what the attempt created). A stronger fix, if you want the concurrent-writer case closed properly rather than narrowed, is to open the legacy store read-only with `rusqlite` and `VACUUM INTO` the new path, which takes a proper read lock and needs no sidecar handling at all.
- **Not at issue:** it never moves, deletes or overwrites (`legacy_project_store_source` returns `None` when a store is already present; the legacy store is only ever a `fs::copy` source; cleanup at 625–626 removes only paths this attempt created); it cannot block startup (`app_store_path` logs and continues, `lib.rs:558–560`); the sibling-directory derivation hard-codes no platform path and correctly refuses to treat the legacy directory as its own source. The intra-process race on the fixed `.carry-forward-partial` name is **not** realizable: every one of the seventeen `app_store_path` callers is a synchronous `#[tauri::command]`, which Tauri v2 runs on the main thread, and the two `async` commands (`save_report_package`, `save_local_result_json`) do not touch the store path.
