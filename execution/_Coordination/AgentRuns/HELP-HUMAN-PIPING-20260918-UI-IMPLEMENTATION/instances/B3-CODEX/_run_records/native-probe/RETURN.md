## Select Escape causal result

CSS.supports('selector(:open)') is true on this WebKit. Pointer-open at startup and at native minimum did NOT reproduce original failure: first Escape emits only DOM keyup and preserves inspector; second Escape from closed select closes inspector and restores opener focus. These failed reproductions are retained, not discarded.

Keyboard Space-open at minimum DOES reproduce: Space keyup sees select :open=true, then Escape keydown already sees :open=false and defaultPrevented=false at window capture and bubble. Inspector closes and focus moves to opener. Thus direct :open at Escape/defaultPrevented is insufficient. Earliest divergence is shell treating a popup-cancel Escape as inspector cancellation after host popup closure. Event-time host state loses the distinction, but prior observed :open at Space keyup establishes real open state. This supports evaluating a narrowly scoped observed-popup lifecycle tracker (record actual :open on select opening-related events; clear on committed change, focus exit, pointer transitions and consumed cancellation) rather than blanket select suppression. That is an option requiring its own exact lifecycle validation, not a tested repair. Pointer/keyboard opening differ; source alone cannot explain original pointer failure. No claim that all pointer openings are safe.
