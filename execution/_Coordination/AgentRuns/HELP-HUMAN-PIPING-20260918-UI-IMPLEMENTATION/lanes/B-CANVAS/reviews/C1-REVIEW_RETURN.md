## Findings

**F1 — minor; actionable before the next part, as a decision rather than a code change.**
File: `{DESKTOP}/src/features/viewport/viewportPalette.ts:139` (`deformedShape: "canvas.vector"`), with the reasoning at lines 121–130 and in `{RUN}/instances/B-CANVAS/slices/C1_PART_A.md` §6.4.
What is wrong: the solid deformed overlay is bound to a token the design gives to another thing on the same canvas, and the design's own answer for this object was never weighed. Design system §6.8 says the deformed shape "draws solid with the result colour or the pipe neutral", and gives `canvas.deformGhost` only to the dashed undeformed outline; §2.8 gives `canvas.vector` to load vectors. The record weighs `canvas.deformGhost` against `canvas.vector` on contrast and never considers §6.8's "pipe neutral".
Evidence: §2.7 states that "When result colour is on the tube, and while a proposal ghost is drawn in the canvas, vectors draw in `canvas.vector` only", and §6.7 draws result colour for a Current run. The deformed overlay is built only when `deformation.state === "available"`, i.e. when there is a result. So in the state C5 and result colour will produce, the deformed tubes and every load vector would be the same colour — a collision the contrast measurement cannot see. (`canvas.vector` is also byte-identical to `canvas.edge` in both themes: `#42484f` light, `#c7cbd0` dark.)
Smallest correction: leave the code as it is for this candidate and return the question to ROOT and the design owner as a one-line design item — which token a *solid* deformed shape takes when it must be told apart both from `canvas.pipe` (the undeformed tube, drawn at the same time) and from `canvas.vector` — rather than settling it inside the lane. If a code change is preferred now, the only change is the one role string.

**F2 — minor; actionable before the next part, which is built inside this material.**
File: `{DESKTOP}/src/features/viewport/viewportFigureMaterial.ts:79`.
What is wrong: `Object.defineProperty(material, "color", { value: tint, enumerable: true, writable: false })` leaves `configurable` at its default `false` and defines the property on the instance only, so `color` is both unassignable and unclonable, while the marker that identifies the material survives cloning.
Evidence: in three 0.181.2, `Material.prototype.clone()` is `new this.constructor().copy( this )`; `this.constructor` here is `THREE.ShaderMaterial`. `ShaderMaterial.copy` copies shaders, uniforms (deep, so the clone does get its own `tint`), defines and extensions, and `Material.copy` at `node_modules/three/src/materials/Material.js:975` does `this.userData = JSON.parse( JSON.stringify( source.userData ) )`. So a clone keeps `userData.viewportFigureMaterial === true` — `isFigureMaterial(clone)` returns `true` — but has no `color` own property. `paintObjectForTheme` in `viewportResource.ts` guards with `if (!("color" in material) || !(material.color instanceof THREE.Color)) continue;`, so a cloned figure material would silently never repaint with the theme rather than failing loudly; and `material.color = …` throws `TypeError` in a module's strict mode. Not reachable in this candidate: I found no `clone`, `copy` or `toJSON` on any material under `src/features/viewport/**`.
Smallest correction: add `configurable: true` to the descriptor and add one assertion to `viewportFigureMaterial.test.ts` that `createFigureMaterial().clone()` still satisfies `isFigureMaterial` **and** exposes a `color`. The durable form is a `class FigureMaterial extends THREE.ShaderMaterial` that defines `color` in its constructor, so `clone()` reconstructs it; either is small.

**F3 — trivial; actionable.**
File: `{DESKTOP}/src/features/viewport/viewportFigureMaterial.ts:63–77`.
What is wrong: the drawn alpha comes from the material's own `opacity` *uniform*, while `THREE.Material.opacity` is left at its default `1`. `createFigureMaterial({ opacity: 0.82, transparent: true })` yields a material that draws at 0.82 and reports `material.opacity === 1`.
Evidence: the constructor passes `opacity` into `uniforms` only; `ShaderMaterial` does not mirror `material.opacity` into a uniform the way the built-in materials do. Nothing reads `material.opacity` in the product today (the only two occurrences in `PipeViewport.tsx`, at 3941 and 4022, are writes to the grid helpers' `LineBasicMaterial`). Smallest correction: set `material.opacity = options.opacity ?? 1` beside the uniform, or expose the uniform through an `opacity` accessor the way `color` is exposed, so the two can never disagree.

## Observations that are not findings

- **Roles the design does not name.** `node → canvas.pipeShade`, `routeGridAxis → canvas.draft` and `routeGridLine → canvas.gridMajor` are reasonable choices, but §6 gives no role for a node blob or for the routing construction grid's two line weights, so they are the lane's judgement rather than the design's word. Worth a line in the design's open items, not a change.
- **The silhouette shade is a derived value, not a token, for every role but the tube.** One global ratio, `linear(canvas.pipeShade)/linear(canvas.pipe)`, is applied to every figure material, so a support cone's silhouette draws `canvas.glyph` times that ratio and a node sphere's draws `canvas.pipeShade` times it. Exact and intended for the tube (§6.2); for the others it produces a colour that is in no token and against which no contrast figure in the record was measured.
- **Residual risk for the next part: the ledger cannot see a texture in a uniform.** Both `countOwnedObjects` and `disposeObjectChildren` find textures by `Object.values(material)`. The figure material is deliberately texture-free and says so, which is the right call — but the first figure material that gains a texture uniform (a gradient or a ramp for the edge line, say) will be neither counted nor disposed, silently. The ledger's texture rule should be extended in the same slice that adds one.
- **Residual risk I could not evaluate: the frozen visual point oracle's rim band.** The oracle qualifies a pair only when the *rim* pixel is within ±48 per channel of white (light) or black (dark). The ground grid moved from 0.55 opacity to full opacity, and `canvas.gridMajor` light `#ced1d5` is 49 off white on the red channel. Whether a major grid line can fall in a rim band depends on the fixture's geometry, which I cannot determine without a Playwright run. Addendum 1 §1 makes the first profile a recorded demonstration rather than a gate that must keep passing on the redesigned canvas, so this is a note for the combined candidate's evidence, not a defect in this one.
