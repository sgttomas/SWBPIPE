## Narrow checksum-label mechanism

After adoption, implement an exhaustive adapter-boundary map: rfc8785_jcs → JCS, NONE → NONE; unknown/TBD fails explicit compatibility validation instead of guessed conversion. Keep internal runner labels and existing serialization contracts unchanged unless separately adopted. Copy algorithm/value/payload_ref exactly. Never recompute or change existing model/mechanics hashes solely because an exported identifier changes. If an enclosing document hash exists, recompute it for changed document bytes under its already accepted algorithm; bind exactly which payload each checksum hashes.

The shared serializer documents an intentional large-integer divergence (`core/serialization/canonical_json/src/lib.rs:16–25`; `fixtures/canonical_hash/README.md`). RFC 8785 §3.1 requires IEEE-754 double representability, and its number serialization uses ECMAScript semantics ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785), inspected 2026-09-08 UTC). Thus JCS is a vocabulary reconciliation on the accepted interoperable input basis, not proof of universal RFC conformity or permission to round/change large integers. Preserve the existing large-integer parity fixture and explicitly disclose/route any wider-input policy. The current witnesses contain model/run references and digests; their conformance does not prove every possible source payload is I-JSON. No algorithm refactor or corpus re-blessing belongs here.
