# Boundary single/batch trust context proposal
No JSON bypass flags. Public apply_operation/validate_operation always use Single context: optional boundary_association creation validates metadata and requires no existing boundary_id in current base supports. A single creates one valid member only; cannot append to an existing group, even with extra caller flags. UI offers composite creation through batch.
Batch preflight validates all grouped create_support members against ORIGINAL input base (no existing group), exact canonical ordered rigid+spring member payloads, same association/node, unique member IDs, no unsupported members; it constructs an opaque crate-private ValidatedBoundaryBatch token whose fields are private and bind canonical submitted batch/member payloads and initial base hash. Token has no serde Deserialize, no public constructor/JSON representation, and is never supplied by caller.
Existing applier run gains a crate-private optional trusted context parameter. Public single exports hardcode None. Batch internal replay calls a crate-private apply_validated_batch_step using token; create_support may accept earlier in-batch group members only if exact current operation/member canonical payload is present in token. All other creation/ref/unit/stale validation remains unchanged. Input JSON cannot supply this parameter. Intermediate IDs collide via existing target uniqueness guards.
Do not remove metadata for replay or patch it into final model afterward: accepted member passes through same create_support write as ordinary single operation. Context changes group-newness basis only. Public single route rejects second member of existing group. Batch all-or-none outputs and one checkpoint remain required.
Tests: direct first member permitted, direct append blocked, direct fake JSON context flag cannot bypass; batch second legitimate member allowed; base collision even if preceding batch deletes old member; mixed nodes/metadata/order/duplicate IDs block entire batch; configuration/scalar edits preserve read-only association.

## V2 associated-support basis guard
All operations targeting an existing support with boundary_association, including configuration replacement, scalar edit and deletion, require complete current authoritative claimed-model-hash evidence. Associated support creation also requires complete current hash to bind group-newness. Legacy unassociated single operations retain existing optional-hash behavior. Missing/null claims block; malformed/mismatch claims flow through existing strict hash validator and block. This is mandatory even though configuration.before excludes read-only association: association changes therefore invalidate the full model hash and queued mechanics edits cannot cross changed group identity unnoticed. Batch internal replay supplies fresh complete hashes after initial base is validated.
