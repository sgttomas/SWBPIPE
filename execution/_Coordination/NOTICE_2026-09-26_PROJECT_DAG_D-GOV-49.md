# One accepted DAG per project (D-GOV-49) and the `project-dag` workflow

Owner-directed Root tranche `ROOT-PROJECT-DAG-D-GOV-49-20260926` (`docs/governance_harness/_DECISIONS/D-GOV-49_project_dag_authority_and_currency.md`) rewrites CONTRACT K-DEP-1, adds SPEC §5.4, and adds the bundled `project-dag` workflow:
- **Authority.** Neither the local dependency files nor a project DAG is self-authorizing; authority comes from the human's acceptance. `_DEPENDENCIES.md` and `Dependencies.csv` are the dependency evidence (human declarations and agent extractions) and may change at any time. An accepted project DAG version is a snapshot of that evidence the human reviewed and accepted. It carries authority only through its acceptance record, and only while it is current with the evidence.
- **Departures.** When a local file departs from the accepted version (a new edge, a removed edge, or a cycle), neither side silently wins. A currency audit flags the DAG stale for the affected deliverables, a candidate new version is prepared, and the human accepts it or rejects the change. Until then, unaffected work uses the accepted version, and affected deliverables are `DAG pending` rather than ready or blocked. The flag clears when a new version is accepted or the change is rejected.
- **Blockers.** A project with an accepted DAG computes blockers from the accepted current version, with `DAG pending` for mismatches. A project without one uses its recorded registers (SPEC §5.3).
- **Scope.** The Chirality repository has no cross-project dependency graph. Each project may accept its own DAG; each development loop builds work graphs (`construct-local-work-graph`) for a tranche of work within it.
- **`_DAG/`.** SPEC §0.3 and §1.2 register `{EXECUTION_ROOT}/_DAG/` (`{DAG_ROOT}`): immutable `DAG-NNN/` versions, a `_LATEST.md` pointer naming only an accepted version, candidates under `_Candidates/`, and SCC cases under `cases/<SCC-ID>/`. Currency audits are observations under `_Evaluation/DAGCurrency/`.
- **Required fields.** `Explicitness`, `SatisfactionStatus` and `Confidence`, which SPEC §6.2 marks SHOULD for a register and `audit_dag.py --canonical --strict` rejects when blank, are REQUIRED in every edge row of an accepted version. Blanks are completed in the local file before acceptance.
- **SCC cases.** `scc-resolution-case` defaults to `_DAG/cases/<SCC-ID>/`. A project that already holds its cases in a PKG-00 control deliverable may keep that legacy home. Each project uses one home; existing cases are not migrated. Retiring the legacy home is a later decision.
- **Workflows.** `project-dag` constructs, examines and obtains acceptance of a version, audits its currency, and holds affected deliverables `DAG pending` until the human decides. It is in the catalog's core navigation list (not a central workflow). `construct-local-work-graph` works within the accepted current version and respects `DAG pending`. `project-setup` Phase 2.2b hands off to `project-dag`, and its Phase 3.1 scan uses the accepted version where one exists. The agent manual v3 §8 is aligned.

Nothing is retrofitted: existing DAG records, pointers and case folders are unchanged. Historical runs are not rewritten. This loop decides its own adoption; this source tranche grants no release.

Piping-specific:
- `execution/_DAG/DAG-001` to `DAG-011` and `execution/_DAG/_LATEST.md` remain this loop's accepted records and follow the layout SPEC §1.2 now registers.
- This loop's records call the approved DAG the "dependency graph authority" (`docs/AGENTIC_DEVELOPMENT_WORKFLOW.md`; decision D-56) or its "dependency authority" (`_DAG/_LATEST.md` for DAG-011), and local `Dependencies.csv` files "synchronized mirrors, not independent sequencing authority" (for example `_DAG/DAG-010/DAG_Audit.md`). That wording is stronger than D-GOV-49. Under D-GOV-49 a DAG carries authority only through acceptance while it is current with the local evidence, and a departure is decided by the human rather than resolved in the DAG's favour.
- Whether and how to change that wording, and any local-register synchronization practice that relies on it, is left to this loop. This notice requires no action.
