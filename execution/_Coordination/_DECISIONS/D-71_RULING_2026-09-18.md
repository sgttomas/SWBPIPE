## Item 7 — what option B would mean, as put to the owner

Under **A** the Checked mark is a working aid: a tick by a named person on a row, bound to that row's content so it lapses when the row changes, kept in the project's interface state, never in a status, an export, a run record or a report. It costs nothing to set and claims nothing.

Under **B** each tick is a stored human acceptance record, and the governance already says what such a record must be (`docs/PROFESSIONAL_BOUNDARY.md` §7): it identifies the accepting authority; it binds to the model hash, the rule-pack checksum, the report hash, the software version and the input manifest; it states its scope and limitations; it goes stale when any bound item changes; it is stored apart from solver, rule and report outputs. Three consequences follow. First, PRD §21.3 says the MVP has no formal acceptance workflow, so B needs a PRD-level act as well as a classification. Second, the storage and invalidation workflow is an open item (`PB-TBD-002`) that has to be designed and built before the mark can exist at all, where A can ship with the first tranche. Third, the binding is to whole-analysis things (model, rule pack, report), which fits a row badly: a row-level tick would go stale whenever anything anywhere in the model changed, which defeats its purpose as a checking aid.

ROOT's recommendation is A for the row mark, and, if the owner wants a formal acceptance in the product, a separate later act on the Review page ("accept this analysis", bound to the run, the model hash and the report), which is where the §7 requirements fit naturally and where the reserved `ENGINEER_ACCEPTED` label would be used. A does not foreclose that; B on the row mark would delay the row mark without delivering the analysis-level acceptance.
