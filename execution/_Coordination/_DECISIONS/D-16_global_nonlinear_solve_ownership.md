## 1. Decision statement and scope

Decide **which deliverable owns the *assembled* iterative loop** that wraps the nonlinear-support active-set classifier — the loop that, each iteration, (a) assembles and solves the global linear frame system for the current active set, (b) feeds the resulting trial displacements/reactions to the per-support state classifier, and (c) re-iterates until the active set stabilizes (convergence) or the iteration cap is reached (non-convergence) — **and the iteration-control method** it uses (active-set fixed-point with a convergence test and, if adopted, relaxation/damping).

The candidates surfaced by the plan are:

- **DEL-04-04** (`core/solver/nonlinear_supports`, the active-set classifier crate), whose built first slice explicitly *does not* assemble or solve the global nonlinear system; or
- **a frame-assembly integration tranche under DEL-04-01** (`core/solver/frame_kernel`, which owns global stiffness assembly + the linear solve), which would host the loop and call the classifier as a per-iteration state oracle.

This decision governs **deliverable ownership and method selection only**. It does not issue any deliverable (all remain `CHECKING` per their lifecycle), does not set the convergence *tolerance value* (that is `D-19`), and does not decide how piping components are realized in the assembled system (that is `D-18`). It is a precondition for opening Phase D item **D6** (the assembled nonlinear iterative solve) as scoped, sequenced tranche work.

## 3. Current state — what exists versus the gap

**The classifier crate exists and is bounded as a per-iteration state oracle.** `core/solver/nonlinear_supports/src/lib.rs` classifies one-way / gap / lift-off / friction support states from *supplied* trial displacement and reaction facts:

- Module header: *"This crate classifies nonlinear support states for iterative mechanics solves. It does not assemble a global solve…"* (`core/solver/nonlinear_supports/src/lib.rs:1–5`).
- Stated limitations include verbatim the phrase the plan quotes: *"This crate does not assemble or solve the global nonlinear system."* and *"Production tolerance policy, sparse solver selection, final constraint strategy, and result-envelope integration remain outside this bounded crate."* (`core/solver/nonlinear_supports/src/lib.rs:335–337`).
- Stated assumptions include: *"Trial displacement and reaction facts are supplied by an external mechanics solve."* (`core/solver/nonlinear_supports/src/lib.rs:325–326`).
- The public entry point evaluates exactly **one** iteration — `evaluate_active_set_iteration(input: &ActiveSetIterationInput)` consumes a single `iteration`/`max_iterations`/`tolerance`/`trial_states`/`prior_states` snapshot and returns one `ActiveSetIteration` with `converged`, `changed_supports`, `residual_norm`, and diagnostics (`core/solver/nonlinear_supports/src/lib.rs:440–511`; input/output structs at `:220–238`). There is **no loop**, no assembly call, no re-solve inside the crate. `residual_norm` is the count of supports that changed state this iteration (`:474`, `:327–328`), and `converged = residual_norm <= tolerance` (`:508`).

**The linear assembled solve exists in the frame kernel.** `core/solver/frame_kernel/src/lib.rs` ("Code-neutral 3D frame stiffness kernel", `:1–4`) provides `assemble_global_stiffness(...)` (`:669–693`), `reduce_system(...)` (`:695`), and `solve_dense(...)` (`:805`). The kernel has **zero** references to nonlinear / active-set / support / gap / lift-off / friction (grep over the file returns none) — it is a linear assembler/solver only. Its deliverable spec confirms ownership of "the global 3D frame stiffness assembly, coordinate transforms, boundary conditions, and sparse solve interface" and explicitly scopes out "Numeric tolerances, convergence thresholds, performance targets" and the support families owned by DEL-04-03/04-04 (`execution/PKG-04…/DEL-04-01_3D frame stiffness kernel/Specification.md:5,10,13`; REQ-003 `:23`, REQ-006 `:26`). It does **not** claim an assembled *nonlinear* iterative loop.

**The non-convergence diagnostics taxonomy exists.** `core/solver/diagnostics/src/lib.rs` defines `SolverDiagnosticCode` with `NonConvergence`, `TolerancePolicyTbd`, `SparseSolverTbd`, `SingularSystem`, `IllConditionedSystem`, `ConditioningFailure`, `NonPositivePivot`, and restraint/topology/numeric-input codes (`:137–148`). `convergence_diagnostic(iteration_count, max_iterations, residual_norm, tolerance)` returns `None` when converged, a `Failure`-severity `NonConvergence` at/after the iteration cap, and a `Warning`-severity `NonConvergence` before the cap (`:494–526`); `tolerance_policy_tbd_diagnostic()` keeps the open tolerance policy explicit (`:625–630`); and the `NonConvergence` remediation text already reads *"Review the nonlinear iteration inputs, active-set state, and accepted tolerance policy."* (`:682–683`). The classifier already emits these via `convergence_diagnostic` and annotates them with active-set context (`core/solver/nonlinear_supports/src/lib.rs:476–501`, `581–613`, `615–621`).

**The gap.** The deliverable record for DEL-04-04 *anticipates* the loop but the *built crate* disclaims it, and no deliverable currently *owns* the assembled loop:

- DEL-04-04 `_CONTEXT.md` lists "nonlinear solver loop" as an Anticipated Artifact and describes the deliverable as "Implement iterative activation … with convergence reporting" (`…/DEL-04-04…/_CONTEXT.md:10,13`). Its `Datasheet.md` Construction table places the "Active-set iteration loop — In scope for future implementation; algorithm details TBD" (`…/DEL-04-04…/Datasheet.md:42`), and REQ-02 requires the behaviors be addressed "through a controlled iterative method" with REQ-09 deferring solver library / convergence tolerances / data contracts as TBD (`…/DEL-04-04…/Specification.md:12,19`).
- The domain ledger carries both sides of the tension verbatim: *"The active-set iteration loop is in scope for future implementation; algorithm details are TBD."* and *"Active-set report limitation: this crate does not assemble or solve the global nonlinear system."* The same ledger records the program state: *"R4 (components + nonlinear supports) is … no assembled nonlinear iterative solve (Phase D)."*

So the *deliverable-level intent* of DEL-04-04 includes a loop, but the *code-neutral boundary* deliberately drawn around the built crate excludes the assembly/solve the loop must perform each iteration. D-16 resolves where that loop lands and how it iterates. (Note: the D9 row of the plan references an `open_pipe_stress_nonlinear_benchmarks` crate validating the classifier; an in-repo crate by that exact name was **not** confirmed in this pass — validation fixtures live under `validation/benchmarks` — so the existence of converged *global-solve* benchmarks should be treated as not-yet-built, consistent with the "no assembled nonlinear iterative solve" ledger state.)

## 4. Options

|---|---|---|---|---|---|---|
| **O-A** | **New integration tranche bridging DEL-04-04 ↔ DEL-04-01.** A dedicated assembled-nonlinear-solve tranche (under PKG-04) owns the loop; DEL-04-01 supplies assemble/reduce/solve, DEL-04-04 stays the per-iteration state oracle. | The loop calls `assemble_global_stiffness`/`reduce_system`/`solve_dense` (or the sparse path per `D-17`) each iteration with the current active set's effective restraints, builds `ActiveSetIterationInput` from trial results, calls `evaluate_active_set_iteration`, and re-iterates until `converged` or the cap fires `NonConvergence`. | Keeps both existing crate boundaries intact and as-documented; no crate has to violate its stated scope; isolates the new cross-crate concern (active-set restraint mutation between iterations) in one named owner; cleanest seam for `D-17` (sparse adoption) and `D-19` (tolerance) to bind into. | Introduces a new deliverable/owner to track and seal; the DEL-04-04 Datasheet's "iteration loop in scope" line must be re-pointed to the new owner (a decomposition-note edit). | Low: both kernels keep their disclaimers literally true; the new owner inherits the code-neutral invariants (mechanics only, no protected data, missing inputs are findings). | Strongest preservation: every existing "does not assemble / does not solve" statement remains accurate; the boundary moves to a *new* explicitly-scoped surface. |
| **O-B** | **DEL-04-04 owns the assembled loop (re-scope the classifier crate).** Promote the classifier crate to host the loop and call the frame kernel. | The crate gains an assembled-solve driver that depends on `frame_kernel` (and later `sparse_direct`), wrapping its existing `evaluate_active_set_iteration`. | Matches DEL-04-04's stated *deliverable intent* (the loop is already an "Anticipated Artifact"); single owner for "everything nonlinear-support"; no new deliverable to seal. | Directly contradicts the crate's own published boundary (`:4`, `:335`) and the ledger limitation atom — those statements would have to be rewritten/retracted, a documented scope change; couples the oracle to assembly, making the classifier harder to unit-test in isolation; concentrates two distinct numerical concerns in one `WATCH`-envelope crate already flagged "Complex" (`…/DEL-04-04…/_CONTEXT.md:23–29`). | Medium: re-opening a sealed boundary statement is a governance-visible edit and risks scope creep within an already-large crate. | The "does not assemble or solve the global nonlinear system" limitation is *deleted/inverted*; care needed that the loop code still cannot decide compliance (OPS-K-MECH-2). |
| **O-C** | **DEL-04-01 owns the assembled loop (extend the frame kernel).** The frame kernel grows a nonlinear driver that calls DEL-04-04 as the state oracle. | The kernel adds a `solve_nonlinear(...)` driver alongside `solve_dense`, looping assembly→solve→classify. | Co-locates the loop with the assembly/solve primitives it calls every iteration (fewest cross-crate hops); reuses the kernel's existing restraint-reduction machinery. | Contradicts DEL-04-01's spec, which scopes the kernel to *linear* assembly + a *solve interface* and explicitly defers convergence thresholds and the support families to DEL-04-03/04-04 (`Specification.md:5,10,13`); pulls active-set/iteration semantics into a crate that today has zero nonlinear references; blurs the clean "linear kernel" identity. | Medium: erodes the conservative-first-slice identity of the kernel and forces a spec re-scope. | The kernel's "code-neutral mechanics kernel" identity is preserved, but its *linear* scoping statement must be widened to include an iteration controller. |

**Method note (applies to all options).** The iteration-control method on offer is the **active-set fixed-point** the classifier already implements: each iteration re-solves the linear system for the current active set, the classifier re-classifies states, and convergence is "no support changed state" (`residual_norm == 0`, i.e. `<= tolerance` with an integer-count residual; `core/solver/nonlinear_supports/src/lib.rs:474,508`). Whether to add **relaxation/damping** (under-relaxing displacement updates, or hysteresis on state flips to prevent chatter/cycling between two active sets) is a method sub-choice the chosen owner must decide; the diagnostics layer already distinguishes pre-cap `NonConvergence` (Warning) from at-cap `NonConvergence` (Failure) to surface chatter (`core/solver/diagnostics/src/lib.rs:507–525`). The convergence *tolerance and iteration cap values* are **out of scope here** and routed to `D-19`.

## 5. Advisory recommended disposition (PROPOSAL — human rules)

**Recommend O-A: a new integration tranche bridging DEL-04-04 ↔ DEL-04-01, with the classifier remaining the per-iteration state oracle** — matching the plan's advisory recommendation (`plans/PLAN_2026-06-17_prd_completion.md` §2.3, D-16 row). Rationale: O-A is the only option under which **every existing deliverable boundary statement stays literally true** — the classifier keeps "does not assemble or solve the global nonlinear system" (`:335`) and the kernel keeps its linear-kernel identity — while the genuinely new concern (mutating effective restraints across iterations and driving assembly→solve→classify to convergence) gets a single, explicitly-scoped owner that `D-17` (sparse adoption) and `D-19` (tolerance) can bind into cleanly. O-B and O-C each require retracting a published scope boundary, which is a governance-visible edit and concentrates two numerical concerns in one crate. The method should be the **active-set fixed-point already built**, with relaxation/anti-chatter left as an in-tranche method decision evidenced by the existing `NonConvergence` Warning/Failure split. The only documentation consequence of O-A is re-pointing DEL-04-04's "iteration loop in scope" Datasheet/`_CONTEXT` line to the new owner (a decomposition-note edit, applied only on acceptance).

## 6. Decision dependencies and relationships

- **D-19 (release convergence tolerance policy)** — *tightly coupled, sequence-after.* D-16 chooses the loop owner and method; D-19 supplies the *criterion* the loop converges against (residual/iteration tolerance + cap) by extending the `DEC-026` class-tiered policy and clearing the `TolerancePolicyTbd` diagnostic (`core/solver/diagnostics/src/lib.rs:147,625–630`; plan §2.3 D-19 row). The loop is buildable once D-16 is ruled, but its R4 exit cases cannot be claimed "converged" until D-19 fixes the tolerance. Recommend ruling D-16 first (or jointly), then D-19 at the D6 lead-up.
- **D-18 (component macro-element realization)** — *coupled via what gets assembled.* D-18 decides whether bends/branches/expansion-joints are solver macro-elements or data + user-flexibility multipliers (`ComponentMechanicsInterface.solver_consumption`; plan §2.3 D-18 row). That choice determines *what stiffness the loop assembles each iteration*, but not *who owns the loop* or *how it iterates*. D-16 and D-18 are separable and can be ruled independently; if D-18 favors macro-elements (e.g., for EJ stiffness), the O-A integration owner is the natural consumer.
- **D-17 (sparse-solver live-path adoption)** — *adjacent.* D-17 decides whether the per-iteration solve uses the dense path (`solve_dense`) or binds `core/solver/sparse_direct` (the `DEC-023` skyline LDLᵀ solver; `core/solver/sparse_direct/src/lib.rs:1–11`). The D-16 owner is the call site either way; O-A gives D-17 the cleanest binding point. Independent ruling; sequence with D6.
- **Carried decisions already RULED that this builds on:** `DEC-023` (D-03 — in-repo sparse skyline solver), `DEC-024`+`DEC-026` (D-04 — class-tiered *verification* tolerance; the *solver convergence* tolerance is the distinct open `D-19`), per `execution/_Decomposition/SOFTWARE_DECOMP.md` §12 rows `DEC-024`/`DEC-026`.

## 7. Ruling mechanism

Per existing practice (`DEC-018`..`DEC-040`): the human project authority selects an option (or rules directly); the ruling is appended to `execution/_Decomposition/SOFTWARE_DECOMP.md` §12 as the next `DEC` entry citing this packet; if O-A is selected, the executing agent's first decomposition action is to (a) register the new integration tranche/owner for D6 and (b) re-point DEL-04-04's "iteration loop in scope" Datasheet/`_CONTEXT.md` lines to that owner; this register row then moves `AWAITING_RULING` → `RULED` with the record pointer. Agents never assign D6 ownership or open the assembled-loop tranche without the recorded ruling. The convergence tolerance value remains gated on `D-19`.
