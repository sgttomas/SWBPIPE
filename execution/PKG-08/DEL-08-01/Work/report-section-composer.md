# Calculation report section composer (RT-R4)

**Implementation basis:** the current source contract at `6108037a5fb3b8a1041940e40ba7d765177743e8`.
Paths are repository-relative. This work serves RT-R4 and exit criterion 4 in
`docs/RELEASE_TARGET_v1.0.md`, under the already adopted R-08-01-011 in
[ScopeOfWork.md](../ScopeOfWork.md). It uses the report-wide exact display step
in DEL-08-04 [csv-export.md](../../DEL-08-04/Work/csv-export.md) §3.
It records no acceptance, issuance, approval, compliance or lifecycle standing
(F-PIP-3). Standard claim fence applies (DEC-081).

C1-C3 implement the contract, renderer and session-only local-private desktop
composer. C4 adds the composition to the native user-release derivation (§4.4).
C5 adds the model-input sections (§2.7). User-released reports admit
exact results under the current D-6 implementation; composition does not reopen
or narrow that adopted route. The current source is the basis for route admission.

## 1. Scope and gap

**What the report does today, on both routes** (pressure-free
`preview-physics-2`; exact `pressure-2`, `pressure-source-1`):
- **One fixed document.** `report_renderer` assembles eight governed sections
  in a fixed order (`SECTION_ORDER`, `report_renderer/src/lib.rs:47-56`;
  `assemble_report_sections`, `:936`). They are Model Input Summary, Load Cases,
  Results, Warnings/Assumptions/Provenance, Audit Manifest, Rule Pack References,
  Limitations and Professional Boundary Notice. A frame of title, meta line,
  status banner, local-private or user-release notice and blocked banner comes
  first. The HTML and the PDF (`pdf_emitter`) consume the same assembled
  sections. The print view is the canonical HTML plus a banner that names its
  hash (`derived_print_view`, `:2428`).
- **Results are one flat table.** It has one row per source row, in source
  order, in the five-field projection (`reportResultRows.ts:47`;
  `bindings::expected_report_result_rows`, `bindings.rs:145`). On an exact
  result the table is preceded by the exact block: the semantic contract, the
  standing line and the stress headlines (W-11 §3.2). The "Referenced result
  export" table lists every source row with its checksum.
- **The generator contract requires all eight kinds**
  (`REQUIRED_SECTION_KINDS`, `report_generator/src/lib.rs:12`;
  `validate_template_slots`, `:773`). The desktop declares all eight, each as
  `required: true` (`renderableReportInput.ts:1016-1029`).
- **Three boundaries re-derive the full row list:** the package producer
  (W-18 §2.3 item 6), the exact native render (`rederive`,
  `report_render_exact.rs:253`) and the user-release derivation (W-18b §2.6).
- **Not present.** Nothing lets the user choose content, order or case
  selection. Results have no per-family tables, extremes or sorted views. The
  report lists no load combinations, model input tables (geometry, supports,
  materials, loads), weight/CoG or support-load tables.

**What the composer adds.** The user chooses which optional content sections
appear, their order within their governed parent section, and per section the
case selection and the view. The governed sections and the frame cannot be
removed. A composed report stays bound to one exact result, states its
composition and shows how many result rows it carries.

**Criterion 4.** The criterion needs the §19.3 notice and a reproducible
canonical hash on a report the user releases, saves and prints. The composer
keeps the notice in every composition (§2.4). It makes the composition a
recorded report setting, so the same inputs, versions and composition give the
same bytes (R-08-01-010). User-released reports cover the currently admitted routes, and C4 carries
the composition into their native derivation (§4.4).

## 2. The composer model

### 2.1 Granularity

The eight governed sections keep their kinds, titles and order. Composable
sections are **subsections of a governed parent** (`<h3>` in the HTML, a
`Subheading` block in the assembled model, so the PDF matches). So the
generator contract and its required-kind check do not change, and no
composition can move the notice ahead of or behind anything (D-1).

### 2.2 Catalogue

Required content (always present; not offered as a choice):

| Parent | Required content |
|---|---|
| Frame | Title; meta line; status banner; local-private notice or user-release notice and record rows; blocked banner; the closing note on derived copies |
| Model Input Summary | Project and model identity, unit system and unit display summary, coordinate systems, **model hash**, input-manifest reference (today's table) |
| Load Cases | Today's load-case table |
| Results | The display-rule statement; on an exact result the exact block (semantic contract, **standing line**, stress headlines on both section bases); the row-coverage line (§2.6); the "Referenced result export" table of every row and checksum |
| Warnings, Assumptions and Provenance | All of it: diagnostics, assumptions, user-supplied values, provenance notes, library records (R-08-01-007; FR-REP-003) |
| Audit Manifest | Envelope references; **Software, Solver And Run** (the solver and engine stamp); the Report Composition table (§2.6) when composed |
| Rule Pack References | References and user-rule outcomes whenever a rule-check run is recorded; otherwise its "none" statements |
| Limitations | The technical-preview limitation, the exact-route limitations, the TBDs |
| Professional Boundary Notice | The PRD §19.3 notice and the sign-off table |

Composable sections. These are the RT-R1 results surfaces and the model input.
Every value shown is a bound row or a projection of the bound model. All
eleven are implemented (`composer::CATALOGUE`, `REPORT_COMPOSITION_CATALOGUE`):

| Id | Parent | Content | Options | Slice |
|---|---|---|---|---|
| `result_rows_all` | Results | Today's flat table (the default) | cases | C2 |
| `result_displacements` | Results | Translation and rotation rows | cases; view `all` or `extremes` (per case and component, the largest magnitude, grouped by case, label and display unit) | C2 |
| `result_forces_moments` | Results | Element force and moment rows | cases | C2 |
| `result_stresses` | Results | Stress rows, with their section-basis suffix on an exact result | cases; view `all` or `largest` (by magnitude, with a limit of 1-1000 within each display unit) | C2 |
| `result_support_loads` | Results | Support reaction rows, grouped by support, then case | cases | C2 |
| `result_other_rows` | Results | Every row of a kind outside the family table, for example the `spring_hanger_user_input_review` rows | cases | C2 |
| `load_combinations` | Load Cases | "Load combinations": combinations as authored (§2.7 columns) | none (all cases, `all` view) | C5 |
| `input_geometry` | Model Input Summary | "Geometry": nodes, pipes and components, as entered | none (all cases, `all` view) | C5 |
| `input_materials_sections` | Model Input Summary | "Materials and sections", as entered | none (all cases, `all` view) | C5 |
| `input_supports` | Model Input Summary | "Supports and restraints", as entered | none (all cases, `all` view) | C5 |
| `input_loads` | Model Input Summary | "Applied loads": primitive loads per case, as entered | none (all cases, `all` view) | C5 |

**Families.** A closed table maps each row `kind` to one family, so the
families partition the rows. The table is derived from the `family` column of
the current semantic-contract fixtures and checked against those fixtures. It is a committed fixture,
`fixtures/reports/invented/report_composition_families.json`, which both the
TypeScript and the Rust code read. A kind not in the table falls to
`result_other_rows`, so no row can be lost by classification.

**Joins later, through the same mechanism** (not in v1):
- weight and CoG (RT-R1), which need a Rust mirror of `weightSummary.ts` and
  touch numerical meaning;
- the modal section (DEL-04-09 M3; this deliverable's `DEL-04-09` need);
- the hanger table (RT-A11);
- comparisons (FR-REP-004; DEL-08-06 sections).

### 2.3 Order, inclusion, options

- **The composition record** is `report_composition`, an optional member of
  `RenderableReportInput`, `#[serde(default, skip_serializing_if =
  "Option::is_none")]`. Its new structs are `deny_unknown_fields`, and the
  shared object-form check covers them (`object_form.rs:485`):

  ```json
  { "composition_version": "1.0.0",
    "sections": [ { "section_id": "result_stresses",
                    "cases": "all",
                    "view": { "kind": "largest", "limit": 25 } } ] }
  ```
- **Inclusion.** A listed section is included and an unlisted one is omitted.
  Each id is listed at most once, and only composable ids may be listed. An
  empty list is permitted.
- **Order.** Within each parent, the list order. Parents keep the governed order.
- **Cases.** The value is `"all"` or a non-empty list of `case_ref` values, as
  the rows carry them (`<basis type>:<basis id>`). A row whose `case_ref` is
  `TBD` is shown only under `"all"`.
- **Views.** These are display orderings and selections of bound rows. They
  compute no new number. Magnitude compares the row's value after the report
  display rule's exact step, which shifts `Pa` to `MPa` by decimals
  (`csv-export.md` §3). It ranks within one display unit, breaks ties by source
  order, and treats `-0` as `0`.
- **Overlap.** `result_rows_all` excludes the family sections, so each row is
  shown at most once (§5 relies on this).
- **Units.** v1 has one report-wide display rule, the existing one (Pa shown as
  MPa, six significant digits). There are no per-section units (D-3).
- **No free text.** The composition carries no title, heading or note, so
  composition adds no wording to the report.
- **Default.** The composer opens on `result_rows_all` alone. While the user
  leaves that unchanged, the desktop sends no composition, so the output is
  today's bytes (K2).

### 2.4 Required content cannot be removed

The catalogue is closed. Required content is not in it, and a composition that
names a governed kind or an unknown id is refused. The renderer emits the frame
and the governed sections before and around any composed subsection, so no
composition reaches them. The same holds on every route because every route
renders through `assemble_report_sections`.

### 2.5 Refusals

These are blocking reasons of the render, with export blocked. Each also
refuses the package.

| Code | When |
|---|---|
| `REPORT-COMPOSITION-VERSION-UNSUPPORTED` | `composition_version` other than `1.0.0` |
| `REPORT-COMPOSITION-SECTION-UNKNOWN` | an id outside the composable catalogue, governed kinds included |
| `REPORT-COMPOSITION-SECTION-DUPLICATE` | an id listed twice |
| `REPORT-COMPOSITION-OPTION-INVALID` | an option the section does not take, a limit outside 1-1000, an empty or duplicate case list, or an explicit `TBD` case (`TBD` appears only under all cases) |
| `REPORT-COMPOSITION-ROW-FIELDS-INVALID` | partial bound metadata or unreadable stored number text |
| `REPORT-COMPOSITION-CONTEXT-NOT-ADMITTED` | a composition outside the explicit local-private and user-released contexts |
| `REPORT-COMPOSITION-CASE-UNKNOWN` | a `case_ref` that no bound row carries (names it) |
| `REPORT-COMPOSITION-ROWS-OVERLAP` | `result_rows_all` together with any family section |

An empty section list omits every optional subsection and shows zero bound
result rows; the governed content remains. There is no required optional
subsection. A family section with no rows under its cases renders the statement "No result
rows of this kind for the selected cases." It is not a refusal.

### 2.6 Binding to one exact result

- **The composer selects; it never supplies.** The renderer input keeps the
  full bound row list, and each boundary keeps its equality check unchanged:
  - producer item 6;
  - the exact native render's custody binding and `rederive`;
  - the user-release derivation.

  The renderer applies the composition to those rows inside
  `assemble_report_sections`. So every shown value is a bound row, and the model
  hash, the run (`report_sections.run_ref`), the received-result checksum, the
  per-row checksums and, on an exact result, the standing line are the
  report's own, as today.
- **Row contract.** Selection needs each row's kind, entity and value. The
  five display fields gain four bound metadata fields:
  - `kind`, the source `kind`;
  - `entity_ref`, the source `entity_ref` or `null`;
  - `value_text`, the canonical stored number text the display rule starts from;
  - `unit`, the stored unit, so Pa and MPa rows can be ranked in the same
    display unit using the exact step.

  Both helpers and `report_result_rows_parity.json` change together (W-18
  §2.3 item 6), so every boundary binds the new fields. The renderer prints
  them only in composed sections, so K2 holds.
- **Disclosure lines.** Existing numerical-health lines carry none of the bound
  metadata. They always render separately and are never selected, ranked or
  counted as bound result rows. A partial metadata set is refused.
- **Disclosure.** When composed, the Results section states "Result rows shown:
  n of N." Each composed subsection states its cases and view. The Audit
  Manifest section gains a "Report Composition" table: every implemented catalogue id (C5 adds the model-input ids),
  `included` or `omitted`, its list position and options, and the SHA-256 of the composition's
  RFC 8785 bytes. Every row stays listed with its checksum in "Referenced
  result export", so omitting a row from view never removes it from the binding.
- **Stale results.** The composition carries no result identity. It is applied
  to whatever result the report is built for, and every existing staleness
  guard keeps deciding:
  - the panel's render invalidation;
  - the save basis's `isCurrent` refs (W-18 §2.5), which gain the composition,
    so a change during the awaited build retires the save;
  - the native custody binding on an exact result;
  - the solve attestation on route 010.

  A composition kept across a re-solve whose cases no longer occur is refused
  with `REPORT-COMPOSITION-CASE-UNKNOWN`. It is never applied as an empty filter.

### 2.7 Model-input sections (C5)

The five model-input ids join the closed catalogue. Each takes `cases: "all"`
and `view: {"kind": "all"}` only; any other option is
`REPORT-COMPOSITION-OPTION-INVALID`. They show no result row, so the coverage
line and `result_rows_all`'s overlap rule are unchanged.

- **Projection.** `P(M, C)` is the renderer input's optional member
  `model_input_tables`. It is present only when C lists at least one
  model-input id, and it then has exactly one member per listed id, named by
  the id. Each table is a list of rows in the model's array order (no
  sorting). Each cell is one of:
  - a stored string, copied;
  - a stored number, as its canonical number text (the row contract's
    `value_text` rule: Rust `canonical_number`, TypeScript `String(value)`);
  - a stored quantity, as `"<canonical number> <unit>"`, unconverted;
  - `null` for an absent member, shown as "—".
- **Columns** (closed; a member not named here is not shown):

  | Id | Table rows and columns |
  |---|---|
  | `load_combinations` | One row per combination: id, label, basis, operands, mode. Operands: each term as `"<factor> × <load_case or combination>"` joined by `"; "`; else `"<minuend_id> − <subtrahend_id>"`; else `operand_ids` joined by `", "`; else null |
  | `input_geometry` | `nodes`: id, label, x, y, z (stored numbers; the model's `project.units.length` names their unit). `pipes`: id, label, from, to, material, outside diameter, wall thickness, section_ref. `components`: id, label, kind |
  | `input_materials_sections` | `materials`: id, label, elastic modulus, shear modulus, Poisson ratio, thermal expansion coefficient. `sections`: id, name, section type, outside diameter, wall thickness |
  | `input_supports` | id, label, node, family, restraints (joined by `", "`), stiffness (`"<dof>: <quantity>"`), nonlinear behaviour |
  | `input_loads` | One row per primitive load, cases in model order: case id, load id, category, target (`"<type>:<node, pipe or support>"`, then `" <dof>"` when the target names one), direction, magnitude |

- **Disclosure.** Each table states that it lists values as entered in their
  stored units, unconverted, and that provenance text and notes are not
  listed. `input_loads` also states that pressure regions, equivalent-static
  inputs and analysis states are not listed; `input_supports` that hanger and
  nonlinear details other than the behaviour are not listed. The tables carry
  no result, no check outcome and no code value.
- **Binding.** The webview builds `P(M, C)`. Every boundary that holds the
  bound model re-derives it from M and C and requires equality
  (`REPORT-COMPOSITION-MODEL-INPUT-UNBOUND`, naming the first differing
  pointer, never a value), and refuses tables without a listing id or a
  listing id without tables:
  - native package save, routes 009 and 010 (its parsed model, checked
    against the request's model hash);
  - the exact native render (its bound intake model);
  - the user-release derivation, which derives `P(M, C)` into the request, so
    whole-request equality binds it.
  The standalone pressure-free render is not natively bound, like its rows;
  its package is.
- **Data boundary.** On route 010, R already refuses library- and
  rule-pack-referenced models, and the tables show only the user's stored
  values. No library record is resolved for a table.
- **Memory.** The projection is linear in the model. The existing lease tests
  gain composed requests that list all five ids.

## 5. Native custody and memory

C1-C3 add no native command. Composition rides inside the existing renderer
input for `render_calculation_report` and `save_report_package`; the complete
result rows continue through producer, native render and user-release checks.
There is no new webview access to unbound results and no catalog re-pin.
Existing object-form and forwarding/reach checks remain applicable to their
actual source surfaces. New nested composition objects must be covered by the
maintained object-form check; no historical pinned digest is copied forward.

Composition adds selection, sorting and audit allocations. A bounded catalogue
and nonoverlapping rows do not by themselves prove that existing native memory
reservations cover them. Targeted native/package checks and any required
measurement must use the actual integrated predecessor and the maintained host
route in a lane-specific window. Until then this is an explicit qualification
condition. C1-C3 change no pricing coefficient, limit or reservation. A measured
need to change those surfaces goes to Agent 0.

The four metadata members are emitted for every ordinary result row, including
inputs without a composition and the native user-release derivation. Therefore
the resource assessment includes serialized IPC/request text, the raw argument
decode, temporary object-form typed copies, source re-derivation, the producer's
full-row comparison and typed conversion, and HTML/PDF/container assembly.
The report's initial object-form check deserializes a temporary typed copy
before exact-route lease growth (`report_renderer/src/object_form.rs`,
`report_render_exact.rs`). Comparing a command's peak only with its final grown
lease does not establish that this earlier copy fits the initial lease.

The targeted native resource checks cover:

- `object_form_tests::the_object_form_check_is_priced_within_the_existing_leases`:
  default, full-family and ranked pressure-free render/package requests from
  raw IPC, retaining response serialization on the render path;
- `report_render_exact_tests::the_genuine_exact_render_and_save_stay_within_their_leases`:
  the same variants for every maintained exact witness shape, with the
  pre-growth object-form copy checked against the initial ingress lease
  separately from the full command's final reservation;
- `user_release_save_tests::default_user_release_metadata_fits_raw_ingress_and_derivation_leases`:
  default and composed pressure-free and both admitted exact user-release
  routes, including raw IPC decoding, the copied composition and native
  derivation/package assembly.

These checks use the current maintained request/vector inputs regenerated by
their writers; no old binary or
manually augmented qualification fixture supplies an implicit input.

Request/input hashes and emitted-document hashes are different evidence.
`report_package/tests/common` checks otherwise identical requests with and
without the four metadata members: canonical request and renderer-input hashes
must differ, while default HTML/PDF bytes and their hashes must match. The
comparison strips metadata only for direct renderer testing; the source-bound
producer still refuses incomplete rows. The tests exercise local-private and
user-release derivations. They do not establish that every package/member,
derivative, provenance pin or historical evidence hash stays unchanged. Each
writer/output has its own hash domain and applicable checks; a protected-output
or pin authority conflict is returned to Agent 0 before any change to it.

The reporting crates retain their unsafe-code prohibition.

## 7. Boundaries

- **No compliance claims.**
  - Section titles are mechanics words: "Stresses", "Support loads",
    "Displacements".
  - No section, view or option names a code, an allowable or a governing
    case.
  - The stress view ranks by magnitude only and carries no ratio or limit
    column.
  - The exact headlines keep "no governing basis is chosen".
- **No protected standards content.** The catalogue titles and the fixed
  statements are public template text, and the linter gates run on every
  composed section (K9). Model-input sections show only the user's own entered
  values. Rule packs stay at safe metadata (R-08-01-008).
- **Outcome wording follows RT-R3.** RT-R3's "within / exceeds user limit" is
  not yet confirmed; outcomes still read pass/fail. The composer adds no
  outcome text and no outcome column. Outcomes stay in the required Rule Pack
  References section through `user_rule_check_status_display`
  (`report_renderer/src/lib.rs:601`). When the RT-R3 wording decision is made,
  that function and its TypeScript and CSV constants change in the RT-R3 PR,
  and composed reports follow unchanged.
- **Claim fence.**
  - Composition carries no free text.
  - The §19.3 notice, the local-private notice, the user-release notice and the
    sign-off table are required.
  - A composed report is a decision-support artifact, like an uncomposed one.
    Composing it, saving it or sharing it records no acceptance, issuance or
    release by anyone but the user's own data statement under W-18b.

## 8. Adopted decisions and remaining scope

The current R-08-01-011 in ScopeOfWork is adopted and unchanged. Its exact
wording governs this implementation; the older proposed Old/New commitment
in this design is superseded and is not an adoption action.
