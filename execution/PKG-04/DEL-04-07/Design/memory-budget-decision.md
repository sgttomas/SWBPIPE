# Memory budget and machine scaling

## Governing direction

The owner clarified on 2026-10-11: the product may use up to 12 GiB on its target 16 GiB base machine, the budget should scale when machines have more available memory, and development testing on the current host may use up to 64 GiB. The earlier 10.5 GiB value was the selected profile, not the limit of this authority. Current T4 qualification uses M = 12 GiB (12,884,901,888 bytes), with the existing 0.9 M margin, 5% text-error allowance, 64 MiB stack reservation and numerical criteria.

The 64 GiB development allowance is separate. The original host's slot wrapper already implements that grant with four lock slots, a 52 GiB T3 start threshold, at least 30% system free memory and the running memory guard's 22% free-memory backstop. It does not select a 64 GiB product profile.

The owner adopted the shared-pool policy below on 2026-10-11: a nominal pool of 75% of physical RAM, a qualified 12 GiB per-invocation default and explicit larger qualified budgets on larger machines, subject to available headroom and ownership reservations. The desktop host implements the pool, leases, a capped worker process for each ordinary solve, and the ingress, result and custody bounds described below. The 12 GiB qualification is independent of that implementation.

## What the current bound means

`core/product_physics/src/retained_memory.rs` bounds a single retained invocation's requested heap, moving copies and reserved stack through caller completion. It qualifies the compiler/build identity, reviewed inputs and native type layouts before admission. The fixed domain remains 32 nodes, 32 members and at most three requested cases/combination owners. A higher M alone admits no larger model or additional owner.

The profile must fit below 0.9 M with room for a further 5% of its applicable text-allocation bound. Text pricing conservatively counts reachable string allocation volume as if retained together. These are accounting/qualification margins, not measured RSS or a guarantee covering the entire desktop process.

The 271 native layout atoms from C8 source `11cb56f3ea36046d6a79b8ae3377a7b91e3b4c52`, evaluated against its generated candidate, give dense E+R = 9,960,037,738 bytes and sparse E+R = 9,900,906,394 bytes, both at X1. Its text allowance is 234,402,248 bytes. At M = 12 GiB, floor(0.9 M) = 11,596,411,699 bytes; the remaining headroom after text is 1,401,971,713 bytes dense and 1,461,103,057 bytes sparse. All fourteen phase/mode combinations pass this arithmetic. The prior generated candidate is SHA256 `cde945bf31503311fecaf5ad7611669eb7f2fe3ff9cedec302d3eaf27bc5dfbc`; it failed the old 10.5 GiB text reserve and was not registered. Exact M12 registration and affected native checks establish the implementing head; this arithmetic does not register it. Each later epoch re-prices and re-registers its actual source under the same M, margin and reserve ([DEL-04-08 Design, retained-pricing-rules.md](../../DEL-04-08/Design/retained-pricing-rules.md)); the C8 figures above are not current headroom. After W1 member-load certification (#1398) the tightest phase, merged dense W4, has 113,188,985 bytes of headroom ([DEL-04-08 Design, w1-member-load-certification.md](../../DEL-04-08/Design/w1-member-load-certification.md)).

## Scaling options

| Option | Effect | Limitation |
|---|---|---|
| Scale each invocation's M with machine capacity | A proposed 75% default gives 12/24/48 GiB on 16/32/64 GiB machines. | Independent jobs can each claim the same memory. It needs a shared reservation system before parallel use. |
| Scale a shared pool, keep a qualified per-invocation default | The same pool sizes permit more concurrent qualified work; the selected per-invocation default is the authorized 12 GiB profile. Larger per-invocation budgets are explicit qualified choices within that pool. | Requires ownership accounting for workers, completed results and handoff copies. It does not enlarge the numerical domain. |

- PROPOSAL: Scale a shared Rust-owned pool first (owner-adopted design)
  - Evidence: `retained_memory.rs::{RegisteredProfile, build_status, cap_priced_maximum, admission_bound, admit}`; `apps/desktop/src-tauri/src/lib.rs::{execute_solve_job, publish_solve_outcome, poll_preview_mechanics_job}` and its job registry/thread creation.
  - Change: Use a nominal aggregate pool of floor(3 * physical_memory / 4), with checked integer arithmetic. After the current 12 GiB target passes qualification, use it as the per-invocation default. Offer a lower user budget and, after qualification, larger per-invocation choices within the pool. Require both an aggregate reservation and a fresh conservative host-headroom verdict before starting heavy work. Unknown capacity/headroom or pressure warning/critical conditions prevent a new adaptive admission.
  - Why: Matches the 16 GiB base target while allowing larger machines to run more work without assigning the same bytes to several jobs.
  - Risk: The numerical route available to an invocation can depend on configured budget, host load and competing reservations. Larger domain caps require their own qualification; a larger pool is not that qualification.
  - Status: APPLIED — governing policy selected; host pool and capped ordinary worker implemented

Ordinary execution (owner, 2026-10-12: "(c) Capped worker process"). Each ordinary solve runs in a local child worker process whose allocator is hard-capped at its pool lease. The lease comes from the same atomic pool admission with a fresh headroom verdict. Exceeding the cap ends that job with a typed resource refusal; it never falls back to another mode or route and never changes the solver mode or numerical predicates. The lease is released only after the child has exited and its result bytes are in the parent's leased custody. Parallel ordinary solves are admitted within the pool. The model family and numerical route are unchanged. A solve completes only if its counted need plus the process reserve, and its measured footprint, fit the budget, and each growth step is admitted against the host's headroom (Headroom counting, below). A growth step refused only with `headroom_insufficient` re-samples within the same window as the intake and result leases, so a solve is refused part-way with `worker_growth_refused` only when headroom stays short for that whole window.

As built, the desktop keeps the shared non-retained facade (B8 unchanged). `apps/desktop/src-tauri/src/memory_pool.rs` owns the aggregate ledger: the pool is floor(3C/4) by checked integer arithmetic, the per-invocation budget defaults to min(12 GiB, pool), a lower budget is accepted, a larger one up to the pool is accepted (see Larger budgets below), and a pool above 3/4 needs an acknowledgement that clears only that refusal. One lock covers the reservation and a fresh host sample; unknown capacity or headroom, a stale sample, pressure other than normal or headroom below the request plus the outstanding unrealized reservations refuses with a typed `ResourceRefusal`. At every admission each live worker lease is re-measured, and the smaller of its resident size and footprint (still an upper bound on its private resident memory) counts as realized, up to the lease; every other lease counts in full. Leases are RAII, released once, also while unwinding.

The worker (`solve_worker.rs`, `worker_alloc.rs`) is the app binary started with `--swbpipe-solve-worker` before any Tauri setup; it talks to the parent over private pipes and is local-only. Its global allocator counts each allocation at a resident-memory envelope: a size class (the next power of two, at least 16 bytes) up to 32 KiB, whole 16 KiB pages above. The heap cap is the grant less a 64 MiB process reserve; a release worker's whole footprint measured at most about 8.1 MB. The worker closes inherited descriptors before reading its request. A fixed grant at the budget would need 12 GiB of headroom per solve, which a 16 GiB machine rarely has, so the grant starts from the intake size and grows on demand. Each step is an atomic pool admission with a fresh headroom verdict and stops at the budget. A step first asks to double, then falls back to the minimal need; it also grows to cover the child's measured footprint. When the minimal need is refused only with `headroom_insufficient` (the double may have been refused for any reason), the step re-samples: every 50 ms, or sooner on a release, it takes a fresh sample and tries the double and then the minimal need again, under one pool lock per attempt, and starts no attempt after 2 s. It is admitted at the first attempt that passes the unchanged rule. A step the child asked for (an exchange) leaves the child blocked in its allocator while the step waits, so it allocates nothing further. A step the parent starts because the measured footprint exceeds the grant (a poll) stops the child with SIGSTOP for the wait and continues it with SIGCONT once admitted (Agent 0, 2026-10-26, option (a) of the poll-path choice). The child may still grow between the poll's measurement and the stop, so its footprint is measured again between attempts, and every attempt's double and minimal need follow the largest footprint measured: an admitted step covers what the stopped child holds. The excess, frozen once the child is stopped, stays unreserved for at most the 2 s window; before, the child kept running for one poll interval plus the kill time. Cancellation and session reset end a waiting step and SIGKILL the child, stopped or not. The worker runs in its own process group, so if the app dies while the worker is stopped, the group is orphaned and the kernel sends it SIGHUP and SIGCONT, which end it. A running worker ends itself when its parent exits: a watchdog thread started before its allocator counts waits on the parent's exit (kqueue `NOTE_EXIT`, with a 100 ms `getppid` poll as fallback) and calls `_exit`. Signals sent to the app's process group, such as a terminal interrupt in development or the native smoke's group kill, therefore no longer reach the worker directly; it ends through these two paths instead. Stopped time is not charged against any timeout or staleness check of the job. A solve whose counted need exceeds the budget ends `worker_cap_exceeded`, one whose footprint exceeds the budget ends `worker_footprint_exceeded`, and a minimal step that is still refused ends `worker_growth_refused`: at once for any refusal other than `headroom_insufficient`, otherwise when the window has elapsed. The child exits without allocating. The parent measures the footprint at each exchange, every 100 ms, and at the result (the lifetime maximum). Memory outside the counted heap can therefore exceed the lease or the budget for at most one polling interval plus the time to kill the child, and, while a poll step waits with the child stopped, exceed the lease for at most the 2 s window. A result is accepted only if it fits the child's grant, and it is leased in the parent while the grant is still held. Cancellation and session reset kill the child; leases release after it is reaped. Crashes and protocol violations fail the job. At most one worker per available CPU runs at a time; further admitted jobs wait in the queue.

## Platform evidence and qualification

Apple documents [`ProcessInfo.physicalMemory`](https://developer.apple.com/documentation/foundation/processinfo/physicalmemory) as physical capacity in bytes and [`DispatchSourceMemoryPressure`](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure) as a pressure-state monitor. Neither is an available-byte guarantee. Apple's [XNU memory-status description](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md) distinguishes pressure-related available memory, including compressed/reclaimable pages, from fully reclaimable memory. Do not equate all such pages with immediately free capacity. A Rust native bridge and conservative byte-headroom policy need target-specific verification before adaptive admission is enabled. `host_memory.rs` reads `hw.memsize` as capacity, `kern.memorystatus_vm_pressure_level` as the pressure state (1/2/4; anything else unknown) and the headroom below. It is an instantaneous host reading, not a guarantee under competing workloads. The pure core takes `RetainedByteLimit` and reports `retained_profile()` (identity, qualified limit, required bytes per mode); a limit above the qualified M is refused as `Unqualified`, never clamped.


### Headroom counting

Ruling (owner, 2026-10-26): "My two decisions are to approve your recommendations in both cases. Proceed accordingly." For headroom, the recommendation it approves is:
- B: headroom also counts memory macOS can reclaim cheaply, file-backed cache pages and purgeable pages. Anonymous (unsaved app) memory is not counted. Every other safeguard stays unchanged: the 12 GiB per-invocation budget, the 75% pool, the outstanding-reservation rule, residency credit, and refusal on any memory pressure other than normal.
- With C's re-check: worker growth steps, and the custody grow at take, re-sample on `headroom_insufficient` within the same 2 s window that the intake and result leases use, rather than refusing on a single sample.

The free-queue rule it replaces was headroom = (free_count − speculative_count − vm.vm_page_free_target)⁺ × page size. On a loaded 128 GiB development host at normal pressure, it counted 53 MB when a 68 MB from-blank solve was refused in the native smoke (2026-10-25). Twenty samples over 10 s on 2026-10-26 found a free queue of 57–366 MiB beside about 40 GB of inactive pages and 0.4–1.3 GB of purgeable pages, with `vm.vm_page_free_target` at 4,000 pages (62.5 MiB).

The rule counts, in pages:
- F, the free list: `vm.page_free_count`, the kernel's free queue without the speculative pages (`host_statistics64`'s `free_count` is this plus the speculative pages);
- E, the pageable file-backed pages: `vm.page_pageable_external_count`, the pages of file-backed (external) objects on the active, inactive, speculative and cleaned queues, so wired file pages are excluded;
- P, the purgeable pages: `vm.page_purgeable_count`, the resident pages of volatile purgeable objects that are not wired (wired ones are `vm.page_purgeable_wired_count`). Their owner has declared their contents discardable, and the kernel empties them rather than compressing or swapping them. They are the only anonymous memory counted, because the ruling names them.

headroom = (F + E + P − T)⁺ × page size, with T = `vm.vm_page_free_target`, the kernel's own reserve, subtracted once from the total. The sum and the product are checked. No page is counted twice. A free page belongs to no object, so it is in neither E nor P. Speculative pages are excluded from F, so a file-backed speculative page is counted once, in E, and an anonymous one not at all. Purgeable objects are anonymous (internal) memory, never file-backed, so E and P are disjoint. Inactive pages are not counted as such: the file-backed ones are already in E and the anonymous ones are never counted. Anonymous, compressed and compressor-occupied pages, wired pages and `external_page_count`'s wired file pages are never counted. For counters read at the same moment the new headroom is never below the free-queue rule's, because E and P are not negative; the live F can still read below the cached `host_statistics64` free count the fallback uses.

All three are live sysctls, read one after another. `host_statistics64` is not used for them: for an unprivileged caller XNU may answer it from a cache up to 1 s old (`osfmk/kern/host.c`), and a page moving from a cached F or P into a live E could then be counted twice over that second. The rule fails closed to the free-queue rule when any of the three cannot be read, or when (F + E + P) × page size exceeds `hw.memsize`, an implausible reading. That rule is (free_count − speculative_count − T)⁺ × page size from `host_statistics64(HOST_VM_INFO64)`, which must succeed with the full 38-word count, as before 2026-10-26. A failed `host_statistics64`, page size or `vm.vm_page_free_target` read still leaves headroom unknown, which refuses admission as before.

Changed with this rule: `host_memory.rs`'s module comment (its Headroom bullet) and `reclaimable_headroom`, which replaces `conservative_headroom`; and `memory_pool.rs`'s module comment (its Re-sampling paragraph, whose last sentence said worker growth and the custody grow did not re-sample).

The three counters are read in three system calls, not atomically, so a page moving between queues in the microseconds between them can be counted twice or not at all. Every admission still takes a fresh sample under the pool lock, and the outstanding-reservation rule, residency credit and the pressure check are unchanged.

Qualify the authorized 12 GiB target first, reusing unchanged numerical evidence and native layout atoms while checking all phases, registration bindings and affected resource refusals. Adaptive implementation then needs targeted checks for simultaneous acquisition races, insufficient/unknown/stale headroom, pressure transitions, result retention and poll-copy overlap, cancellation, panic and failed starts, plus independent review. Larger per-invocation thresholds must fit the qualified bound and the pool; larger input tiers must re-price the actual domain and native layouts. The same compiled product identity can share a deterministic policy version, but the chosen budget and typed resource refusal must be recoverable in the run's existing result/provenance interface. Public format changes, if needed, use one current format rather than compatibility variants.

The supported-machine statement should distinguish a 16 GiB base target from a guarantee under arbitrary competing workloads. Show the selected per-invocation budget, aggregate pool, queued work and reason for a resource refusal. Warn before a user requests a pool above the recommended machine fraction; acknowledgement cannot bypass a known insufficient-headroom or qualification refusal. A changing host load may change retained availability. Ordinary fallback after a method refusal remains possible only within its own admitted resource lease; it must not change the numerical predicates or fabricate a retained result. Release identity selection remains with B7's qualified build and the owner's release act.
