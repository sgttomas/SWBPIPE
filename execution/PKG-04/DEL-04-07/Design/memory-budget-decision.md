# Memory budget and machine scaling

## Governing direction

The owner clarified on 2026-10-11: the product may use up to 12 GiB on its target 16 GiB base machine, the budget should scale when machines have more available memory, and development testing on the current host may use up to 64 GiB. The earlier 10.5 GiB value was the selected profile, not the limit of this authority. Current T4 qualification uses M = 12 GiB (12,884,901,888 bytes), with the existing 0.9 M margin, 5% text-error allowance, 64 MiB stack reservation and numerical criteria.

The 64 GiB development allowance is separate. The original host's slot wrapper already implements that grant with four lock slots, a 52 GiB T3 start threshold, at least 30% system free memory and the running memory guard's 22% free-memory backstop. It does not select a 64 GiB product profile.

The owner adopted the shared-pool policy below on 2026-10-11: a nominal pool of 75% of physical RAM, a qualified 12 GiB per-invocation default and explicit larger qualified budgets on larger machines, subject to available headroom and ownership reservations. The desktop host implements the pool, leases, a capped worker process for each ordinary solve, and the ingress, result and custody bounds described below. The 12 GiB qualification is independent of that implementation.

## What the current bound means

`core/product_physics/src/retained_memory.rs` bounds a single retained invocation's requested heap, moving copies and reserved stack through caller completion. It qualifies the compiler/build identity, reviewed inputs and native type layouts before admission. The fixed domain remains 32 nodes, 32 members and at most three requested cases/combination owners. A higher M alone admits no larger model or additional owner.

The profile must fit below 0.9 M with room for a further 5% of its applicable text-allocation bound. Text pricing conservatively counts reachable string allocation volume as if retained together. These are accounting/qualification margins, not measured RSS or a guarantee covering the entire desktop process.

The 271 native layout atoms from C8 source `11cb56f3ea36046d6a79b8ae3377a7b91e3b4c52`, evaluated against its generated candidate, give dense E+R = 9,960,037,738 bytes and sparse E+R = 9,900,906,394 bytes, both at X1. Its text allowance is 234,402,248 bytes. At M = 12 GiB, floor(0.9 M) = 11,596,411,699 bytes; the remaining headroom after text is 1,401,971,713 bytes dense and 1,461,103,057 bytes sparse. All fourteen phase/mode combinations pass this arithmetic. The prior generated candidate is SHA256 `cde945bf31503311fecaf5ad7611669eb7f2fe3ff9cedec302d3eaf27bc5dfbc`; it failed the old 10.5 GiB text reserve and was not registered. Exact M12 registration and affected native checks establish the implementing head; this arithmetic does not register it. Each later epoch re-prices and re-registers its actual source under the same M, margin and reserve ([DEL-04-08 Design, retained-pricing-rules.md](../../DEL-04-08/Design/retained-pricing-rules.md)); the C8 figures above are not current headroom. After W1 member-load certification (#1398) the tightest phase, merged dense W4, has 113,188,985 bytes of headroom ([DEL-04-08 Design, w1-member-load-certification.md](../../DEL-04-08/Design/w1-member-load-certification.md)).

## Scaling options

| Option | Effect | Limitation |
|---|---|---|
| Scale each invocation's M with machine capacity | A proposed 75% default gives 12/24/48 GiB on 16/32/64 GiB machines. | Independent jobs can each claim the same memory. It needs a shared reservation system before parallel use. |
| Scale a shared pool, keep a qualified per-invocation default | The same pool sizes permit more concurrent qualified work; the selected per-invocation default is the authorized 12 GiB profile. Larger per-invocation budgets are explicit qualified choices within that pool. | Requires ownership accounting for workers, completed results and handoff copies. It does not enlarge the numerical domain. |

- PROPOSAL: Scale a shared Rust-owned pool first (owner-adopted design)
  - Evidence: `retained_memory.rs::{RegisteredProfile, build_status, cap_priced_maximum, admission_bound, admit}`; `apps/desktop/src-tauri/src/lib.rs::{execute_solve_job, publish_solve_outcome, poll_preview_mechanics_job}` and its job registry/thread creation.
  - Change: Use a nominal aggregate pool of floor(3 * physical_memory / 4), with checked integer arithmetic. After the current 12 GiB target passes qualification, use it as the per-invocation default. Offer a lower user budget and, after qualification, larger per-invocation choices within the pool. Require both an aggregate reservation and a fresh conservative host-headroom verdict before starting heavy work. Unknown capacity/headroom or pressure warning/critical conditions prevent a new adaptive admission.
  - Why: Matches the 16 GiB base target while allowing larger machines to run more work without assigning the same bytes to several jobs.
  - Risk: The numerical route available to an invocation can depend on configured budget, host load and competing reservations. Larger domain caps require their own qualification; a larger pool is not that qualification.
  - Status: APPLIED — governing policy selected; host pool and capped ordinary worker implemented

Ordinary execution (owner, 2026-10-12: "(c) Capped worker process"). Each ordinary solve runs in a local child worker process whose allocator is hard-capped at its pool lease. The lease comes from the same atomic pool admission with a fresh headroom verdict. Exceeding the cap ends that job with a typed resource refusal; it never falls back to another mode or route and never changes the solver mode or numerical predicates. The lease is released only after the child has exited and its result bytes are in the parent's leased custody. Parallel ordinary solves are admitted within the pool. The model family and numerical route are unchanged. A solve completes only if its counted need plus the process reserve, and its measured footprint, fit the budget, and each growth step is admitted against free headroom. On a loaded machine, where macOS's free queue may be a few hundred MB, a solve that previously ran can therefore be refused part-way with `worker_growth_refused`.

As built, the desktop keeps the shared non-retained facade (B8 unchanged). `apps/desktop/src-tauri/src/memory_pool.rs` owns the aggregate ledger: the pool is floor(3C/4) by checked integer arithmetic, the per-invocation budget defaults to min(12 GiB, pool), a lower budget is accepted, a larger one up to the pool is accepted (see Larger budgets below), and a pool above 3/4 needs an acknowledgement that clears only that refusal. One lock covers the reservation and a fresh host sample; unknown capacity or headroom, a stale sample, pressure other than normal or headroom below the request plus the outstanding unrealized reservations refuses with a typed `ResourceRefusal`. At every admission each live worker lease is re-measured, and the smaller of its resident size and footprint (still an upper bound on its private resident memory) counts as realized, up to the lease; every other lease counts in full. Leases are RAII, released once, also while unwinding.

The worker (`solve_worker.rs`, `worker_alloc.rs`) is the app binary started with `--swbpipe-solve-worker` before any Tauri setup; it talks to the parent over private pipes and is local-only. Its global allocator counts each allocation at a resident-memory envelope: a size class (the next power of two, at least 16 bytes) up to 32 KiB, whole 16 KiB pages above. The heap cap is the grant less a 64 MiB process reserve; a release worker's whole footprint measured at most about 8.1 MB. The worker closes inherited descriptors before reading its request. A fixed grant at the budget would need 12 GiB of free-queue headroom per solve, which a 16 GiB machine rarely has, so the grant starts from the intake size and grows on demand. Each step is an atomic pool admission with a fresh headroom verdict and stops at the budget. A step first asks to double, then falls back to the minimal need; it also grows to cover the child's measured footprint. A solve whose counted need exceeds the budget ends `worker_cap_exceeded`, one whose footprint exceeds the budget ends `worker_footprint_exceeded`, and a refused minimal step ends `worker_growth_refused`; the child exits without allocating. The parent measures the footprint at each exchange, every 100 ms, and at the result (the lifetime maximum). Memory outside the counted heap can therefore exceed the lease or the budget for at most one polling interval plus the time to kill the child. A result is accepted only if it fits the child's grant, and it is leased in the parent while the grant is still held. Cancellation and session reset kill the child; leases release after it is reaped. Crashes and protocol violations fail the job. At most one worker per available CPU runs at a time; further admitted jobs wait in the queue.

`ingress.rs` prescans the raw request bytes without allocating, validating them as serde_json would. It also prices their `Value` materialization (objects by B-tree node count, arrays by doubling capacity, exact-length strings, scratch and one reallocation, each requested allocation at the next power of two of at least 16 bytes), which sizes the worker's starting grant; the parent itself keeps only the raw bytes. `start_preview_mechanics_job` takes a raw body and refuses a JSON body; wry has already buffered the body, and a postMessage IPC fallback would materialize a `Value` first.

Model-sized interactive commands get the same ingress discipline: render, agent proposal, the operation and batch validate/apply commands, the self-weight plan, display conversion, project create/save, rule-pack validate/checksum/save, rule checks, library import/save, report package save and result save. Each takes a raw `args-json-v1` body (`command_ingress.rs`). It is prescanned and leased before it is parsed, and a JSON body is refused. The lease is the raw-body envelope plus the materialization bound plus a 4 KiB error allowance, and it is held until the command returns. Arguments are moved out of the one parsed value with bounded decode errors. The report-package request text, which the command parses itself, grows the lease by its parse, once more by its parse bound for the command's working memory, once more by the containers of its opaque `Value` regions, which decoding rebuilds, and by four times the containers of its typed-vector regions (Report-package request pricing, below). These leases use an interactive admission class: known capacity, the per-invocation budget, the pool and a fresh headroom verdict, but not the pressure state, so edits and saves are not refused at every macOS pressure warning. Their headroom verdict counts retained results, and half of each custody lease (the webview's copy), as already written. Even so, on a loaded machine an edit or save made while a large solve holds an unrealized grant can be refused with `headroom_insufficient`. The free queue itself swings between about zero and gigabytes within a second on a loaded Mac at normal pressure, because the pageout daemon keeps it near `vm.vm_page_free_target`. The completeness map's native run (2026-10-23) had a 16.56 MiB result save refused at 6.44 MiB headroom. An instrumented native build on the same host the same day (PR #1547) had a 4 KiB solve intake and a 215 KiB project save refused at zero headroom. Sampling that host at 20 Hz found refusal runs of at most 0.8 s at a 16.56 MiB request. A solve's intake lease and a finished solve's result lease, both off the main thread, refused only with `headroom_insufficient` therefore take further fresh samples every 50 ms, or sooner on a release or a cancellation request, and start no attempt after 2 s. They are admitted at the first sample that passes the unchanged rule. A cancellation during the result lease's wait ends the job as cancelled. Interactive admissions still refuse at once, because most interactive commands run on the main thread. The desktop re-sends a command refused at admission with `headroom_insufficient` every 100 ms, starting no send after 2 s (`nativeIngress.ts`). The refusal precedes argument parsing, so a re-send repeats none of the command's work, only the IPC transfer and the prescan. The pool status's `last_refusal` keeps the latest refused send even when a later send is admitted; a re-sample in the host records only a refusal that stands. Any other refusal, and `headroom_insufficient` after the window, stands. Off macOS, capacity is unknown and these commands are refused like solves. Solves and worker growth keep the full adaptive rule. A command's own working memory and its response serialization run under the held lease but are not separately bounded. The report-package save's lease carries a working-memory term in proportion to its request's size (below), which covers its measured working memory but does not prove it bounded in general.

Report-package request pricing. `save_report_package` moves its arguments, then grows its lease before it parses the request, model and input-manifest texts (`report_package_save::parse_lease_bytes`). The prescan of the request text also assigns each priced allocation to a region of the typed request `report_package::wire::ReportPackageRequest`, by the path the decoder follows. The region table is static and mirrors the wire types. A struct is matched by field name in an object, after the key's escapes are decoded as the parser decodes them, or by field position in an array. The opaque regions are the value at `report` and the elements of `result_documents`, `source_results` and `state_comparison_handoff_records`. The typed-vector regions are the values at the six `Vec` fields, without those opaque elements: the three arrays just named, and `source_basis_refs`, `audit_manifest.rule_pack_refs` and `audit_manifest.assets` with their elements. Everything else, including keys the decoder ignores, is in neither region. Regions follow from these paths alone; no member of the request names or marks one.

With M the request text's materialization bound, C_V the priced containers (array buffers and object nodes) of the opaque regions and C_T those of the typed-vector regions, the growth is M + W M + C_V + 4 C_T, plus the canonical re-serialization (two envelopes of the text's length) and the 4 KiB error allowance. W is the working-memory factor `REPORT_PACKAGE_WORKING_MEMORY_FACTOR` (`command_ingress.rs`), which is 1, so the growth is M + M + C_V + 4 C_T. The model and input-manifest texts are priced as before: M plus their re-serialization and the allowance. The bound holds for these reasons. The parse and the binding check's re-serialization stay within M and their allowance, as before. Decoding moves every string and key, so it allocates only containers and typed vectors. A rebuilt opaque container has its source's entry count and grows as the parser's did: an array to the same doubling capacity, an object by insertion into at most floor(n/5) + 1 nodes. The rebuilt values therefore fit in C_V even while every source container is still live. Only one growth transient is live at a time, and it fits the parse's array-transient allowance in M, which is free once the parse has returned. Struct and scalar fields outside the vectors are inline and allocate nothing. A typed vector, with its growth transient, is at most four times the priced containers of its own region; `report_package_vec_expansion_bounds_every_vector_type` computes 2.667 for the worst element types and 1.5 for `Vec<Value>`. Each priced container is in at most one region, so C_V + C_T <= M, and for any W <= 1 the growth never exceeds the former (2 + 4) M. Content placed in another region is still priced for what the decoder does with it: the decoder builds vectors only at the typed-vector paths, so vector-shaped content in an opaque region is rebuilt as a `Value` within C_V, and opaque-shaped content inside a typed vector's element is priced at four times. The screening walk over the parsed request and model and the shared producer's assembly of the members and the container run afterwards under the held lease, as the command's working memory. The W M term prices it in proportion to the request's size. That is a provision, not a computed bound: the whole-command checks below measure it for two requests, and it is not proven bounded for every request. Ruling: owner, 2026-10-25, "Both decisions I approve your recommended options." (recommended option: the +M working-memory term, W = 1; the alternative, W = 0, left the working memory unpriced).

The tests keep `report_package_vec_expansion_bounds_every_vector_type`, `report_package_shapes_match_the_wire_types` and `report_package_text_parse_stays_within_its_priced_growth`, with its cases and its assertion unchanged against the new growth. They add: the region table checked against the wire types' field names, positions and kinds; a region prescan that allocates nothing and whose regions and fixed allowances sum to M; region cases for escaped field names, positional structs, duplicate and unknown keys and `null` options; counting-allocator cases with vector-shaped content in the opaque regions, opaque-shaped content in typed-vector elements, positional structs, escaped field names, duplicate keys and numbers whose canonical form outgrows their text; a check that for W <= 1 the growth never exceeds the former rule; and a whole-command counting-allocator check, from the raw body through admission and a cancelled dialog, whose peak with the buffered body is within the whole lease. That last check runs on the committed witness request as a normal test, and on the demo's request (the bundled demo solved in dense scrutiny, as the native smoke saves it) as an ignored test. The demo's request is about 7 MB, so it is not committed: the desktop helper `src/test-support/demoReportPackageRequest.ts` builds it with the session's own builders from `invented_demo_model.json` and its committed dense result, and its test writes the raw args body to the path in `OPENPIPESTRESS_DEMO_REPORT_PACKAGE_REQUEST`, which the ignored test reads (`lib.rs` `report_package_save_demo_request_peak_is_within_its_lease` documents the commands). Larger budgets. The ordinary route runs in the capped worker, so for that route, "qualified" means the worker's enforced cap. A per-invocation budget above 12 GiB, up to the pool, admits larger ordinary solves without a separate numerical qualification. The route, model family and predicates are unchanged, and the worker's grant, frame and lease arithmetic are checked up to u64 limits. A 96 GiB budget on an injected 1 TiB host runs a real worker solve with identical bytes. The default stays 12 GiB. No larger retained budget is offered. The retained route's D1 domain is fixed at 32 nodes, 32 members and three cases, whose required bytes (about 10 GB with R) already fit M = 12 GiB, so a larger M admits nothing new. A larger retained domain would need its own pricing and registration. The desktop does not use the retained route (B8).

`solve_jobs.rs` bounds queued jobs (4), retained untaken results (4, refused before reserving and again at publication) and delivered undisposed results (4). Polls never carry the result; `take_preview_mechanics_job_result` moves the bytes out after growing the lease to twice their allocation for the handoff copy, and the webview's `dispose_preview_mechanics_result` releases it. At session start `dispose_all_preview_mechanics_results` releases every retained or delivered result and abandons queued or running jobs. The per-invocation budget bounds intake and each worker. Results and custody are bounded by the pool, headroom and count limits; the custody bound counts delivered bytes and does not measure webview heap.

Refusals are typed and never change the solver mode. Intake, queue and early retention refusals come before a solve, and worker refusals end it; a result-lease or retention refusal at publication drops a finished result, and a custody or headroom refusal at take keeps it retained. The rule check consumes a job's result and does not solve. The packaged CLI self-test still solves in its own process outside the pool.

Every refusal point below, except the queue wait, which is not a refusal, ends the session's solve job `refused`, with job summary `state=refused; …; result_rows=0`, the panel line "Refused by the native memory pool: … No result was published." and `refusal=<code>` in the Memory line. Run record (owner, 2026-10-12: "Keep them out"). The persisted `analysis_run` 0.3 record stays machine-independent. The budget, pool, route pricing, intake bytes, worker grants and any typed refusal are kept in the run's solve-job audit record and its exported Solve job JSON. The pool is per process; another app instance keeps its own ledger.

The pure Rust core should consume an immutable byte limit and expose its qualified required bytes/profile identity; it should not discover the machine or silently rewrite caps. Keep budget policy outside the model payload. The native host supplies capacity/headroom and owns the aggregate lease. Integrate through the existing job/service boundary; retained desktop activation B8 remains owner-held, and this study does not switch the desktop onto the retained facade. Distinguish an ordinary retained-method refusal from an aggregate resource refusal: the current dispatcher falls back to ordinary execution after retained refusal, so pool/headroom refusal must be handled before that dispatcher. It queues or returns a typed resource-unavailable result; it must not escape the pool through an unbounded ordinary fallback or silently change the requested solver mode.

An ordinary-route lease needs a whole-invocation bound over its existing supported domain. The retained D1 bound cannot price requests outside D1 or impose its 32-node cap on ordinary execution. Existing dense/sparse 6 GiB checks are component estimates, not that whole-product proof. Adaptive integration must preserve current ordinary capability while establishing its input, solver, output and handoff bounds; it cannot claim safety by silently shrinking the supported model family.

## Platform evidence and qualification

Apple documents [`ProcessInfo.physicalMemory`](https://developer.apple.com/documentation/foundation/processinfo/physicalmemory) as physical capacity in bytes and [`DispatchSourceMemoryPressure`](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure) as a pressure-state monitor. Neither is an available-byte guarantee. Apple's [XNU memory-status description](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md) distinguishes pressure-related available memory, including compressed/reclaimable pages, from fully reclaimable memory. Do not equate all such pages with immediately free capacity. A Rust native bridge and conservative byte-headroom policy need target-specific verification before adaptive admission is enabled. `host_memory.rs` reads `hw.memsize` as capacity, `kern.memorystatus_vm_pressure_level` as the pressure state (1/2/4; anything else unknown) and, from `host_statistics64`, headroom = (free_count − speculative_count − vm.vm_page_free_target) × page size. That counts only the free queue: speculative, purgeable, inactive, file-cache and compressor pages are excluded. It is an instantaneous host reading, not a guarantee under competing workloads. The pure core takes `RetainedByteLimit` and reports `retained_profile()` (identity, qualified limit, required bytes per mode); a limit above the qualified M is refused as `Unqualified`, never clamped.

Qualify the authorized 12 GiB target first, reusing unchanged numerical evidence and native layout atoms while checking all phases, registration bindings and affected resource refusals. Adaptive implementation then needs targeted checks for simultaneous acquisition races, insufficient/unknown/stale headroom, pressure transitions, result retention and poll-copy overlap, cancellation, panic and failed starts, plus independent review. Larger per-invocation thresholds must fit the qualified bound and the pool; larger input tiers must re-price the actual domain and native layouts. The same compiled product identity can share a deterministic policy version, but the chosen budget and typed resource refusal must be recoverable in the run's existing result/provenance interface. Public format changes, if needed, use one current format rather than compatibility variants.

The supported-machine statement should distinguish a 16 GiB base target from a guarantee under arbitrary competing workloads. Show the selected per-invocation budget, aggregate pool, queued work and reason for a resource refusal. Warn before a user requests a pool above the recommended machine fraction; acknowledgement cannot bypass a known insufficient-headroom or qualification refusal. A changing host load may change retained availability. Ordinary fallback after a method refusal remains possible only within its own admitted resource lease; it must not change the numerical predicates or fabricate a retained result. Release identity selection remains with B7's qualified build and the owner's release act.

MISSING: none for the adopted design. Documented residuals remain: the solve intake's re-sample runs inline in its async command and can hold one async-runtime worker for up to 2 s; worker growth and the custody grow at take do not re-sample, so a dip in the free queue can still end a growing solve (`worker_growth_refused`) or defer a take; a free queue that stays low for longer than the 2 s window still refuses saves, edits and solve intakes; wry buffers raw bodies before any check, and a postMessage IPC fallback would materialize a value first; webview custody counts delivered bytes, not webview heap; uncounted worker footprint can exceed its lease for one 100 ms poll interval plus the kill time; command working memory and responses are not separately bounded, except that the report-package save's lease carries a working-memory term in proportion to its request's size, measured for the witness and demo requests but not proven bounded in general (instances in the desktop's model-state and analysis-run history, W-12 S2: the run-read response and its IPC copies, SQLite's own allocations, Record Run's transient record copies, a new state's record value, library and SQLite messages built before they are capped, and length-counter scratch; accepted as v0.1 residuals by the owner on 2026-10-24, with the run-read IPC copies to be measured natively in development testing; DEL-14-01 Design `desktop-states-runs-comparison.md` §3); the pool is per process; the packaged CLI self-test solves outside the pool.

NEEDS_HUMAN_RULING: none for the selected policy, the capped worker or the run record. A change to the budget model, numerical domain or other reserved condition requires the corresponding owner decision.

DEPENDENCY_NOTES: parallel ordinary solves are admitted only within the pool, by capped workers; larger numerical domains need their own qualification, and B8 retained desktop activation remains owner-held.
