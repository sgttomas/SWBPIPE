# Memory budget and machine scaling

## Governing direction

The owner clarified on 2026-10-11: the product may use up to 12 GiB on its target 16 GiB base machine, the budget should scale when machines have more available memory, and development testing on the current host may use up to 64 GiB. The earlier 10.5 GiB value was the selected profile, not the limit of this authority. Current T4 qualification uses M = 12 GiB (12,884,901,888 bytes), with the existing 0.9 M margin, 5% text-error allowance, 64 MiB stack reservation and numerical criteria.

The 64 GiB development allowance is separate. The original host's slot wrapper already implements that grant with four lock slots, a 52 GiB T3 start threshold, at least 30% system free memory and the running memory guard's 22% free-memory backstop. It does not select a 64 GiB product profile.

The owner adopted the shared-pool policy below on 2026-10-11: a nominal pool of 75% of physical RAM, a qualified 12 GiB per-invocation default and explicit larger qualified budgets on larger machines, subject to available headroom and ownership reservations. The desktop host implements the pool, leases and ingress, result and custody bounds described below; the ordinary solve stage is not yet priced. The 12 GiB qualification is independent of that implementation.

## What the current bound means

`core/product_physics/src/retained_memory.rs` bounds a single retained invocation's requested heap, moving copies and reserved stack through caller completion. It qualifies the compiler/build identity, reviewed inputs and native type layouts before admission. The fixed domain remains 32 nodes, 32 members and at most three requested cases/combination owners. A higher M alone admits no larger model or additional owner.

The profile must fit below 0.9 M with room for a further 5% of its applicable text-allocation bound. Text pricing conservatively counts reachable string allocation volume as if retained together. These are accounting/qualification margins, not measured RSS or a guarantee covering the entire desktop process.

The 271 native layout atoms from C8 source `11cb56f3ea36046d6a79b8ae3377a7b91e3b4c52`, evaluated against its generated candidate, give dense E+R = 9,960,037,738 bytes and sparse E+R = 9,900,906,394 bytes, both at X1. Its text allowance is 234,402,248 bytes. At M = 12 GiB, floor(0.9 M) = 11,596,411,699 bytes; the remaining headroom after text is 1,401,971,713 bytes dense and 1,461,103,057 bytes sparse. All fourteen phase/mode combinations pass this arithmetic. The prior generated candidate is SHA256 `cde945bf31503311fecaf5ad7611669eb7f2fe3ff9cedec302d3eaf27bc5dfbc`; it failed the old 10.5 GiB text reserve and was not registered. Exact M12 registration and affected native checks establish the implementing head; this arithmetic does not register it.

## Scaling options

| Option | Effect | Limitation |
|---|---|---|
| Scale each invocation's M with machine capacity | A proposed 75% default gives 12/24/48 GiB on 16/32/64 GiB machines. | Independent jobs can each claim the same memory. It needs a shared reservation system before parallel use. |
| Scale a shared pool, keep a qualified per-invocation default | The same pool sizes permit more concurrent qualified work; the selected per-invocation default is the authorized 12 GiB profile. Larger per-invocation budgets are explicit qualified choices within that pool. | Requires ownership accounting for workers, completed results and handoff copies. It does not enlarge the numerical domain. |

- PROPOSAL: Scale a shared Rust-owned pool first (owner-adopted design)
  - Evidence: `retained_memory.rs::{RegisteredProfile, build_status, cap_priced_maximum, admission_bound, admit}`; `apps/desktop/src-tauri/src/lib.rs::{execute_solve_job, publish_solve_outcome, poll_preview_mechanics_job}` and its job registry/thread creation.
  - Change: Use a nominal aggregate pool of floor(3 * physical_memory / 4), with checked integer arithmetic. After the current 12 GiB target passes qualification, use it as the per-invocation default. Offer a lower user budget and, after qualification, larger per-invocation choices within the pool. Require both an aggregate reservation and a fresh conservative host-headroom verdict before starting heavy work. Unknown capacity/headroom or pressure warning/critical conditions prevent a new adaptive admission.
  - Why: Matches the 16 GiB base target while allowing larger machines to run more work without assigning the same bytes to several jobs.
  - Risk: The numerical route available to an invocation can depend on configured budget, host load and competing reservations. Larger domain caps require their own qualification; a larger pool is not that qualification.
  - Status: APPLIED — governing policy selected; host pool implemented except the ordinary solve stage's byte bound

As built, the desktop keeps the shared non-retained facade (B8 unchanged). `apps/desktop/src-tauri/src/memory_pool.rs` owns the aggregate ledger: the pool is floor(3C/4) by checked integer arithmetic, the per-invocation budget defaults to min(12 GiB, pool), a lower budget is accepted, a larger one is refused as unqualified, and a pool above 3/4 needs an acknowledgement that clears only that refusal. One lock covers the reservation and a fresh host sample; unknown capacity or headroom, a stale sample, pressure other than normal or headroom below the request plus all outstanding reservations (deliberately double-counted) refuses with a typed `ResourceRefusal`. Leases are RAII (released once, also while unwinding) and move from ingress to the worker, the result record and webview custody. `ingress.rs` prescans the raw request bytes without allocating, validating them as serde_json would and pricing their `Value` materialization (objects by B-tree node count, arrays by doubling capacity, exact-length strings, scratch and one reallocation, each allocation at the next power of two of at least 16 bytes, checked against `malloc_size` on macOS). `start_preview_mechanics_job` takes a raw body, reserves that bound before parsing and refuses a JSON body; wry has already buffered the body, and a postMessage IPC fallback would materialize a `Value` first. `solve_jobs.rs` bounds queued jobs (4), retained untaken results (4, refused before reserving ingress and again at publication) and delivered undisposed results (4). Polls never carry the result; `take_preview_mechanics_job_result` moves the bytes out after growing the lease to twice their allocation for the handoff copy, and the webview's `dispose_preview_mechanics_result` (or `dispose_all_preview_mechanics_results` at session start) releases it. That custody bound counts delivered bytes; it does not measure webview heap. Cancellation and panics release owners only when the worker drops them; a failed thread start drops its lease. Refusals are typed, are handled before any solve starts and never change the solver mode; the rule check consumes a job's result and does not solve. The run's `analysis_run` 0.3 record carries `execution_resources` (budget, pool, route pricing, ingress bytes) and the solve-job audit export carries a refusal. The ordinary solve stage has no whole-invocation bound, so it reserves no bytes: one unpriced ordinary solve runs at a time, admitted on known capacity, a fresh sample, known headroom and normal pressure, and it is reported as `ordinary_unpriced`. The pool is per process; another app instance keeps its own ledger.

The pure Rust core should consume an immutable byte limit and expose its qualified required bytes/profile identity; it should not discover the machine or silently rewrite caps. Keep budget policy outside the model payload. The native host supplies capacity/headroom and owns the aggregate lease. Integrate through the existing job/service boundary; retained desktop activation B8 remains owner-held, and this study does not switch the desktop onto the retained facade. Distinguish an ordinary retained-method refusal from an aggregate resource refusal: the current dispatcher falls back to ordinary execution after retained refusal, so pool/headroom refusal must be handled before that dispatcher. It queues or returns a typed resource-unavailable result; it must not escape the pool through an unbounded ordinary fallback or silently change the requested solver mode.

An ordinary-route lease needs a whole-invocation bound over its existing supported domain. The retained D1 bound cannot price requests outside D1 or impose its 32-node cap on ordinary execution. Existing dense/sparse 6 GiB checks are component estimates, not that whole-product proof. Adaptive integration must preserve current ordinary capability while establishing its input, solver, output and handoff bounds; it cannot claim safety by silently shrinking the supported model family.

## Platform evidence and qualification

Apple documents [`ProcessInfo.physicalMemory`](https://developer.apple.com/documentation/foundation/processinfo/physicalmemory) as physical capacity in bytes and [`DispatchSourceMemoryPressure`](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure) as a pressure-state monitor. Neither is an available-byte guarantee. Apple's [XNU memory-status description](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md) distinguishes pressure-related available memory, including compressed/reclaimable pages, from fully reclaimable memory. Do not equate all such pages with immediately free capacity. A Rust native bridge and conservative byte-headroom policy need target-specific verification before adaptive admission is enabled. `host_memory.rs` reads `hw.memsize` as capacity, `kern.memorystatus_vm_pressure_level` as the pressure state (1/2/4; anything else unknown) and, from `host_statistics64`, headroom = (free_count − speculative_count − vm.vm_page_free_target) × page size. That counts only the free queue: speculative, purgeable, inactive, file-cache and compressor pages are excluded. It is an instantaneous host reading, not a guarantee under competing workloads. The pure core takes `RetainedByteLimit` and reports `retained_profile()` (identity, qualified limit, required bytes per mode); a limit above the qualified M is refused as `Unqualified`, never clamped.

Qualify the authorized 12 GiB target first, reusing unchanged numerical evidence and native layout atoms while checking all phases, registration bindings and affected resource refusals. Adaptive implementation then needs targeted checks for simultaneous acquisition races, insufficient/unknown/stale headroom, pressure transitions, result retention and poll-copy overlap, cancellation, panic and failed starts, plus independent review. Larger per-invocation thresholds must fit the qualified bound and the pool; larger input tiers must re-price the actual domain and native layouts. The same compiled product identity can share a deterministic policy version, but the chosen budget and typed resource refusal must be recoverable in the run's existing result/provenance interface. Public format changes, if needed, use one current format rather than compatibility variants.

The supported-machine statement should distinguish a 16 GiB base target from a guarantee under arbitrary competing workloads. Show the selected per-invocation budget, aggregate pool, queued work and reason for a resource refusal. Warn before a user requests a pool above the recommended machine fraction; acknowledgement cannot bypass a known insufficient-headroom or qualification refusal. A changing host load may change retained availability. Ordinary fallback after a method refusal remains possible only within its own admitted resource lease; it must not change the numerical predicates or fabricate a retained result. Release identity selection remains with B7's qualified build and the owner's release act.

MISSING: ordinary whole-invocation lease bound (the solve stage stays unpriced and serialized); ingress bounds for the other model commands, which Tauri deserializes before they run; target-specific adaptive qualification of larger per-invocation budgets.

NEEDS_HUMAN_RULING: how to bound the ordinary solve stage. A sound input-dependent bound needs a new staged pricing of the ordinary route, and an honest bound refuses some inputs admitted today, notably sparse-mode nonlinear supports, which form dense n² arrays without a guard. The alternative of enforcing the lease in a separate worker process would change the execution architecture. Until then the interim is the unpriced, serialized stage above. A change to the budget model, numerical domain or other reserved condition requires the corresponding owner decision.

DEPENDENCY_NOTES: no parallel scaling is claimed for unpriced ordinary work; larger numerical domains need their own qualification, and B8 retained desktop activation remains owner-held.
